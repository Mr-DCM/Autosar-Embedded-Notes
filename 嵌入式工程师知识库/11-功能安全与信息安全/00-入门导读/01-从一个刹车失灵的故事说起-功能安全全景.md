# 从一个刹车失灵的故事说起——功能安全全景

> 一句话定位：用一个"概率性刹车助力失效"的案例，把 ISO 26262 从 HARA 到验证的全流程走一遍，让 E2E、WdgM、Lockstep 这些名词各就各位，为整个 11 区建立全景坐标。
> 等级：L1 ｜ 前置：无

## 0. 开场：一辆"偶尔"踩不动的车

想象你在测一辆带电子刹车助力（iBooster 类）的车。一万次刹车里有那么两三次，踏板突然变得死硬——助力电机没出力，好在人的腿还有机械备份，车还是停住了。售后数据一汇总：失效概率大约百万分之一每次驾驶。

概率很低。但刹车这件事，一年要踩几十万次，路上有几百万辆车——"极小概率"乘以"巨大基数"，迟早变成新闻标题。工程师面对的问题从来不是"如何让助力永不失效"（电子的东西没有永不），而是：

**失效可以发生，但失效不允许演变成伤害。**

这一句话，就是功能安全的全部出发点，也是本区与 [07-AUTOSAR架构](../../07-AUTOSAR架构/README.md)（讲"怎么搭起来"）的根本区别——这里讲"搭起来的东西坏了怎么办"。

## 1. ISO 26262 是一套"驯化流程"

ISO 26262 不是一堆必须背的规则，而是一条流水线：把一个模糊的"会不会出事"的担忧，一步步驯化成可以写进代码、可以测试验证的具体要求。还是用刹车助力的例子走一遍：

**第一步：HARA（危害分析与风险评估）。** 问三个问题——刹车助力失效时，人还在开车吗（暴露度 E）？能控制住吗（可控性 C）？伤多重（严重度 S）？假设答案是"高速行驶时发生（E4）、司机来不及用力（C3）、可能致命（S3）"，这一格查表就是 **ASIL D**——最高安全等级。ASIL 不是玄学，就是"这事有多不能容忍"的量化打分。

**第二步：定安全目标。** 一句话写清楚期望行为："助力失效时，必须在 XX ms 内让司机以不超过 YY 牛的踏板力获得至少 ZZ% 的制动减速度。"这句目标后面会一路细化成软件需求。

**第三步：拆成安全机制。** 目标不能靠祈祷达成，得有具体手段：检测——电机堵转怎么发现？通信——发给助力电机的控制报文被干扰了怎么发现？执行——发现之后切换到什么备份路径？每个"怎么发现/怎么切换"的答案，就是一个安全机制。

**第四步：验证。** 故障注入测试——人为把电机驱动断掉，看备份路径是否在规定时间内接管；算失效率——单个机制不够就把冗余拼起来，证明整车的残余风险降到可接受水平。

顺手把 ASIL 四级（加 QM）的直觉表放这里，后面读到任何等级都不慌：

| 等级 | 一句话直觉 | 开发纪律 |
|---|---|---|
| QM | 坏了只是难用/不舒适，不伤人 | 按质量管理正常做，无附加安全要求 |
| ASIL A | 伤了也是轻伤，且司机多半能控制 | 基本的安全分析与验证 |
| ASIL B | 中等伤害，可控性一般 | 更严的评审、覆盖率与独立性要求 |
| ASIL C | 重伤概率上升，控制吃力 | 高覆盖要求，独立验证开始加码 |
| ASIL D | 可能致命且司机来不及反应（刹车/转向/气囊类） | 最高纪律：冗余、高诊断覆盖率、独立评估 |

记住方向就好：**等级越高，越不信任"单一机制"，越要求"坏了我能发现，发现了能兜底"**。

## 2. 安全机制：各自补"链条上的哪个环节"

你会在本区和邻区反复撞见这几个机制名。别背定义，记住它们在链条上的位置：

| 机制 | 补哪个环节 | 一句话直觉 |
|---|---|---|
| 看门狗 / WdgM | 程序"卡死/跑飞"的检测 | 定期按暗号打卡，不打卡就认为你出事了 |
| E2E 保护 | 总线传输的"数据坏了" | 报文自带 CRC 和计数器，收方验真再信 |
| Lockstep 锁步核 | CPU"自己算错"的检测 | 两个核算同一道题，答案不一致就停机 |
| MPU | 隔离，防"坏模块踩坏别人" | 给每个任务划地盘，越界直接触发异常 |
| 冗余 / 备份通道 | 执行环节的兜底 | 主路径失效时切换到降级路径保安全目标 |

分工上注意：**WdgM 的模块配置在 07 区**（[系统服务栈/WdgM](../../07-AUTOSAR架构/2-L2进阶/系统服务栈/WdgM/README.md)），**SecOC 的栈实现在 07 区加密栈**（[Csm/CryIf/Crypto 与 SecOC 配置](../../07-AUTOSAR架构/3-L3高级/加密栈/README.md)），**本区讲"为什么需要、原理本质、ASIL 怎么要求"**——两区互链，不重复。

## 3. 双支柱：功能安全 vs 信息安全

本区名字里有两个"安全"，它们防的不是一种东西：

- **功能安全（Safety，ISO 26262）**：假设**系统自己会坏**——元件老化、位翻转、软件 bug。对策是检测与冗余。
- **信息安全（Security，ISO 21434 / SecOC / HSM）**：假设**有人要弄坏你**——CAN 总线是广播的，插个 OBD 盒子就能发假报文。对策是认证与加密。

两根支柱互相帮忙：SecOC 防的"假报文让助力电机乱转"，本质上也是在保刹车这条安全目标；而 HSM 里跑的密钥，又依赖功能安全那套"程序卡死要能检测"的机制。所以本区把两根支柱放在一起学——L1/L2 带先吃透 26262 主线，Security 侧从 [ISO-21434概览](../2-L2进阶/ISO-21434概览/README.md) 入门。
