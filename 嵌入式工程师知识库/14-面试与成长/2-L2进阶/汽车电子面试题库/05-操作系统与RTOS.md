## 基础题（8 题——RTOS 通识必答）

**Q：前后台系统（super loop）和 RTOS 的区别？什么时候必须上 RTOS？**

答：前后台：主循环轮询 + 中断置标志——简单确定，但"任务"没有优先级，慢逻辑会阻塞快逻辑。RTOS：任务各自有优先级与栈，内核按优先级抢占调度——每个"逻辑"有自己的节拍。

必须上 RTOS 的信号：多个不同周期的逻辑（1ms/10ms/100ms）互相纠缠、需要阻塞式等待（等信号量/延时）而不想手写状态机、协议栈/文件系统这类中间件需要任务环境。点灯和简单状态机，前后台更稳。

出处：[前后台系统](../../../08-操作系统/1-L1基础/裸机与状态机编程/01-前后台系统.md)

**Q：RTOS 的任务状态有哪些？怎么迁移？**

答：典型五态：**运行**（占 CPU）↔ **就绪**（万事俱备只差 CPU）；运行 → **阻塞/等待**（等延时、信号量、消息）；阻塞条件满足 → 就绪；运行 → 挂起（Suspend，外部强停）；中断发生时运行被打断进中断态，退出后回就绪参与调度。

关键直觉：调度器只从"就绪"里挑最高优先级；阻塞不占 CPU——这就是 RTOS 比"死等轮询"省资源的本质。

出处：[调度模型](../../../08-操作系统/1-L1基础/RTOS通用原理/任务调度原理/01-调度模型.md)

**Q：抢占式调度和时间片轮询的区别？汽车 MCU 常用哪种？**

答：抢占式：高优先级任务一就绪立刻打断低优先级运行——响应确定，汽车 MCU 主流（OSEK/AUTOSAR OS、FreeRTOS 抢占模式）。时间片轮询：同优先级平分时间片，公平但响应不确定——消费电子常用。AUTOSAR OS 里同优先级任务按 FIFO（不支持时间片），要"确定性优先"——答案落在"车规要的是最坏情况可分析"。

出处：[调度模型](../../../08-操作系统/1-L1基础/RTOS通用原理/任务调度原理/01-调度模型.md)

**Q：上下文切换具体做了什么？开销多大？**

答：保存当前任务的现场（PC、寄存器、状态字；若有 FPU 再存 FPU 寄存器组）到它的栈/TCB，换栈指针，恢复下一个任务的现场。开销 = 汇编几十条指令 + cache/流水线失效，典型 1~10µs 量级。

两个工程含义：①中断频繁 + 高频任务 → 切换开销吃掉 CPU（用 traceOS 时间统计验证）；②TriCore 用 CSA 硬件栈管理上下文，切换更快但深度有限——CSA 耗尽是真实事故。

出处：[上下文切换](../../../08-操作系统/1-L1基础/RTOS通用原理/任务调度原理/02-上下文切换.md)

**Q：临界区保护有哪些手段？各自适用什么场景？**

答：从轻到重——①**关中断**：最直接，保护"对中断也可见的短临界区"（几行以内），关太久丢中断；②**锁调度**（SuspendScheduler）：只挡任务不挡中断，适合涉及多任务较长但不含中断共享的场景；③**互斥锁/信号量**：可阻塞、可跨长临界区，但注意优先级反转与死锁；④**硬件原子指令**：计数、标志类。

选型口诀：能原子不做锁，能关中断别关调度，锁的粒度最小化。

出处：[临界区](../../../08-操作系统/1-L1基础/RTOS通用原理/中断管理/02-临界区.md)

**Q：信号量和互斥锁的区别？什么时候必须用互斥锁？**

答：信号量：计数器，用于同步（等事件）与资源计数，谁都可以释放；互斥锁：所有权语义——谁加锁谁解锁，可配**优先级继承**防优先级反转。

必须用互斥锁的场景：保护"任务之间共享的可重入资源"（如一块缓冲、Flash 写操作），尤其当高优先级任务也可能抢这份资源。用二值信号量冒充锁的两个坑：无所有权（B 任务的代码可以解 A 任务的锁）+ 无优先级继承。

出处：[信号量](../../../08-操作系统/1-L1基础/RTOS通用原理/同步与互斥/01-信号量.md)、[互斥锁与优先级继承](../../../08-操作系统/1-L1基础/RTOS通用原理/同步与互斥/02-互斥锁与优先级继承.md)

**Q：什么是优先级反转？怎么解决？**

答：低优先级任务持有锁，高优先级任务等锁被阻塞，而**中优先级任务**抢先运行（它不需要锁）——高优先级被"不相干的中优先级"拖住，等效优先级倒挂。经典事故：火星探路者 reset。

解法：**优先级继承/天花板**——持锁的 low 任务临时抬升到等锁者的优先级，尽快放锁跑完。OSEK 的 RESOURCE 就是优先级天花板协议；FreeRTOS 互斥锁带继承，二值信号量没有。追答"信号量为什么没有继承"：信号量没有所有权概念，找不到该抬谁的优先级。

出处：[优先级反转案例](../../../08-操作系统/1-L1基础/RTOS通用原理/同步与互斥/05-优先级反转案例.md)

**Q：任务栈大小怎么定？溢出了什么现象、怎么查？**

答：定法三步：理论估（局部变量 + 调用深度）→ 实测（高水位标记法：启动时栈填 0xA5，跑全工况后看"水位线"）→ 加 30~50% 余量。注意中断也用当前任务栈（或独立栈，看内核）。

溢出现象：相邻内存被踩——变量莫名变化、硬件跑飞、HardFault。查法：栈金丝雀（canary 检查）、内核栈溢出钩子、TRACE32 监视栈水位。Autosar OS 的 stack monitoring / protection 配置就是干这个。

出处：[栈大小确定](../../../08-操作系统/1-L1基础/RTOS通用原理/内存管理/01-栈大小确定.md)、[栈溢出检测](../../../08-操作系统/1-L1基础/RTOS通用原理/内存管理/02-栈溢出检测.md)

## 进阶题（6 题——拉开差距）

**Q：OSEK OS 和 AUTOSAR OS 是什么关系？**

答：OSEK OS（ISO 17356）是基础规范：静态配置任务/中断/资源、固定优先级抢占、无动态创建。AUTOSAR OS 是 OSEK 的超集扩展：调度表（ScheduleTable，替代纯 Alarm 精确相位控制）、同步/异步计数器、时间保护与执行时间监控、内存保护（MPU）、多核支持（IOC）。

按扩展程度分 SC1~SC4：SC1≈OSEK，SC4 带保护与多核。答出"配置态生成、运行态零动态"这一 OSEK 血统即加分。

出处：[OSEK 内核](../../../08-操作系统/2-L2进阶/OSEK与AUTOSAR-OS/01-OSEK内核.md)、[AUTOSAR-OS 扩展](../../../08-操作系统/2-L2进阶/OSEK与AUTOSAR-OS/02-AUTOSAR-OS扩展.md)

**Q：1 类中断和 2 类中断的区别？**

答：OSEK 术语：**Category 1**——不经过内核、不能调 OS 服务、最快最确定（通常直接挂硬件向量）；**Category 2**——内核包装的 ISR（有 ISR 上下文），可用 ActivateTask/SetEvent 等"ISR 级 API"，代价是进出多一层封装。

工程惯例：高速硬实时（如电机 PWM 环）用 Cat1，普通外设通知用 Cat2。MCAL 驱动的中断配置里就按这个分类挂接。

出处：[OSEK 内核](../../../08-操作系统/2-L2进阶/OSEK与AUTOSAR-OS/01-OSEK内核.md)、[中断挂接规范](../../../04-MCAL与外设驱动/2-L2进阶/CDD设计方法论/02-中断挂接规范.md)

**Q：任务间通信选消息队列、事件组还是全局变量？**

答：**全局变量+锁**：最快，但耦合强、易忘锁，仅限模块内；**消息队列**：传"数据块"，天然解耦与缓冲（收发速率不匹配），开销是拷贝；**事件组**：传"发生了什么"（多事件位或/与等待），适合唤醒"等多个条件齐"的任务。选型看三问：传数据还是传状态？要不要缓冲？谁等谁？

出处：[消息队列](../../../08-操作系统/1-L1基础/RTOS通用原理/同步与互斥/04-消息队列.md)、[事件组](../../../08-操作系统/1-L1基础/RTOS通用原理/同步与互斥/03-事件组.md)

**Q：死锁四条件是什么？工程上怎么防？**

答：互斥、持有并等待、不可剥夺、循环等待——四条同时成立才死锁。预防手段对应拆一条：统一加锁顺序（拆循环等待，最常用）、一次性申请全部资源（拆持有并等待）、超时放弃重试（拆不可剥夺）。车规实践：模块设计文档里规定锁序 + code review 卡关；OS 的 GetResource 本身按天花板顺序就不允许嵌套乱序——这也是 OSEK RESOURCE 无死锁的原因。

出处：[死锁四条件](../../../08-操作系统/1-L1基础/RTOS通用原理/死锁与竞态分析/01-死锁四条件.md)

**Q：FreeRTOS 和 AUTOSAR OS 比有什么不同？**

答：FreeRTOS：动态创建任务（也可静态）、软件定时器、优先级抢占+可选协作、heap_1~5 内存方案可裁剪、生态大、免费——消费/工业常用，车规项目多用 AUTOSAR OS（静态、可认证、保护与调度表）。核心差异一句话：FreeRTOS 为灵活，AUTOSAR OS 为可认证可分析。答出"汽车量产认证链要求（26262 工具链/OS 认证）"即体现行业理解。

出处：[FreeRTOS 任务管理](../../../08-操作系统/2-L2进阶/FreeRTOS/01-任务管理.md)、[heap 方案对比](../../../08-操作系统/2-L2进阶/FreeRTOS/05-内存管理heap方案对比.md)、[商业实现对比](../../../08-操作系统/2-L2进阶/OSEK与AUTOSAR-OS/03-商业实现对比.md)

**Q：中断嵌套要不要开？什么原则？**

答：开嵌套=高优先级中断可打断低优先级中断，好处是关键事件延迟确定；代价是共享数据临界区更复杂（嵌套时低优先级 ISR 的数据被高优先级动）。原则：中断优先级映射要精心设计（见 02 区 TC377 SRC 路由），高频短小 ISR 高优先级、长处理 ISR 低优先级并把工作丢给任务（顶半/底半）；能不用嵌套就不用——不嵌套时临界区天然安全。

出处：[中断嵌套](../../../08-操作系统/1-L1基础/RTOS通用原理/中断管理/01-中断嵌套.md)、[顶半底半](../../../08-操作系统/1-L1基础/RTOS通用原理/中断管理/04-顶半底半.md)

## 区分度题（4 题——聊出深度）

**Q：讲一个你定位过的优先级反转/调度问题。**

答：STAR 模板：S——某 ECU 偶发 50~200ms 的 CAN 响应延迟，日志显示任务周期抖动；T——定位根因；A——先 OS 时间统计（哪些任务超预算）→ 发现日志任务（中优先级）频繁抢占 CAN 处理任务（高优先级）→ 追查发现 CAN 任务等一把被配置任务（低优先级）持有的二值信号量 → 换互斥锁（带优先级继承）+ 缩小临界区；R——抖动消失，写入问题单库。要点：展示"从现象到调度证据链"的路径，而不是背理论。

出处：[优先级反转案例](../../../08-操作系统/1-L1基础/RTOS通用原理/同步与互斥/05-优先级反转案例.md)、[竞态排查](../../../08-操作系统/1-L1基础/RTOS通用原理/死锁与竞态分析/02-竞态排查.md)

**Q：CPU 负载率怎么测？多少算安全？**

答：方法：空闲任务钩子里翻转 IO + 示波器测占空比；或 OS 提供的 idle 计数统计、ORTI/trace 工具（TRACE32 OS awareness 直接读）。车规经验值：稳态 <70%，峰值工况 <85%——留余量给最坏中断风暴与诊断刷写等突发。答出"负载率要分工况测（正常/诊断/下电写入）"是亮点。

出处：[调度模型](../../../08-操作系统/1-L1基础/RTOS通用原理/任务调度原理/01-调度模型.md)、[优先级设计](../../../08-操作系统/1-L1基础/RTOS通用原理/任务调度原理/03-优先级设计.md)

**Q：任务优先级怎么设计？说说你的方法论。**

答：按"截止期单调"（Rate Monotonic）起步：周期越短优先级越高（1ms > 10ms > 100ms）；再按关键性微调（安全相关任务拔高）；中断优先级全部高于任务；为未来扩展留空档（别把 1~10 用满）。验证：RMS 可调度性分析（利用率上界）+ 实测最坏响应时间。常见反面教材：把"最忙"的任务放最高优先级——忙不等于急。

出处：[优先级设计](../../../08-操作系统/1-L1基础/RTOS通用原理/任务调度原理/03-优先级设计.md)

**Q：看门狗为什么要窗口型？和 WdgM 怎么配合？**

答：普通看门狗只防"喂得太晚"（程序跑飞不喂）；窗口型还防"喂得太早"——喂狗必须落在窗口区间，任务失控空转狂喂也会被咬复位。WdgM 在此之上做**监督实体**管理：各任务在 checkpoint 打点，WdgM 判断"该到的没到/不该到的到了/执行超时"，全Alive 才由专用任务在正确时机喂硬件狗。这样"个别任务死而主循环还在喂"也能检出——功能安全的基础机制。

出处：[WdgM 联动](../../../04-MCAL与外设驱动/2-L2进阶/Wdg/04-WdgM联动.md)、[监督实体与 checkpoint](../../../07-AUTOSAR架构/2-L2进阶/系统服务栈/WdgM/01-监督实体与checkpoint.md)
