## 基础题（8 题——入门分水岭）

**Q：UDS 是什么？常用服务有哪些？**

答：UDS = Unified Diagnostic Services（ISO 14229），统一诊断服务协议，定义诊断仪与 ECU 的问答式交互（请求/正响应/负响应）。常用服务：0x10 会话控制、0x11 ECU 复位、0x14 清 DTC、0x19 读 DTC、0x22 读 DID、0x27 安全访问、0x2E 写 DID、0x28 通信控制、0x29 认证、0x31 例程控制、0x34/0x36/0x37 下载、0x3E Tester Present。

记忆钩子：按"会话→安全→读→写→控制→例程→刷写→保活"的使用顺序背。

出处：[服务总览](../../../06-诊断与标定/1-L1基础/UDS协议/01-服务总览.md)

**Q：三种诊断会话有什么区别？**

答：0x01 默认会话（上电即入，只开放基本读服务）、0x02 编程会话（刷写专用，开放 34/36/37）、0x03 扩展会话（开发/产线/售后常用，开放更多读写）。

关键机制：**非默认会话有 S3 定时器（5s）**——诊断仪必须周期发 0x3E 保活，超时 ECU 自动回落默认会话并撤销安全状态。这是"为什么刷写/标定中必须周期发 3E"的答案。

出处：[SID10 会话控制](../../../06-诊断与标定/1-L1基础/UDS协议/SID10-会话控制.md)、[会话与安全配置](../../../06-诊断与标定/2-L2进阶/Dcm配置/03-会话与安全配置.md)

**Q：负响应是什么？常见 NRC 有哪些？**

答：格式 `7F SID NRC`。高频 NRC：0x11 服务不支持、0x12 子函数不支持、0x13 长度/格式错、0x22 条件不满足、0x24 请求序列错、0x31 请求超范围、0x33 安全拒绝、0x35 密钥无效、0x36 超次数、0x37 时间延迟未到、0x78 响应挂起（pending）。

工程最要紧的是 **0x78**：Dcm 处理慢（如 Flash 擦除）时先回 78 拉长 P2*（5s）窗口，否则诊断仪按 P2（50ms）超时重发。

出处：[服务总览](../../../06-诊断与标定/1-L1基础/UDS协议/01-服务总览.md)

**Q：安全访问（0x27）流程是什么？为什么要配对发两个子函数？**

答：两步握手：①诊断仪发 `27 01`（请求种子）→ ECU 回随机 seed；②诊断仪本地算法算出 key，发 `27 02 key` → ECU 校验，通过则解锁对应安全等级。

配对原因：**01 请求种子会同时使已解锁状态失效**——重新请求 seed 即重新上锁，防止"解锁一次永远有效"。防暴力：连续 N 次（常 3 次）key 错误进入 0x36 拒绝 + 0x37 延时（如 10s），且 seed 算法由 Tier1/主机厂各自保密。

出处：[SID27 安全访问](../../../06-诊断与标定/1-L1基础/UDS协议/SID27-安全访问.md)

**Q：DID 是什么？读/写 DID 的流程？**

答：DID = Data Identifier，2 字节编号标识一份数据（如 F1 86 = 应用软件版本号）。读：`22 DID_H DID_L` → `62 DID + 数据`；写：`2E DID + 数据` → `6E DID`（或 0x78 pending，写 Flash 常见）。

设计约束：DID 数据长度、字节序、缩放由 CDD/ODX 描述；写 DID 常挂钩会话+安全等级（如软件号只读、产线数据需扩展会话解锁后写）。

出处：[SID22 读 DID](../../../06-诊断与标定/1-L1基础/UDS协议/SID22-读DID.md)、[SID2E 写 DID](../../../06-诊断与标定/1-L1基础/UDS协议/SID2E-写DID.md)

**Q：DTC 的 8 个状态位分别什么含义？**

答：bit0 testFailed（当前失败）、bit1 testFailedThisOperationCycle（本操作循环失败过）、bit2 pendingDTC（待定，跨循环确认中）、bit3 confirmedDTC（确认）、bit4 testNotCompletedSinceLastClear（清后未完成）、bit5 testFailedSinceLastClear（清后失败过）、bit6 testNotCompletedThisOperationCycle（本循环未完成）、bit7 warningIndicatorRequested（警示灯请求）。

讲清"pending→confirmed 的防抖逻辑"（故障连续出现 N 个循环才确认）是加分项。

出处：[事件与 DTC](../../../06-诊断与标定/2-L2进阶/Dem配置/01-事件与DTC.md)、[SID19 读 DTC](../../../06-诊断与标定/1-L1基础/UDS协议/SID19-读DTC.md)

**Q：清 DTC（0x14）实际做了什么？**

答：`14 FF FF FF`（组 0xFFFFFF = 全清）把指定组的 DTC 状态位清零、删除冻结帧与老化计数，并复位老化/操作循环统计。注意：**不是物理删除故障记录区**，只是状态复位；故障仍在则下个检测周期重新置位。0x19 01 与 0x14 的联动、按组（动力/底盘/车身/网络）分类清码是常见追问。

出处：[SID14 清 DTC](../../../06-诊断与标定/1-L1基础/UDS协议/SID14-清DTC.md)

**Q：OBD 和 UDS 是什么关系？**

答：OBD 是法规层（排放监管，ISO 15031 系），面向"读排放相关故障、就绪状态、冻结帧、清码"；UDS 是实现层协议，OBD 的九种服务（01/02/03/04/07/08/09/0A 等 Mode）在 CAN 上由 UDS 之外的一套简化 SID 承载。工程视角：排放 ECU 必须同时支持两套——OBD Mode 面向法规检测站，UDS 面向产线/售后深度诊断。

出处：[法规与模式](../../../06-诊断与标定/1-L1基础/OBD/01-法规与模式.md)

## 进阶题（7 题——拉开差距）

**Q：Dcm 的 DSL/DSD/DSP 三层各干什么？**

答：**DSL**（诊断会话层）管协议时序——P2/P2*、S3 定时、Tester Present、缓冲与并发诊断仪仲裁；**DSD**（服务分发）解析请求 SID/子函数，查服务表确定可用性（会话/安全/数据长度），决定走正响应或 NRC；**DSP**（服务处理）执行具体动作——回调 RTE/应用接口读写 DID、调 Dem 接口、驱动刷写例程。

一句话：DSL 管时间、DSD 管准入、DSP 管干活。排障"P2 超时"查 DSL 配置，"NRC 0x22"查 DSD 会话安全表。

出处：[DSL-DSD-DSP 分层](../../../06-诊断与标定/2-L2进阶/Dcm配置/01-DSL-DSD-DSP分层.md)

**Q：Dem 事件和 DTC 是什么关系？冻结帧存什么？**

答：DemEvent 是"一个故障检测"的逻辑实体（对应 SWC 里的一次判定），DTC 是它对外的编码（3 字节，含故障类别）。一个事件可有去抖动策略（计数器/时间）、老化次数、操作循环绑定——这些决定状态位如何迁移。

冻结帧（Snapshot）：故障首次确认时抓拍的现场数据（车速、电压、温度、相关信号），供 0x19 04 读取——"故障当时车在什么状态"的证据。

出处：[事件与 DTC](../../../06-诊断与标定/2-L2进阶/Dem配置/01-事件与DTC.md)、[冻结帧](../../../06-诊断与标定/2-L2进阶/Dem配置/02-冻结帧.md)

**Q：完整刷写流程走一遍？**

答：三段式——

- 预编程：全网 0x28 通信控制（静默其他 ECU）+ 0x85 关 DTC 记录 → 目标 ECU 进编程会话 0x10 02 → 0x27 安全解锁；
- 编程：0x31 例程检查预置（指纹/依赖）→ 0x34 请求下载（地址+长度）→ 0x36 循环传数据（CanTp 分段）→ 0x37 传输退出 → 0x31 校验（CRC/签名）→ 写软件号/DID；
- 后编程：0x11 ECU 复位 → 恢复通信 0x28/0x85 → 产线适配（写 VIN、码）。

每一步失败都有 NRC 路径，答出"为什么要静默全网（防刷写报文被干扰/防其他 ECU 报 DTC）"是亮点。

出处：[刷写流程总览](../../../06-诊断与标定/3-L3高级/Bootloader/01-刷写流程总览.md)、[SID34-37 刷写下载](../../../06-诊断与标定/1-L1基础/UDS协议/SID34-37-刷写下载.md)

**Q：0x34/36/37 在 Bootloader 里怎么落地？**

答：0x34 携带地址+长度，BL 校验 Flash 区间合法性后准备擦除；0x36 每块数据写入 RAM 缓冲再编程 Flash（回 0x78 掩盖擦写延时）；0x37 结束后 BL 对整段做 CRC 校验，比对 0x31 例程下发的期望值。要点：擦除以扇区为单位（先擦后写）、写入要按页对齐、失败要能回 NRC 且停在安全状态；驱动下载（Flash 驱动先写 RAM 再执行）是高配项目做法。

出处：[34-37 实现细节](../../../06-诊断与标定/3-L3高级/Bootloader/02-34-37实现细节.md)

**Q：XCP 和 UDS 的区别？**

答：定位不同：UDS 是**诊断**（故障、配置、刷写），问答式、慢节奏；XCP 是**标定与测量**（读改 RAM 变量、高速采集、DAIO），主从式、时间关键。XCP on CAN 一帧一命令（CONNECT/GET_STATUS/SET_MTA/DOWNLOAD/UPLOAD/DISCONNECT），批量数据走 DAQ 模式（ECC 周期性主动上传，不占主机问答带宽）。

口诀：UDS 管"坏没坏"，XCP 管"调得准不准"。

出处：[XCP on CAN](../../../06-诊断与标定/2-L2进阶/XCP与标定/01-XCP-on-CAN.md)

**Q：A2L 文件里有什么？**

答：标定描述文件：MEASUREMENT（观测变量：地址、类型、单位、转换公式）、CHARACTERISTIC（标定量：地址、类型、上下限、Format）、COMPU_METHOD（物理值转换：raw↔phys 公式/查表）、RECORD_LAYOUT（内存布局）、AXIS_pts（Map/曲线轴）+ XCP 协议参数（字节序、对齐）。

工程要点：A2L 的地址必须与实际固件 map 一致——链接变化后不重新生成 A2L，标定量就会写飞（经典事故源）。

出处：[A2L 文件](../../../06-诊断与标定/2-L2进阶/XCP与标定/02-A2L文件.md)

**Q：29 认证和 27 安全访问有什么不同？**

答：0x29 认证用非对称/证书方案（ISO 14229-1:2020 引入），支持一次性挑战-响应与证书校验，安全强度远高于 0x27 的对称 seed-key；面向"车载以太网/远程诊断/云端解锁"等开放通道场景。现状：传统 CAN 诊断仍以 27 为主，29 在新平台逐步落地——答"知道 29、用得少、为什么它更安全"即可。

出处：[SID29 认证](../../../06-诊断与标定/1-L1基础/UDS协议/SID29-认证.md)

## 区分度题（3 题——聊出深度）

**Q：P2 和 P2* 定时怎么用？0x78 的正确姿势？**

答：P2=50ms（诊断仪等首响应的时限），ECU 回 0x78 后切换到 P2*（5s）窗口，可连发 78 直到真响应或超时。配置要点：DcmP2TimerMax/P2* 参数与 DSL 任务周期匹配；回调函数预计超过 50ms（Flash 擦除、EEPROM 写）必须实现 pending 回调；否则诊断仪超时重发、Dcm 缓冲溢出连锁。真实事故叙事：写大 DID 没回 78，产线工位 50ms 超时重发 2E，双写竞争导致数据错乱。

出处：[DSL-DSD-DSP 分层](../../../06-诊断与标定/2-L2进阶/Dcm配置/01-DSL-DSD-DSP分层.md)、[会话与安全配置](../../../06-诊断与标定/2-L2进阶/Dcm配置/03-会话与安全配置.md)

**Q：双分区（A/B）与回滚怎么设计？**

答：Flash 分 Application A/B 两区 + 常驻 Bootloader：刷写时 BL 把新固件写入非活动分区，校验（CRC/签名）通过后置"启动指向"标志切换活动分区；新固件首跑自检失败则标志回滚到旧分区。要点：标志本身要有冗余（双份+CRC），防止"刷到一半断电"卡死；回滚次数与产线日志挂钩。这套讲清，等于证明你真碰过 Bootloader。

出处：[双分区与回滚](../../../06-诊断与标定/3-L3高级/Bootloader/03-双分区与回滚.md)、[Fls 依赖](../../../06-诊断与标定/3-L3高级/Bootloader/04-Fls依赖.md)

**Q：描述一次你做过的标定（或数据闭环）实操。**

答：STAR 骨架：S——某工况扭矩响应偏差，需要台架标 PI 参数；T——负责标定量梳理与 CANape 工程；A——从 map 文件整理标定量清单→生成 A2L→CANape 建 DAQ 列表在线观测→按工况扫点改参→冻结 Hex;R——台架复测达标，参数入库基线。如果没做过完整标定，诚实版："我做过 A2L 生成与地址核对、参与过两轮台架支持，标定策略本身是标定工程师定的，我保证工具链与数据正确。"

出处：[CANape 实操](../../../06-诊断与标定/2-L2进阶/XCP与标定/03-CANape实操.md)、[CANape 工具](../../../09-调试与测试/2-L2进阶/总线工具/03-CANape.md)
