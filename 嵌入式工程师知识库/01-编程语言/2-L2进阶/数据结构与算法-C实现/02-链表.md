# 02 链表

> 一句话定位：增删 O(1) 的动态结构，但在 AUTOSAR 静态分配的世界里它真正的价值是"侵入式"——节点直接挂在对象体内，零额外内存分配，事件队列、定时器链、DID 查找表全靠它。
> 等级：L2 ｜ 前置：[02-指针运算与多级指针](../../1-L1基础/指针专题/02-指针运算与多级指针.md)

## 原理

### 1. 单链表与双链表

| 结构 | 节点指针数 | 删除已知节点 | 反向遍历 |
|---|---|---|---|
| 单链表（Singly Linked List） | 1 个 `next` | O(n)（需找前驱） | 不支持 |
| 双链表（Doubly Linked List） | 2 个 `next/prev` | O(1) | 支持 |

嵌入式里**双链表是默认选项**，原因不是性能，而是删除方便——一个对象可能在多处被引用，删除时不需要先遍历找前驱，节省 CPU 也避免遍历过程中链表被改的风险。

### 2. 哨兵节点（Sentinel）：消除边界判断

普通链表的痛点是"删除头节点"和"删除中段节点"代码路径不同——每次操作前都要判 `if (head == node)`。引入一个**永不删、永不存数据的伪节点**当哨兵：

- 链表初始化时 `head = &sentinel; sentinel.next = NULL;`
- 所有节点都"前面有个东西"，删除时统一 `prev->next = node->next`
- 判空变成 `sentinel.next == NULL`，没有"链表头为空"的特殊分支

代码可读性提升巨大，分支变少对流水线友好的核（Cortex-M4 / TriCore）也是性能提升——分支预测失败的代价远大于多一次内存访问。

### 3. 侵入式链表（Intrusive）vs 外部容器式（Container）

**外部容器式**：节点里装一个数据指针，节点自己另开内存。

```c
typedef struct Node {
    void            *data;
    struct Node     *next;
} Node;
```

Linux 内核早期这么写，被骂了多少年——每个对象要分配两次（一次对象，一次节点），节点和对象生命周期管理乱成一锅粥，删了节点忘了删对象就内存泄漏。

**侵入式链表**：节点结构体直接嵌进对象体内，对象自带"挂载点"。

```c
typedef struct Timer {
    uint32          timeoutMs;
    TimerCb         callback;
    struct Timer    *next;   /* 嵌入式节点 */
} Timer;
```

好处：

- 零额外内存分配，AUTOSAR 里所有对象都是静态分配的，天然契合；
- 一个对象可以挂在多条链表上（多挂载点）；
- 节点和对象生命周期绑定，不会出现"删了节点忘删对象"的悬挂引用。

代价：节点结构是"侵入"对象体内的，**反向从节点拿回宿主对象**需要技巧——下一节讲。

### 4. offsetof + container_of：从节点反查宿主

侵入式链表的终极问题是"我手里只有一个 `Timer *next` 指针，怎么拿回外层宿主对象指针？"

答案是 `offsetof` + `container_of`：

```c
#include <stddef.h>
#define offsetof(TYPE, MEMBER) ((size_t)&(((TYPE *)0)->MEMBER))

#define container_of(ptr, type, member) \
    ((type *)((char *)(ptr) - offsetof(type, member)))
```

原理：把 `NULL` 假装成一个 `type *`，访问其 `member` 字段的地址——这个地址数值就是 member 在结构体内的偏移量。然后从节点指针往前回退这个偏移，就回到了宿主对象首地址。

这是 Linux 内核 `list_head` 工作的全部魔法。它对编译器实现友好（绝大多数编译器都正确处理），但 **MISRA-C 视角下却是个雷区**：

- **Rule 11.3**：cast pointer to different object type ——`(char *)(ptr)` 把节点指针强转 `char *`；
- **Rule 11.8**：cast to pointer to more qualified——类型限定符变化；
- **Rule 19.13**：`offsetof` 依赖未定义行为（标准只对 POD 类型有定义，但 C 里所有 struct 都是 POD，所以这条几乎不会触发）。

**MISRA 友好的两种替代写法**：

**写法 A：宿主反向指针（最稳，AUTOSAR 推荐）**

节点里直接多存一个 `owner` 指针，构造时初始化：

```c
typedef struct ListNode {
    struct ListNode *next;
    void            *owner;   /* 反向指向宿主对象 */
} ListNode;
```

每个对象多占 4 字节，但完全合规、可读、零 UB。这是 AUTOSAR OS 和大部分商用栈的做法。

**写法 B：deviation（偏离声明）保留 container_of**

团队做一次正式 deviation：声明此宏在内部限定使用、有单元测试覆盖、所有调用点静态可验证。生产代码里把宏声明放在统一头文件，加注释引用 deviation ID。

下面代码示例两种写法都给出。

## 代码示例

### 4.1 双向链表 + 哨兵：事件链表（侵入式，写法 A）

```c
/* 02-链表示例：事件链表（侵入式 + 反向指针，MISRA 友好） */
#include "Std_Types.h"

/* 通用链表节点：双向 + 哨兵 + 反向 owner 指针 */
typedef struct ListNode {
    struct ListNode *next;
    struct ListNode *prev;
    void            *owner;   /* 反向指向宿主对象，避免 container_of */
} ListNode;

/* 链表头：哨兵节点 */
typedef struct {
    ListNode         sentinel;   /* 永不删的伪节点 */
} ListHead;

/* 初始化：哨兵自指，表示空链表 */
void List_Init(ListHead *list)
{
    list->sentinel.next = &list->sentinel;
    list->sentinel.prev = &list->sentinel;
    list->sentinel.owner = NULL;
}

/* 头插法：把节点插到哨兵之后 */
void List_PushFront(ListHead *list, ListNode *node, void *owner)
{
    ListNode *first = list->sentinel.next;
    node->owner = owner;
    node->next  = first;
    node->prev  = &list->sentinel;
    first->prev = node;
    list->sentinel.next = node;
}

/* 删除任意节点：O(1)，无需找前驱 */
void List_Remove(ListNode *node)
{
    node->prev->next = node->next;
    node->next->prev = node->prev;
    node->next = NULL;
    node->prev = NULL;
}

/* 判空：哨兵自指即空 */
boolean List_IsEmpty(const ListHead *list)
{
    return (list->sentinel.next == &list->sentinel) ? TRUE : FALSE;
}

/* 遍历：从哨兵的下一个开始，到回到哨兵为止 */
typedef void (*ListVisitCb)(void *owner, void *arg);
void List_ForEach(const ListHead *list, ListVisitCb cb, void *arg)
{
    const ListNode *cur = list->sentinel.next;
    while (cur != &list->sentinel) {
        cb(cur->owner, arg);
        cur = cur->next;
    }
}
```

### 4.2 应用：定时器链表（按到期时间排序插入）

```c
/* 应用：软件定时器，按到期时间升序挂在链表上 */
typedef struct SwTimer {
    ListNode         node;       /* 嵌入式链表节点 */
    uint32           timeoutMs;  /* 距离到期的毫秒数 */
    TimerCb          callback;   /* 到期回调 */
    void            *cbArg;      /* 回调参数 */
} SwTimer;

static ListHead g_TimerList;

void SwTimer_Init(void)
{
    List_Init(&g_TimerList);
}

/* 链表已按 timeoutMs 升序，新定时器插入到合适位置 */
void SwTimer_Start(SwTimer *timer, uint32 timeoutMs, TimerCb cb, void *arg)
{
    ListNode *cur;
    timer->timeoutMs = timeoutMs;
    timer->callback  = cb;
    timer->cbArg     = arg;

    /* 找到第一个 timeout 大于新 timer 的位置，插在它前面 */
    cur = g_TimerList.sentinel.next;
    while (cur != &g_TimerList.sentinel) {
        SwTimer *t = (SwTimer *)cur->owner;   /* 反向取宿主：写法 A */
        if (t->timeoutMs > timeoutMs) {
            break;
        }
        cur = cur->next;
    }
    /* 插在 cur 前面：复用头插思路改 next/prev */
    timer->node.owner = timer;
    timer->node.next  = cur;
    timer->node.prev  = cur->prev;
    cur->prev->next   = &timer->node;
    cur->prev         = &timer->node;
}

/* 周期调度：链表头最先生效，链表本身保证有序 */
void SwTimer_Tick(uint32 elapsedMs)
{
    ListNode *cur;
    ListNode *next;

    cur = g_TimerList.sentinel.next;
    while (cur != &g_TimerList.sentinel) {
        SwTimer *t = (SwTimer *)cur->owner;
        next = cur->next;
        if (t->timeoutMs > elapsedMs) {
            t->timeoutMs -= elapsedMs;
            break;   /* 链表有序，后面的更没到期 */
        }
        /* 到期：先从链表摘下，再回调（回调里可能再次启动自己） */
        List_Remove(cur);
        if (t->callback != NULL) {
            t->callback(t->cbArg);
        }
        cur = next;
    }
}
```

### 4.3 写法 B 对照：container_of 版本

如果团队选择 deviation 保留 `container_of`，定时器结构改成：

```c
/* container_of 版本：节点不存 owner，靠偏移反查 */
#define CONTAINER_OF(ptr, type, member) \
    ((type *)((uint8 *)(ptr) - (uint32)offsetof(type, member)))

typedef struct SwTimerIntrusive {
    ListNode         node;       /* 不再存 owner */
    uint32           timeoutMs;
    TimerCb          callback;
    void            *cbArg;
} SwTimerIntrusive;

/* 取宿主：CONTAINER_OF(cur, SwTimerIntrusive, node) */
/* MISRA Deviation: DEV-LIST-001 引用 Rule 11.3 偏离声明 */
```

省 4 字节/节点，但代码评审必须每次检查 deviation 引用，新人维护成本高。

## 易错点与陷阱

1. **`next`/`prev` 没初始化**：节点对象静态分配时是 0，看着像 NULL，但插入前忘调 `List_PushFront` 直接用，下次遍历就跳到 0 地址硬错误。推荐节点结构在 `List_Remove` 后强制 `next = prev = NULL`，下次插入前可断言"必须是 NULL 才允许插入"。

2. **哨兵节点未初始化**：用静态全局 `ListHead g_list;` 没调 `List_Init`，sentinel 的 next/prev 是 0，第一次插入就崩。要么用静态初始化 `= {0}` 加显式 Init，要么用宏 `#define LIST_INIT(name) {&(name).sentinel, &(name).sentinel, NULL}`。

3. **链表遍历中删除节点**：`while(cur != NULL) { cb(cur); if(条件) List_Remove(cur); cur = cur->next; }` ——删除后 `cur->next` 已被改成 NULL。正确做法是先 `next = cur->next`，再处理。

4. **侵入式链表同一对象挂多条链**：节点结构必须为每条链各放一个 `ListNode` 成员，共用一个会乱。例如同时挂"超时链"和"类型分组链"：

   ```c
   typedef struct Event {
       ListNode timeoutNode;
       ListNode typeNode;
       ...
   } Event;
   ```

5. **`container_of` 在 union 上用**：union 没有"固定布局"，offset 不稳定。侵入式节点不要放进 union。

6. **MISRA 报 Rule 11.3 就无脑删 `container_of`**：要看 deviation 流程是否建立。直接改回"反向指针写法"是更稳的选择，但会增加内存占用——评审要权衡。

7. **中断里调用 `List_PushFront` 但任务里也调用**：链表操作的多个指针写入不是原子的，跨 ISR/任务使用必须关中断或加锁。

8. **回调里销毁对象本身**：`SwTimer_Tick` 里直接 `free(timer)`——链表迭代器还指向它。务必先 `List_Remove`，回调完再决定释放。

## 面试高频题

**Q1：为什么 Linux 内核链表都用侵入式而不是外部容器式？**
A：(1) 零额外内存分配，内核不能依赖 malloc；(2) 一个对象可挂多条链表（多节点成员）；(3) 节点与对象生命周期绑定，无悬挂引用；(4) 通用 `list_head` 不依赖数据类型，泛型性来自 container_of 反查宿主。

**Q2：哨兵节点解决了什么问题？**
A：消除"链表头为空"的特殊分支。所有节点的"前面有个东西"，删除/插入操作不需要判 `if (head == NULL)`，代码统一。代价是占一个空节点内存，对几十节点的链表完全可以接受。

**Q3：双链表比单链表多用一个 prev 指针，什么场景值得？**
A：删除已知节点 O(1) vs O(n)。凡是"对象可能在多处被引用、被随时删除"的场景——定时器到期删除、事件取消、DID 表项动态注销——双链表都更合适。单链表适合只追加、只头删的栈/队列场景。

**Q4：`container_of` 在 MISRA-C 下违规的具体规则是什么？怎么替代？**
A：违反 Rule 11.3（指针类型转换）、Rule 11.8（限定符变化）。MISRA 友好的替代是节点里加 `void *owner` 反向指针，构造时初始化。多 4 字节/节点，但完全合规可读。生产代码可选 deviation 保留 container_of，需正式声明 + 单测覆盖。

**Q5：AUTOSAR 里链表为什么用得不多？**
A：AUTOSAR 强调静态配置 + 生成代码，运行时动态数据结构很少。但 CDD 复杂驱动里软件定时器、自定义事件分发、动态注册的诊断回调常常自己实现小链表——这是 CDD 工程师的常见武器。

**Q6：定时器链表按到期时间排序插入有什么好处？**
A：`Tick` 时只需要看链表头一个节点：head 没到期，后面的肯定也没到期，提前 break。复杂度从 O(n) 降到 O(到期数)。代价是插入时 O(n) 找位置——但定时器通常一次性启动、长期运行，插入代价可摊薄。
