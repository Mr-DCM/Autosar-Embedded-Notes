# 03 队列与栈

> 一句话定位：FIFO（First-In First-Out）与 LIFO（Last-In First-Out）是两块最基础内存模型——队列做诊断请求积压、栈做任务上下文切换的容器，CDD 里几乎每天都用，只是没有标准库帮你写好。
> 等级：L2 ｜ 前置：[01-环形缓冲区](01-环形缓冲区.md)

## 原理

### 1. 队列：FIFO 与环形复用

队列的语义是"先入先出"。在静态分配的嵌入式世界里，**数组实现的环形队列**是默认选择——头尾两根索引在数组里循环绕圈，详见 [01-环形缓冲区](01-环形缓冲区.md)。本节只补一节"为什么不用链表实现队列"。

链表队列的优势是大小动态、增删 O(1)，但代价：

- 每个节点多 4~8 字节指针开销；
- 节点动态分配带来内存碎片风险（AUTOSAR 默认禁用 `malloc`）；
- 节点池管理代码量比环形队列多一倍。

所以 **AUTOSAR 几乎所有"队列"都退化成定长数组环形缓冲**——大小由 ARXML 配置，编译期固定。链表队列只用于节点生命周期不确定的场景（如动态注册的回调）。

### 2. 优先级队列：按优先级出队

普通队列只看时间——"先到的先服务"。优先级队列（Priority Queue）按优先级出队：**高优先级先出，同优先级再按 FIFO**。

嵌入式里有两种实现思路：

**思路 A：插入排序式（适合数据量小、出队频率高）**

入队时遍历找位置、后移元素、插入。出队 O(1)。N 个元素入队 O(N²)，但 N 一般很小（< 16），代码简单，常用于诊断请求队列。

**思路 B：多桶队列（适合优先级数固定）**

每级优先级一个独立队列（数组），出队时从最高级开始扫。N 级优先级扫描 O(N)。OS 任务调度（如 OSEK Priority Ceiling）就是这种思路——ready list 按 priority 分桶。

AUTOSAR OS 内部优先级队列是 B 类，但 CDD 自己实现的诊断/事件队列通常是 A 类。

### 3. 栈：LIFO 与嵌入式应用

栈的语义是"后入先出"。教科书案例是括号匹配、表达式求值——嵌入式里很少自己写表达式解析，但栈的实际身影无处不在：

- **函数调用栈**：编译器自动管理，CDD 工程师无需关心机制，但要理解"栈不够深就 Stack Overflow"——这部分见 [内存管理](../内存管理/README.md)。
- **任务上下文切换**：合作式调度器手动 `push/pop` 寄存器到任务私有栈数组，下一节讲。
- **递归算法的迭代化**：深度优先搜索用显式栈替代递归，避免栈深不可控。
- **UDS 多帧收发**：ISO-TP 中收到的分段包用栈暂存、收到最后一帧再组装。

### 4. 用数组实现任务上下文保存

OS 任务切换时，需要把当前 CPU 寄存器状态保存到"任务控制块"（TCB）里，下次切回来时再恢复。硬件 SP（栈指针）可以指向每个任务独立的栈段，也可以用数组显式保存——后者更直观、便于调试，代价是不能用编译器自动生成的 prologue/epilogue。

下面给的代码示例就是一个**最小化合作式调度器**：每个任务一个上下文结构体数组，主循环依次恢复运行。

## 代码示例

### 4.1 诊断请求优先级队列（插入排序式）

```c
/* 03-队列与栈示例：诊断请求优先级队列 */
#include "Std_Types.h"
#include <string.h>

#define DIAG_QUEUE_CAPACITY    (8u)   /* 诊断请求通常不会同时积压 8 个 */
#define DIAG_DATA_MAX_LEN      (8u)   /* 单帧诊断数据最大长度，多帧另走 ISO-TP */

/* 优先级定义：数值越小优先级越高 */
#define DIAG_PRIO_PROGRAMMING  (0u)   /* 刷写/安全：最高 */
#define DIAG_PRIO_ROUTINE       (1u)   /* 例程控制 */
#define DIAG_PRIO_READ          (2u)   /* 读 DID/状态 */
#define DIAG_PRIO_DEFAULT       (3u)   /* 默认 */

typedef struct {
    uint8  serviceId;        /* UDS SID，如 0x22/0x27/0x31/0x34/0x36 */
    uint8  subFunction;      /* 子功能 */
    uint16 did;              /* DID/RID，仅 0x22/0x2E 用 */
    uint8  priority;         /* 优先级 */
    uint8  dataLen;
    uint8  data[DIAG_DATA_MAX_LEN];
    uint32 sequence;         /* 同优先级 FIFO 排序用 */
} DiagRequest;

typedef struct {
    DiagRequest  slots[DIAG_QUEUE_CAPACITY];
    uint8        count;
    uint32       sequenceCounter;   /* 单调递增，保证同优先级 FIFO */
} DiagRequestQueue;

static DiagRequestQueue g_DiagQueue;

void DiagQueue_Init(DiagRequestQueue *q)
{
    q->count = 0u;
    q->sequenceCounter = 0u;
}

boolean DiagQueue_IsFull(const DiagRequestQueue *q)
{
    return (q->count >= DIAG_QUEUE_CAPACITY) ? TRUE : FALSE;
}

boolean DiagQueue_IsEmpty(const DiagRequestQueue *q)
{
    return (q->count == 0u) ? TRUE : FALSE;
}

/*
 * 入队：插入排序式
 * 排序键：(priority ASC, sequence ASC)
 * 遍历找到第一个 priority > 新请求的位置，其后元素整体后移一位，新元素插入空位。
 * 入队 O(N)，出队 O(1)。
 */
boolean DiagQueue_Enqueue(DiagRequestQueue *q, const DiagRequest *req)
{
    uint8 i;
    uint8 insertPos;

    if (q->count >= DIAG_QUEUE_CAPACITY) {
        return FALSE;   /* 队列满 */
    }
    /* 赋序号：保证同优先级按入队顺序 FIFO */
    insertPos = q->count;
    for (i = 0u; i < q->count; i++) {
        if (q->slots[i].priority > req->priority) {
            insertPos = i;
            break;
        }
    }
    /* insertPos 之后元素整体后移一位 */
    for (i = q->count; i > insertPos; i--) {
        q->slots[i] = q->slots[i - 1u];
    }
    q->slots[insertPos] = *req;
    q->slots[insertPos].sequence = q->sequenceCounter++;
    q->count++;
    return TRUE;
}

/* 出队：永远取 slots[0]，剩余前移 */
boolean DiagQueue_Dequeue(DiagRequestQueue *q, DiagRequest *outReq)
{
    uint8 i;

    if (q->count == 0u) {
        return FALSE;
    }
    *outReq = q->slots[0];
    for (i = 0u; i < (q->count - 1u); i++) {
        q->slots[i] = q->slots[i + 1u];
    }
    q->count--;
    return TRUE;
}

/* 把 UDS 接收到的请求包装为队列项入队 */
void Diag_OnRxIndication(uint8 sid, uint8 subFunc, uint16 did,
                         uint8 prio, const uint8 *data, uint8 dataLen)
{
    DiagRequest req;
    req.serviceId  = sid;
    req.subFunction = subFunc;
    req.did        = did;
    req.priority   = prio;
    req.dataLen    = (dataLen > DIAG_DATA_MAX_LEN) ? DIAG_DATA_MAX_LEN : dataLen;
    (void)memcpy(req.data, data, req.dataLen);

    (void)DiagQueue_Enqueue(&g_DiagQueue, &req);
}

/* 主循环消费：高优先级请求先处理 */
void Diag_MainFunction(void)
{
    DiagRequest req;
    while (DiagQueue_Dequeue(&g_DiagQueue, &req) == TRUE) {
        Diag_ProcessRequest(&req);   /* 按 SID 路由处理 */
    }
}
```

### 4.2 任务上下文栈（合作式调度器）

下面给一个**简化视角**：每个任务有独立上下文块，主循环遍历"保存-恢复"。真实 OS 的上下文切换在汇编层做（PendSV/Trap），这里用 C + 数组展示原理，便于理解任务切换的内存模型。

```c
/* 任务上下文：保存一份寄存器快照 */
typedef struct {
    uint32 r4;
    uint32 r5;
    uint32 r6;
    uint32 r7;
    uint32 r8;
    uint32 r9;
    uint32 r10;
    uint32 r11;
    uint32 sp;       /* 任务私有栈指针 */
    uint32 pc;       /* 任务入口/恢复点 */
    uint32 flags;    /* 状态标志：READY/RUNNING/SUSPENDED */
} TaskContext;

#define TASK_MAX_COUNT   (4u)
typedef enum {
    TASK_READY     = 0x01u,
    TASK_RUNNING   = 0x02u,
    TASK_SUSPENDED = 0x04u
} TaskState;

static TaskContext g_TaskTable[TASK_MAX_COUNT];   /* 任务上下文数组（栈） */
static uint8       g_CurrentTask = 0u;

/* 任务"压栈"：把当前寄存器存到 task 的 context 块 */
/* 真实场景由 trap handler 在汇编层完成，这里给 C 视角 */
void Task_SaveContext(uint8 taskId)
{
    TaskContext *ctx = &g_TaskTable[taskId];
    /* 这里在汇编层会 push r4-r11 到当前 SP，再把 SP 存到 ctx->sp */
    /* C 视角下省略硬件细节 */
    ctx->flags = TASK_READY;
}

/* 任务"出栈"：从 task 的 context 块恢复寄存器 */
void Task_RestoreContext(uint8 taskId)
{
    TaskContext *ctx = &g_TaskTable[taskId];
    /* 真实场景：从 ctx->sp 恢复 SP，pop r4-r11，ret 触发 PC 切换 */
    ctx->flags = TASK_RUNNING;
    g_CurrentTask = taskId;
    (void)ctx;   /* 真实场景不会返回，会跳到 ctx->pc */
}

/* 合作式调度：当前任务主动 yield 后，主循环选下一个 READY 任务恢复 */
void Schedule_Next(void)
{
    uint8 i;
    uint8 next = g_CurrentTask;

    Task_SaveContext(g_CurrentTask);

    /* 轮询找下一个 READY 任务 */
    for (i = 1u; i <= TASK_MAX_COUNT; i++) {
        uint8 candidate = (uint8)((g_CurrentTask + i) % TASK_MAX_COUNT);
        if (g_TaskTable[candidate].flags == TASK_READY) {
            next = candidate;
            break;
        }
    }
    Task_RestoreContext(next);
}
```

## 易错点与陷阱

1. **优先级队列的"同优先级 FIFO"忘了实现**：只比较 priority 入队，同优先级的入队顺序乱掉——两个 0x22 请求被乱序处理，导致上位机超时。务必加 sequence 单调递增字段作为次序键。

2. **诊断请求队列满直接丢**：刷写流程里诊断请求被丢掉，上位机不知道，永远超时。队列满应回调 Dcm 返回 NRC 0x21（General reject）或 NRC 0x22（Conditions not correct），不要静默丢弃。

3. **入队时 memcpy 越界**：`data` 字段定长 8 字节，但调用方传了 64 字节多帧数据没截断。入队接口必须钳位 `dataLen`。

4. **数组实现的栈容量固定**：忘记 `IsFull` 检查，push 第 N+1 个元素就越界写穿相邻变量。生产代码务必每次 push 前检查。

5. **任务上下文切换的"嵌套"问题**：高优先级中断切断了 yield 流程，下次切回来时 ctx->pc 指向的不是 yield 点而是中断里被强切的位置。务必确保上下文保存/恢复是原子的（关中断或 trap handler 处理）。

6. **栈元素对齐**：上下文块里 PC/SP 必须 4 字节对齐（Cortex-M / TriCore），手写 struct 时加 `__attribute__((aligned(4)))` 或编译选项 `#pragma pack`，否则 Unaligned Access 触发 HardFault。

7. **队列环形索引溢出**：`uint8 head` 在 256 队列里溢出回 0 时正好绕回正确，但同队列不同长度溢出可能逻辑错误。索引类型必须能容纳 `2 * capacity`。

8. **优先级反转**：低优先级任务持有共享资源，高优先级诊断请求被卡住。优先级队列本身解决不了这个——需要资源继承协议，AUTOSAR OS 的 `GetResource` 带优先级提升机制。

## 面试高频题

**Q1：嵌入式里为什么队列大多用数组环形而不是链表？**
A：(1) 静态分配，无 malloc 碎片风险；(2) 节点无指针开销，内存利用率高；(3) 缓存友好（连续内存）；(4) 代码量少。代价是容量固定、出队后元素整体前移 O(N)——但小队列上这点开销忽略不计。

**Q2：优先级队列的"插入排序式"和"多桶式"实现怎么选？**
A：插入排序适合小规模（N<16）、出队频繁、优先级数不固定；多桶适合优先级数固定、出队频繁、规模大（OS 任务调度）。诊断请求队列通常 N<8 用插入排序就够；OS ready list 用多桶。

**Q3：为什么同优先级请求要保证 FIFO？**
A：(1) 上位机的预期是顺序服务，乱序会导致状态机错乱（如先 ReadDID 再 WriteDID 不能反）；(2) 调试可预测；(3) 复现 bug 方便。实现方式是入队时给每个请求单调递增的 sequence 号，排序时 `(priority, sequence)` 联合排序。

**Q4：任务上下文切换为什么不在 C 函数里做？**
A：(1) C 函数有 prologue/epilogue 会破坏当前寄存器；(2) PC 切换要直接跳转而不是 return；(3) SP 切换需要直接操作 SP 寄存器，C 不允许直接访问。所以上下文切换一定在 trap handler 汇编层做，C 层只是触发 trap 和准备 TCB。本节给 C 视角只是为了展示数据结构。

**Q5：诊断队列满了应该怎么处理？**
A：不能静默丢弃，应该：(1) 回 NRC 0x22 (ConditionsNotCorrect) 给上位机；(2) 触发 Det 报错；(3) 计数溢出次数便于事后分析。流量控制由 ISO-TP 的 Stmin/BS 保证，但应用层队列仍需独立限流。

**Q6：栈溢出（Stack Overflow）和队列溢出有什么区别？**
A：栈溢出是堆栈段不够深，函数调用层数过多或局部变量过大，触发 HardFault；队列溢出是元素数量超过容量，是逻辑判断失误。前者是内存规划问题，后者是设计限流问题。AUTOSAR Stack 估算工具专门解决前者。
