# 05 排序与查找

> 一句话定位：嵌入式世界 90% 的"排序"在编译期完成、90% 的"查找"用二分走有序静态表——运行时复杂排序是反模式，DID 表是这套思想的典型战场。
> 等级：L2 ｜ 前置：[01-指针与数组](../../1-L1基础/指针专题/01-指针与数组.md)

## 原理

### 1. 嵌入式排序的取舍

教科书里讲快排、归并、堆排序——CDD 工程师一年用不上一次。原因：

- **静态表为主**：DID 表、RID 表、IO 硬件抽象映射、信号路由表都是编译期生成的常量表，写源码时手动按 key 升序填好，运行时不排序；
- **数据量小**：DID 表通常几十到几百条，O(N) 线性查找都不慢，O(log N) 二分更稳；
- **运行时排序代价高**：栈深不确定（递归快排）、最坏复杂度 O(N²)（快排在已排序表上退化）、函数指针调用（`qsort` 的 comparator）——这三个点在功能安全 / MISRA 评审里几乎过不去。

什么时候才真需要运行时排序？极少：

- 在线学习算法里的 top-K（罕见）；
- 动态注册的回调按优先级排序（其实可以用 [优先级队列](03-队列与栈.md) 代替）；
- 调试日志按时间戳排序输出（开发期工具，不进生产）。

> 经验：CDD 工程师 95% 的"排序"问题答案都是"把表写源码里按升序填好"，剩下 5% 是"用优先级队列代替排序"。

### 2. 二分查找详解

二分查找（Binary Search）在有序数组上找目标值，复杂度 O(log N)。算法本身简单，但**边界写法能写错十种**，每个错版都能在某些测试用例下"碰巧工作"。

#### 循环不变量（Loop Invariant）

正确的二分查找满足不变量：**若 target 存在，必在区间 [low, high) 内**。

- 区间是**左闭右开** `[low, high)`：`low` 包含、`high` 排除；
- 初始 `low = 0, high = N`（N 个元素，索引 0..N-1，high 取 N 表示"哨兵"）；
- 每次迭代要么 `low = mid + 1`（target 在右半），要么 `high = mid`（target 在左半含 mid）；
- 终止条件 `low == high`：区间为空，target 不存在。

关键：因为 `mid` 已经被比较过且不等于 target，下一次的 `low` 可以从 `mid + 1` 开始；而 `high = mid` 不是 `mid - 1`，因为右开区间本来就排除 `high`。

#### 三种常见错版对比

| 版本 | 关键写法 | 错误 |
|---|---|---|
| 错版 A | `mid = (low + high) / 2` | `low + high` 在大数组上溢出，TC377 上 32 位 int 撑不住 |
| 错版 B | `high = mid - 1`（用左闭右闭区间） | 区间定义和不变量混用，写错边界条件就漏掉 `mid` 这个值 |
| 错版 C | `low = mid`（不 +1） | `low = mid` 时如果 `low = mid = high - 1`，下次迭代区间没缩小，**死循环** |

正确版（左闭右开）：

```c
uint16 low = 0u;
uint16 high = N;       /* 注意是 N，不是 N-1 */
while (low < high) {
    uint16 mid = low + (high - low) / 2u;   /* 防溢出 */
    if (table[mid].key == target) {
        return mid;
    } else if (table[mid].key < target) {
        low = mid + 1u;
    } else {
        high = mid;    /* 不是 mid - 1 */
    }
}
return NOT_FOUND;
```

#### 边界验证

- N = 0（空表）：直接返回 NOT_FOUND，循环不进入。
- N = 1：low = 0, high = 1，mid = 0；相等返回，不等时要么 low = 1（high == low == 1 退出），要么 high = 0（low == high == 0 退出）。两种都正确终止。
- 找不到的元素比所有元素大：low 一直推到 N，high == N 退出。
- 找不到的元素比所有元素小：high 一直退到 0，low == 0 退出。

### 3. 有序静态表 vs 哈希

DID 查找的两种思路：

| 方案 | 时间复杂度 | 空间 | 适用 |
|---|---|---|---|
| 有序表 + 二分 | O(log N) | 紧凑（仅 N 条） | DID 数量 < 几千，编译期固定 |
| 哈希表 | O(1) 平均 | 大（桶数组 + 拉链） | DID 数量上万、运行时动态增删 |

DID 通常几十到几百条，且**编译期完全确定**——哈希表的 O(1) 收益在 N=100 时（二分 7 次比较）几乎无感，反而要付出哈希函数 + 桶数组 + 冲突处理的内存代价。**AUTOSAR 里 DID 查找一律有序表二分**，这是产业共识。

### 4. qsort 与嵌入式顾虑

标准库 `qsort` 用法：

```c
int cmp_did(const void *a, const void *b) {
    uint16 x = ((const DidEntry *)a)->did;
    uint16 y = ((const DidEntry *)b)->did;
    return (x > y) - (x < y);   /* 安全比较，避免溢出 */
}
qsort(table, N, sizeof(DidEntry), cmp_did);
```

嵌入式上的顾虑：

1. **递归 + 栈深不确定**：标准 `qsort` 大多递归实现，最坏情况栈深 O(log N)~O(N)，AUTOSAR 任务栈估算工具不友好；
2. **函数指针违反 MISRA Rule 11.1**：把函数指针转成 `void (*)(const void*, const void*)` 类型；
3. **类型擦除**：`void *` 参数失去类型信息，MISRA Rule 11.5 警告；
4. **最坏 O(N²)**：对已排序表上退化（很多实现选 pivot 不当）；
5. **非线程安全**：标准库实现可能用静态变量。

**替代方案**：

- 编译期排序：写源码时手动升序填好，加 `_Static_assert` 检查（编译期遍历检查相邻元素）；
- 用 `insertion sort` 替代：N < 16 时 insert sort 比 qsort 快，且栈深 O(1)；
- 完全避免运行时排序：所有"排序"需求退化为优先级队列。

## 代码示例

DID 有序表 + 二分查找的完整 CDD 实战代码：

```c
/* 05-排序与查找示例：DID 有序表二分查找 */
#include "Std_Types.h"

#define DID_NOT_FOUND   ((sint16)-1)

/* DID 访问权限 */
#define DID_ACCESS_READ      (0x01u)
#define DID_ACCESS_WRITE     (0x02u)
#define DID_ACCESS_READWRITE (DID_ACCESS_READ | DID_ACCESS_WRITE)

/* 读写回调原型 */
typedef uint8 (*DidReadCb)(uint8 *outData, uint8 *outLen);
typedef uint8 (*DidWriteCb)(const uint8 *inData, uint8 inLen);

/* DID 表项：每条对应一个诊断数据标识符 */
typedef struct {
    uint16      did;        /* DID 号，如 0xF190 */
    uint8        access;     /* 读/写权限 */
    uint8        dlcMax;     /* 最大数据长度 */
    DidReadCb    readCb;     /* 读回调，返回 NRC，0 表示正响应 */
    DidWriteCb   writeCb;    /* 写回调，可为 NULL */
} DidEntry;

/* DID 表：必须按 did 升序排列，否则二分结果错误。
 * 源码写时手动按 did 升序填好，编译期 _Static_assert 会校验。 */
static const DidEntry g_DidTable[] = {
    { 0xF184u, DID_ACCESS_READ,        32u, ReadBootSoftwareId,  NULL                },
    { 0xF190u, DID_ACCESS_READWRITE,   17u, ReadVin,             WriteVin            },
    { 0xF195u, DID_ACCESS_READ,        16u, ReadSystemSupplier,  NULL                },
    { 0xF197u, DID_ACCESS_READ,         4u, ReadEcuSerialNumber, NULL                },
    { 0xF1A0u, DID_ACCESS_READ,         4u, ReadEcuManufactureDate, NULL             },
    { 0xFD00u, DID_ACCESS_READWRITE,    8u, ReadAppSwVersion,    WriteAppSwVersion   },
};

#define DID_TABLE_SIZE   (sizeof(g_DidTable) / sizeof(g_DidTable[0]))

/* 编译期检查：DID 表必须升序。
 * 用 _Static_assert 配合一个常量表达式函数遍历相邻项。
 * 简化版只检查相邻两项；完整版用宏递归检查全部。 */
#define ASSERT_DID_ASCENDING(idx) \
    _Static_assert(g_DidTable[(idx)].did < g_DidTable[(idx) + 1u].did, \
                   "DID table must be ascending at index " #idx)

/* 表 N 项时检查相邻对共 N-1 对：本表 6 项，检查 5 对 (0,1)...(4,5) */
ASSERT_DID_ASCENDING(0u);
ASSERT_DID_ASCENDING(1u);
ASSERT_DID_ASCENDING(2u);
ASSERT_DID_ASCENDING(3u);
ASSERT_DID_ASCENDING(4u);   /* 注意：最后一项 idx 为 N-1，加 1 即 N 越界，所以最末只到 N-2 */

/*
 * 二分查找：返回匹配项索引，未找到返回 DID_NOT_FOUND。
 * 不变量：若 target 存在，必在 [low, high) 内。
 */
sint16 DidTable_Lookup(uint16 targetDid)
{
    uint16 low  = 0u;
    uint16 high = DID_TABLE_SIZE;

    while (low < high) {
        uint16 mid = (uint16)(low + ((high - low) / 2u));   /* 防溢出 */
        if (g_DidTable[mid].did == targetDid) {
            return (sint16)mid;
        } else if (g_DidTable[mid].did < targetDid) {
            low = (uint16)(mid + 1u);    /* target 在右半 */
        } else {
            high = mid;                   /* target 在左半含 mid，右开所以 high = mid */
        }
    }
    return DID_NOT_FOUND;
}

/* UDS 0x22 ReadDataByIdentifier 处理入口 */
uint8 Diag_HandleReadDID(uint16 did, uint8 *outData, uint8 *outLen)
{
    sint16 idx = DidTable_Lookup(did);
    if (idx == DID_NOT_FOUND) {
        return 0x31u;   /* NRC requestOutOfRange：DID 不存在 */
    }
    if ((g_DidTable[idx].access & DID_ACCESS_READ) == 0u) {
        return 0x33u;   /* NRC securityAccessDenied：无读权限 */
    }
    if (g_DidTable[idx].readCb == NULL) {
        return 0x31u;   /* 防御性检查 */
    }
    return g_DidTable[idx].readCb(outData, outLen);
}

/* UDS 0x2E WriteDataByIdentifier 处理入口 */
uint8 Diag_HandleWriteDID(uint16 did, const uint8 *inData, uint8 inLen)
{
    sint16 idx = DidTable_Lookup(did);
    if (idx == DID_NOT_FOUND) {
        return 0x31u;
    }
    if ((g_DidTable[idx].access & DID_ACCESS_WRITE) == 0u) {
        return 0x33u;   /* 无写权限 */
    }
    if (g_DidTable[idx].writeCb == NULL) {
        return 0x72u;   /* NRC writeDataNotFound */
    }
    if (inLen > g_DidTable[idx].dlcMax) {
        return 0x13u;   /* NRC incorrectMessageLength */
    }
    return g_DidTable[idx].writeCb(inData, inLen);
}
```

## 易错点与陷阱

1. **表不是升序，二分结果错乱**：手动填表时漏一项往中间插，编译能过但二分永远找不到。务必加 `_Static_assert` 编译期检查相邻项递增。

2. **`mid = (low + high) / 2` 在大数组溢出**：N = 50000、low + high > 65535 时 uint16 溢出。虽然 DID 表通常 < 1000 条，但写法上仍用 `low + (high - low) / 2` 习惯化避免坑。

3. **左闭右开和左闭右闭混用**：`low = 0; high = N - 1;` 配 `high = mid` 的写法会漏掉一个元素。统一用左闭右开 `[low, high)`，`high` 初始为 N，循环 `low < high`。

4. **`low = mid` 死循环**：`low = mid`（不 +1）时如果 `low + 1 == high`，mid = low，下次区间不变，死循环。务必 `low = mid + 1`。

5. **DID 表项未初始化**：`g_DidTable` 是 `static const`，未列出的元素默认全 0。但若数组大小声明 `DidEntry g_DidTable[10]` 但只填 5 项，后面 5 项 did = 0，二分会把目标误判为"在表头"。要么不指定大小让编译器数，要么确保全部填好。

6. **`qsort` 在标准库实现里栈深不可控**：标准 qsort 大多递归，最坏栈深 O(N)，AUTOSAR 任务栈估算不友好。生产代码尽量不用，需要排序时手写 `insertion sort` 或 `heap sort`，或干脆退化到优先级队列。

7. **MISRA Rule 11.1 警告 `qsort` 回调**：`cmp_did` 是函数指针，被传给 `qsort` 时类型擦除。可以加 deviation 声明，但更推荐完全不用 `qsort`。

8. **二分返回值类型选 `int` 还是 `sint16`**：`sint16` 在 N <= 32767 时够用且省内存；N 大时用 `sint32`。NOT_FOUND 用 `(sint16)-1` 需要保证有效索引非负，调用方用 `< 0` 判错。

9. **DID 大小写问题**：0xF190 与 0xf190 在十六进制字面量上是同一个值，但代码评审时不统一容易被误读为不同 DID。团队约定全部大写。

10. **DID 表放在哪段**：`const` 表默认放在 Flash，节省 RAM；但如果代码里意外把 `static` 漏了写成 `DidEntry g_DidTable[]`，会进 RAM 占空间。AUTOSAR 工程通常配 link script 把 const 段映射到 Flash。

## 面试高频题

**Q1：为什么嵌入式里运行时排序很少用？**
A：(1) 静态表为主，编译期排好序即可；(2) 数据量小（N<100），O(N) 线性查找都不慢；(3) 运行时排序栈深不可控、有函数指针、最坏 O(N²)，对功能安全和 MISRA 不友好。95% 的"排序"问题答案是"源码里手动升序填好"。

**Q2：二分查找最常见的三种 bug 是什么？**
A：(1) `mid = (low + high) / 2` 溢出，改 `low + (high - low) / 2`；(2) `high = mid - 1` 与左闭右开区间混用，漏掉 mid 这一项，改 `high = mid`；(3) `low = mid` 不 +1 导致死循环，改 `low = mid + 1`。

**Q3：循环不变量是什么？为什么左闭右开 `[low, high)` 更安全？**
A：不变量是"若 target 存在必在 [low, high) 内"。左闭右开的好处是 `high` 初始可取 N（不需要 N-1），区间为空判断就是 `low == high`，不需要额外思考边界。`high = mid` 不用 `mid - 1` 也避免减成负数。

**Q4：DID 表为什么不用哈希表？**
A：(1) DID 数量小（< 1000），二分 10 次比较以内，O(1) 收益无感；(2) 哈希表要桶数组 + 冲突处理，内存代价大；(3) DID 编译期固定，没有动态增删；(4) 二分实现简单、可静态分析。产业共识是 DID 表用有序表二分。

**Q5：`qsort` 在 MISRA-C 评审里会被卡在哪几条？**
A：(1) Rule 11.1 函数指针转换；(2) Rule 11.5 `void *` 类型擦除；(3) Rule 17.x 标准库函数是否允许使用；(4) 栈深不确定违反 Dir 4.1 必要的运行时属性。生产代码替代方案：编译期排序 + `_Static_assert` 检查，或手写 `insertion sort`。

**Q6：编译期怎么检查 DID 表确实升序了？**
A：用 `_Static_assert` 加宏递归检查相邻项：`_Static_assert(g_DidTable[i].did < g_DidTable[i+1].did, "ascending")`。完整做法用宏展开 N 条断言，或用 X-Macro 生成表 + 检查代码。这样表写错时编译就过不去，把 bug 拦在编译期。
