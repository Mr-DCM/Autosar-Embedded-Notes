# 02 栈与堆

> 一句话定位：栈是编译器管的"自动"内存，堆是运行时管的"自由"内存——前者吃不准会溢出复位，后者用不慎会碎片卡死，ECU 工程两边的坑都不少。
> 等级：L2 ｜ 前置：[01-五大内存区](01-五大内存区.md)

## 原理

### 1. 栈帧结构（Stack Frame）

每次函数调用，编译器在栈上划出一块连续区域称为**栈帧**（stack frame），向下生长（ARM/TriCore 都是栈地址递减）。一个典型栈帧包含：

| 区域 | 内容 | 谁写 |
|---|---|---|
| 参数区 | 超出寄存器传参个数的实参 | 调用者（caller）压入 |
| 返回地址 | 函数返回后跳回的 PC | 调用者（`CALL` 指令自动） |
| 寄存器保存区 | 被 callee 改写、需恢复的寄存器 | callee prologue 保存 |
| 局部变量区 | 函数内 `auto` 变量 | callee prologue 预留 |
| 编译器临时区 | 中间结果、对齐填充 | 编译器 |

函数返回时，callee 的 epilogue 把保存的寄存器弹回、`RET` 取返回地址、调整栈指针回收整块栈帧。**栈帧大小在编译期就确定了**（除了 VLA 变长数组和 alloca），这就是 map 文件里"每个函数的 stack size"能列出来的原因。

TriCore 用硬件上下文（CSA）保存一部分寄存器，调用开销比纯栈小，但局部变量和溢出（spill）仍走栈。Cortex-M4/M7 用纯软件栈，PSP（进程栈）和 MSP（主栈）分开，ISR 默认用 MSP。

### 2. 函数调用开销

一次调用至少付出：①压参数/返回地址；②保存 caller-saved 寄存器；③执行函数体；④恢复寄存器、`RET`。在 ECU 里这套开销通常几十纳秒到几百纳秒，但要注意两类放大：

- **深嵌套**：CAN 接收 → CanIf → PduR → IpduM → Com → RTE → SWC，7 层调用栈每层都占栈帧，叠加起来栈消耗大。
- **ISR 内调用**：中断里再调一个深函数，中断栈（通常是 MSP 或独立中断栈）瞬间吃紧。

### 3. 栈溢出的三大来源

1. **大局部数组**：`void f(void){ uint8 buf[4096]; ... }` 一次吃 4 KB。CAN 信号处理函数里很常见。
2. **深递归**：递归深度无法编译期确定，栈消耗不可预测。MISRA-C 规则 17.2 限制递归，ECU 工程基本禁用。
3. **ISR 嵌套叠加**：高优先级中断打断低优先级中断，每层都占中断栈。TriCore 三级中断优先级、Cortex-M NVIC 16 级抢占，最坏情况下多级嵌套栈消耗叠加。

栈溢出后果：栈指针越过栈底（向下长，越过保留区），踩到 `.bss` 或其他核数据——变量莫名被改、偶发复位、HardFault/Trap，且**难复现**。

### 4. 任务栈估算方法

AUTOSAR OS 的每个 Task/ISR 有独立栈，估错要么溢出、要么浪费 RAM。两种方法结合用：

**调用深度法（静态）**：从任务入口出发，递归找出最深调用链，累加每函数的 stack size（map 文件给）。再加中断嵌套预留（最坏抢占深度 × 最大 ISR 栈）和安全裕量（10%~20%）。工具如 aiT（AbsInt）、StackAnalyzer 能自动算。

**实测水位法（运行时）**：栈区初始化时填一个固定 pattern（如 `0xA5`），运行一段时间后检查栈底还有多少 pattern 没被覆盖，得到"高水位线"。TRACE32、Lauterbach 的 stack analysis、OS 自带的 OsStackMonitoring 都是这个思路。**两种方法必须并用**：静态估算给上限，水位法验证实际使用率。

### 5. 堆碎片化：ECU 的大忌

`malloc/free` 在通用系统里看似无害，在 ECU 里是定时炸弹：

- **外部碎片**：频繁 alloc/free 不同大小，留下大量不连续小孔，总空闲够但单块不够，分配失败。ECU 寿命 10~15 年，长期运行下碎片只会越来越严重，**无法靠重启清掉**（车不能随时重启）。
- **不确定性**：malloc 的最坏耗时不可控（可能要遍历空闲链表+合并），违反实时性。
- **失败处理**：分配失败时 ECU 不能像 PC 那样"提示内存不足"，只能进入 limphome 或复位，用户体验和功能安全双输。
- **安全标准**：ISO 26262 不鼓励动态内存，ASIL-D 评级几乎要求静态分配。

### 6. 静态分配 / 内存池替代

ECU 工程的标配是两类替代：

- **静态分配**：所有缓冲在编译期定长。NvM 的 RAM block、Com 的 I-PDU 缓冲、Dem 事件队列都是固定大小全局数组。简单、可预测、好验证。
- **定长内存池（fixed-size pool）**：把一块大 RAM 切成 N 个等大块，分配/释放是 O(1) 链表操作，**永不碎片**（块大小一致）。适合"同类型对象频繁创建销毁"场景，如 CanTp 的多会话缓冲。

## 代码示例

```c
#include "Std_Types.h"

/* --- 静态分配：CAN 接收缓冲，编译期定长 --- */
#define CAN_RX_BUF_SIZE   64u
static uint8  CanRxBuffer[CAN_RX_BUF_SIZE];   /* 落 .bss，永不动态分配 */
static uint16 CanRxWriteIdx;

void CanRx_Put(uint8 byte)
{
    if (CanRxWriteIdx < CAN_RX_BUF_SIZE)
    {
        CanRxBuffer[CanRxWriteIdx] = byte;
        CanRxWriteIdx++;
    }
    /* else: 缓冲满，丢包或上报 Dem，绝不动态扩容 */
}

/* --- 定长内存池：永不碎片 --- */
typedef struct {
    uint8  data[8];
    uint8  dlc;
    uint8  inUse;
} CanMsg;

#define MSG_POOL_SIZE   16u
static CanMsg MsgPool[MSG_POOL_SIZE];          /* .bss */

CanMsg *MsgPool_Alloc(void)
{
    uint16 i;
    CanMsg *p = NULL_PTR;
    for (i = 0u; i < MSG_POOL_SIZE; i++)
    {
        if (MsgPool[i].inUse == 0u)
        {
            MsgPool[i].inUse = 1u;
            p = &MsgPool[i];
            break;
        }
    }
    return p;                                 /* 满则返回 NULL，调用方处理 */
}

void MsgPool_Free(CanMsg *p)
{
    if (p != NULL_PTR)
    {
        p->inUse = 0u;
    }
}

/* --- 栈水位法：初始化时填 pattern --- */
#define STACK_PATTERN  0xA5u
void Stack_FillPattern(uint8 *stackTop, uint32 size)
{
    uint32 i;
    for (i = 0u; i < size; i++)
    {
        stackTop[i] = STACK_PATTERN;
    }
}

uint32 Stack_HighWaterMark(uint8 *stackTop, uint32 size)
{
    uint32 i;
    for (i = 0u; i < size; i++)
    {
        if (stackTop[i] != STACK_PATTERN)
        {
            break;                            /* 第一次被改写的位置即高水位 */
        }
    }
    return i;                                 /* 剩余未用栈字节 */
}
```

## 易错点与陷阱

1. **局部数组开大**：`uint8 frame[2048];` 在 CAN 信号打包函数里直接吃 2 KB 栈。改用静态缓冲或堆外内存池。
2. **递归写嗨了**：JSON/树解析递归实现，深度不可控。改迭代或限深。
3. **中断栈当任务栈**：Cortex-M 默认 ISR 用 MSP，若任务也用 MSP（没用 PSP），任务栈和中断栈共享一片，嵌套时溢出概率大增。
4. **栈估算漏掉 ISR 嵌套**：只算任务调用链没算最坏抢占深度，运行中高优中断一嵌就溢。
5. **malloc 在初始化里用**：很多人在 `Init` 里 `malloc` 一次不 free，以为"只 alloc 一次不会碎"。但若失败处理不当、或后续模块也 malloc，碎片仍会累积。AUTOSAR 工程应整体禁用 malloc。
6. **水位法只跑短时间**：只跑 10 分钟的水位不能代表整车周期。必须覆盖最坏工况（刷写、诊断、NM 抖动同时发生）。

## 面试高频题

**Q1：栈帧里都装了什么？函数返回时栈指针怎么恢复？**
答：参数、返回地址、保存的寄存器、局部变量、编译器临时量。返回时 epilogue 弹回寄存器、`RET` 取返回地址，栈指针靠 epilogue 里的"加法"恢复（栈帧大小编译期已知）。

**Q2：栈为什么向下生长？**
答：历史约定：栈和堆分别从 RAM 两端相向生长，最大化两者可用空间。向下生长让"栈顶 = 高地址"，push 时地址递减，与硬件栈指针寄存器行为一致。不是硬性规定，但主流架构都这么设计。

**Q3：任务栈怎么估？只算调用深度够吗？**
答：不够。调用深度法给静态上限，还要加最坏中断嵌套预留和安全裕量，并用运行时水位法验证实际使用率。两者并用才靠谱。

**Q4：为什么 ECU 几乎不用 `malloc`？**
答：①碎片化不可逆，长期运行累积；②最坏耗时不确定，违反实时性；③失败处理复杂；④ISO 26262/ASIL 不鼓励动态内存。替代是静态分配 + 定长内存池。

**Q5：定长内存池为什么不会碎片？**
答：所有块大小相同，free 后归还到空闲链表，下次 alloc 取任一块都一样大，不存在"小块插不进大请求"的外部碎片。

**Q6：Cortex-M 的 MSP 和 PSP 有什么区别？什么时候用哪个？**
答：MSP 是主栈，复位后默认用，ISR 强制用 MSP。PSP 是进程栈，任务切换后可切到 PSP。把任务栈和中断栈分开（任务用 PSP、ISR 用 MSP）能隔离栈溢出影响范围。
