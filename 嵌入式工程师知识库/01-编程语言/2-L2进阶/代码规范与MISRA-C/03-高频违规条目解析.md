# 03 高频违规条目解析

> 一句话定位：项目告警榜的常客就这十几条——整数提升（integer promotion）、指针转换、多出口、库依赖——每条按"本意 → 违规 → 改法 → 是否常走偏差"拆开，把"会消警"升级为"懂条目"。
> 等级：L2 ｜ 前置：[02-MISRA-C规则分类导读](02-MISRA-C规则分类导读.md)

## 原理

静态分析报告里 80% 的告警集中在四类根因：

1. **隐式转换**：C 的整数提升和寻常算术转换（usual arithmetic conversions）静默改变值的类别与宽度——10.x 区专门设"基本类型模型（essential type model）"拦截。
2. **指针双关**：`void*`、整数↔指针、跨类型 cast——11.x 区一网打尽，但嵌入式寄存器访问又是刚需，成为偏差重灾区。
3. **控制流形状**：花括号、else 收尾、单出口——15.x 区管"代码的骨架"。
4. **库与资源依赖**：malloc、stdio、保留标识符——21.x 区把不可控的外部行为挡在门外。

本篇条目速览（级别均经 MISRA-C:2012 核对）：

| 条目 | 级别 | 一句话 | 常走偏差？ |
|---|---|---|---|
| Rule 2.1 / 2.2 | Required | 不可达代码 / 死代码 | 防御性代码常见项目偏差 |
| Rule 8.7（+8.4/8.6/8.8） | Required/Advisory | 外部链接最小化一族 | 生成代码常见项目偏差 |
| Rule 8.9 | Advisory | 单函数用的对象搬进块作用域 | 少 |
| Rule 10.1 | Required | 操作数类别要恰当 | 少 |
| Rule 10.3 | Required | 禁窄化/跨类别赋值 | 偶尔（批量算术） |
| Rule 10.4（+7.2） | Required | 双操作数类别一致 | 少 |
| Rule 11.3 | Required | 禁跨对象类型指针转换 | 协议解析处常见 |
| Rule 11.4 | Advisory | 指针↔整数 | **寄存器访问必走偏差** |
| Rule 11.5（+11.6） | Advisory/Required | `void*` 收窄 | 标准 API 调用点常见 |

## 代码示例

### 1. Rule 2.1 / 2.2：不可达代码与死代码（Required）

**本意**：不可达代码掩盖逻辑错误（return 后的语句说明作者对流程理解有误），且覆盖测试永远到不了，形成 MC/DC 盲区；死代码（赋值后未读、恒假分支）是维护噪声。连带 Dir 4.4（Advisory）：不要用注释"保留"废代码，删掉，版本管理器记得住。

```c
/* 违规 */
Std_ReturnType Demo(uint8 val)
{
    if (val > 100u)
    {
        return E_NOT_OK;
        val = 0u;               /* Rule 2.1：return 之后的不可达代码 */
    }
    if (0u == 1u)               /* Rule 14.3：恒定条件 */
    {
        val++;                  /* Rule 2.2：死代码 */
    }
    return E_OK;
}
```

```c
/* 合规 */
Std_ReturnType Demo(uint8 val)
{
    Std_ReturnType ret;
    if (val > 100u)
    {
        ret = E_NOT_OK;
    }
    else
    {
        ret = E_OK;
    }
    return ret;
}
```

**常走偏差？** 防御性 `default` 分支里的"理论不可达"错误处理常走项目偏差——注意 `default` 里调用 `Det_ReportError` 是有副作用的有效代码，多数工具不判为不可达，优先这么写。

### 2. Rule 8.7 + 8.4/8.6/8.8：作用域与外部链接一族

**本意**：外部链接是全工程共享的稀缺资源——能 `static` 就 `static`，缩小攻击面与耦合。8.7（Advisory）：只被一个翻译单元引用的函数/对象不应外部链接；8.4（Required）：定义外部符号时须有兼容声明（头文件）可见；8.6（Required）：外部符号唯一定义；8.8（Required）：内部链接一律显式 `static`。

```c
/* 违规：utils.c 里只被本文件使用的 CRC 却暴露成全局符号，且没有头文件声明 */
uint16 Utils_CalcCrc16(const uint8 *data, uint32 len)   /* Rule 8.7 + 8.4 */
{
    /* ... */
    return 0u;
}
```

```c
/* 合规：加 static；确需跨文件时在 utils.h 里声明，定义处包含自身头 */
static uint16 Utils_CalcCrc16(const uint8 *data, uint32 len)
{
    /* ... */
    return 0u;
}
```

**常走偏差？** 手写代码少；AUTOSAR 生成代码里大量"单 TU 引用但规范要求外部链接"的 API，通常对生成代码目录整层走项目偏差。

### 3. Rule 8.9：块作用域最小化（Advisory）

**本意**：只在单个函数里出现的对象不应放文件级 `static`——作用域越窄，误用与并发误共享的概率越低。

```c
/* 违规：文件级 static，却只有 MainFunction 用它 */
static uint8 LedCtrl_Tick = 0u;
void LedCtrl_MainFunction(void) { LedCtrl_Tick++; /* ... */ }

/* 合规：搬进函数，static 生命周期语义不变 */
void LedCtrl_MainFunction(void)
{
    static uint8 tick = 0u;    /* 函数内 static：跨调用保持，仅本函数可见 */
    tick++;
}
```

**常走偏差？** 少，直接改。

### 4. Rule 10.1：操作数类别要恰当（Required）

**本意**：本质布尔型（essentially Boolean）不做算术、本质字符型（essentially character）不做算术——布尔只有 0/1，参与加减是逻辑错误；`char` 参与算术还叠加符号实现定义问题。

```c
/* 违规 */
boolean ready = TRUE;
uint8 cnt = (uint8)(ready + 1u);      /* 布尔参与算术（10.1） */

/* 合规：先显式转到无符号类别再运算 */
uint8 cnt = (uint8)((uint8)(ready ? 1u : 0u) + 1u);
```

**常走偏差？** 少。

### 5. Rule 10.3：禁窄化/跨类别赋值（Required）

**本意**：赋值两侧的本质类型类别（有符号/无符号/布尔/字符/浮点）或宽度不一致时，值的解释静默改变。最经典的触发：`uint8` 参与运算被整数提升为 `int`（有符号类别），再赋回无符号变量就是跨类别。

```c
/* 违规：a + b 整数提升为 int 类别，赋给 uint16 跨类别 */
uint8 a = 100u;
uint8 b = 100u;
uint16 sum = a + b;

/* 合规：显式 cast 收敛到目标类型 */
uint16 sum = (uint16)(a + b);
```

**常走偏差？** 大量算术密集代码偶尔对成批表达式走偏差；正常做法是逐处 cast（工具可自动插入）。

### 6. Rule 10.4 + 7.2：双操作数类别一致（Required）

**本意**：位运算、比较两侧须同类别，否则掩码位宽不齐、比较结果反直觉。最常见触发：十六进制字面量默认是 `int`（有符号），与无符号变量按位与。

```c
/* 违规：0x01 是有符号 int，与 uint8 类别不一致 */
uint8 reg = Dev_ReadReg();
if ((reg & 0x01) != 0u) { }

/* 合规：u 后缀让常量进入无符号类别（Rule 7.2） */
if ((reg & 0x01u) != 0u) { }
```

**常走偏差？** 少，加 `u` 后缀即可，团队可在提交钩子里自动查。

### 7. Rule 11.3：禁跨对象类型指针转换（Required）

**本意**：`uint8*` 转成 `FrameType*` 之类"类型双关（type punning）"破坏对齐与别名假设，未定义行为高发区。

```c
/* 违规：把原始缓冲当结构体用 */
typedef struct { uint8 cmd; uint8 len; } FrameType;
static uint8 RxBuf[8];
const FrameType *frame = (const FrameType *)RxBuf;   /* Rule 11.3 */
```

```c
/* 合规：memcpy 搬运（标准豁免场景）或逐字段位操作解析 */
FrameType frame;
(void)memcpy(&frame, RxBuf, sizeof(FrameType));
```

**常走偏差？** 协议栈（Com/PduR 的缓冲区视图）常对少数几处集中偏差。

### 8. Rule 11.4：指针↔整数（Advisory）

**本意**：整数与指针互转不可移植（宽度、表示都依赖平台），还掩盖拼写错的地址。但**内存映射寄存器访问没有合规替代**。

```c
/* 违规（工程刚需） */
#define DEV_STATUS_REG_ADDR  (0xF0180200u)
volatile uint32 *const Dev_RegPtr = (volatile uint32 *)DEV_STATUS_REG_ADDR;
```

**处置**：无法"改掉"，走**偏差许可（Deviation Permit）**并收敛到 MCAL 单点文件（配合厂商寄存器头文件）；这是汽车项目最高频的正式偏差。

### 9. Rule 11.5 / 11.6：`void*` 收窄（Advisory / Required）

**本意**：`void*` 万能转换绕过全部类型检查；11.6 更进一步禁止 `void*` 与算术类型互转。11.3 不拦 `void*`（语言允许），但 `void*` → 具体类型触发 11.5。

```c
/* 违规：通用池返回 void*，调用点必然收窄 */
void *buf = Pool_Alloc(&pool, sizeof(PwmCfgType));
PwmCfgType *cfg = (PwmCfgType *)buf;          /* Rule 11.5 */
```

**改法**：接口类型化（见 [04 案例②](04-合规改写案例.md)）。若面对的是 NvM 这类标准 API（RAM 块就是 `void*`），在调用点集中转换并走偏差/评审确认。

### 10. Rule 14.4：条件表达式须为本质布尔（Required）

**本意**：`if (x)` 里 x 是整数或指针时，"非零即真"的隐式转换把取值范围压成一个 bit，掩盖"忘了比较"类笔误。

```c
/* 违规 */
uint8 ready = 1u;
const PwmCfgType *cfgPtr = NULL_PTR;
if (ready) { }            /* 整数当条件 */
if (cfgPtr) { }           /* 指针当条件 */

/* 合规 */
if (ready != 0u) { }
if (cfgPtr != NULL_PTR) { }
```

**常走偏差？** 少；老代码批量迁移时偶尔项目偏差。

### 11. Rule 15.5 / 15.6 / 15.7：控制流骨架

**本意**：15.6（Required）要求 `if/else/for/while` 体必须花括号——防"苹果 goto fail"式追加语句悬挂；15.7（Required）要求 else-if 链以 else 收尾——让"漏掉的条件"有落点；15.5（Advisory）建议单出口——便于资源清理与路径追踪。

```c
/* 违规 */
if (a > b)
    x = 1u;               /* Rule 15.6：无花括号 */
else if (a == b)
    { x = 2u; }           /* Rule 15.7：链尾无 else */

/* 合规 */
if (a > b)
{
    x = 1u;
}
else if (a == b)
{
    x = 2u;
}
else
{
    x = 0u;               /* 显式兜底 */
}
```

**常走偏差？** 15.5 是全库争议最大条目：守卫子句（guard clause）提前 return 风格的团队大多整层项目偏差；15.6/15.7 基本没人偏差。单出口重构手法见 [04 案例④](04-合规改写案例.md)。

### 12. Rule 17.7 + Dir 4.7：返回值必须使用（Required）

**本意**：忽略返回值 = 忽略错误通道。17.7 要求非 void 返回值必须被使用；Dir 4.7 进一步：**返回错误信息的函数，其错误信息必须被检查**。

```c
/* 违规：静默丢弃 */
NvM_ReadBlock(NVM_BLOCK_LED, &Led_Cfg);

/* 合规一：真的不在乎——显式 (void) 声明意图 */
(void)NvM_ReadBlock(NVM_BLOCK_LED, &Led_Cfg);

/* 合规二（更符合 Dir 4.7 本意）：检查错误 */
Std_ReturnType ret = NvM_ReadBlock(NVM_BLOCK_LED, &Led_Cfg);
if (ret != E_OK)
{
    (void)Det_ReportError(NVM_SID, 0x02u);
}
```

**常走偏差？** 不需要，`(void)` 即合规写法。

### 13. Rule 18.1 + 18.4：指针算术边界（Required / Advisory）

**本意**：指针加减的结果必须仍落在同一数组（或末元素之后一格）内；18.4 建议直接用下标，可读性即安全性。工具报的多是"可能越界"（Undecidable），需要代码里给出可证明的边界约束。

```c
/* 违规：环形缓冲索引 +1 后未回卷 */
static uint8 Buf[8];
static uint8 Idx = 0u;
Idx = (uint8)(Idx + 1u);          /* Idx 到 8 即越界（Rule 18.1） */
Buf[Idx] = 0u;

/* 合规：显式回卷，边界可证明 */
Idx++;
if (Idx >= 8u)
{
    Idx = 0u;
}
Buf[Idx] = 0u;                    /* 18.4：用下标而非 *(Buf + Idx) */
```

**常走偏差？** 环形缓冲、滑动窗口处常见；优先补回卷/饱和逻辑让工具可判定，实在证明不了再偏差。

### 14. Rule 21.3 / 21.6 / 21.1 + Dir 4.12：标准库约束（Required）

**本意**：21.3 + Dir 4.12 禁 `malloc/calloc/realloc/free`——碎片、时序不确定、失败路径难覆盖；21.6 禁 `stdio.h` 的输入输出——栈与重入不可控；21.1/21.2 禁占用保留标识符（下划线开头等）——与实现/库冲突。

```c
/* 违规 */
NodeType *n = (NodeType *)malloc(sizeof(NodeType));  /* 21.3 + Dir 4.12 */
(void)printf("debug %d\n", value);                    /* 21.6 */
#define _MY_DEBUG 1u                                  /* 21.1：下划线开头保留 */

/* 合规：静态池替代 malloc（04 案例③）；日志走封装宏，量产裁剪 */
#define LEDCTRL_DBG(...)   ((void)0u)                 /* 量产：空实现 */
```

**常走偏差？** 量产件不偏差；开发期 printf 走编译开关的临时偏差，出货前必须清理。

## 易错点与陷阱

1. **10.3 只加 cast 不看语义**：把溢出前的 `uint8` 加法 cast 成 `uint16` 只是"合规地错"——先想清楚运算应在哪个宽度进行。
2. **`(void)` 万能化**：` (void)` 只对 17.7 合规，掩盖 Dir 4.7 的"错误要检查"是评审责任。
3. **为消 11.3 引入 memcpy 后不查长度**：`memcpy` 越界比 cast 更隐蔽，来源长度必须校验（Dir 4.14 外部输入校验）。
4. **11.4 偏差遍地开花**：偏差许可应绑定"单点文件 + 厂商头"，每个 `.c` 都来一处 11.4 的项目，审计必然挂。
5. **15.5 单出口改成深嵌套金字塔**：超过三层的 if 嵌套可读性反而更差——优先用"提前计算条件变量 + else-if 扁平化"，别硬凹。
6. **18.1 的"可能越界"直接压制**：先补边界逻辑（回卷、饱和、断言），工具证明不了再偏差，否则真越界也被噪声淹没。
7. **把 2.2 死代码当"未来功能"注释保留**：违反 Dir 4.4，删掉交给 git。

## 工具视角

- **10.x 批量治理**：Polyspace/QAC 都支持"自动插 cast"修复建议，先跑一遍分类统计，同一根因（如全局缺 `u` 后缀）一次性批量修复。
- **11.4 偏差可视化**：按文件统计 11.4 触点数，超过阈值的模块说明寄存器访问没有收敛到抽象层，先重构再谈偏差。
- **15.5 策略化**：与其逐条偏差，不如在工具里对整个工程把 15.5 降级为信息级并在 GCS 里登记一条项目偏差，台账干净。
- **回归防线**：修复后重跑全量基线对比，确认没有"按下葫芦浮起瓢"（典型：改 10.3 引入新的 10.4）。

## 面试高频题

**Q1：`uint16 sum = a + b;`（a/b 为 uint8）违反哪条规则？根因是什么？怎么改？**
答：违反 Rule 10.3（禁窄化/跨类别赋值）。根因是整数提升：uint8 参与运算被提升为 int（有符号类别），赋回无符号变量即跨类别。改法：显式 cast 收敛——`uint16 sum = (uint16)(a + b);`。注意 cast 前先想清运算该在哪个宽度做，"合规地错"比违规更隐蔽。

**Q2：Rule 11.4（指针↔整数）为什么是汽车项目最高频的正式偏差？怎么管好它？**
答：因为内存映射寄存器访问（整数地址转指针）没有合规替代实现，是嵌入式刚需。管理方式：走 Deviation Permit，把偏差收敛到 MCAL 层单点文件（配合厂商寄存器头文件），按文件统计触点数做可视化——每个 .c 都冒出一处 11.4 的项目说明寄存器访问没收敛到抽象层，审计必挂。

**Q3：把接收缓冲直接 `(FrameType *)RxBuf` 强转当结构体用，违反什么？正确写法？**
答：违反 Rule 11.3（禁跨对象类型指针转换）——类型双关破坏对齐与别名假设，是未定义行为高发区。正确写法：用 memcpy 把缓冲搬进结构体变量（标准豁免场景）或逐字段移位解析；协议栈确需缓冲区视图的少数几处集中走偏差。memcpy 时来源长度必须校验（Dir 4.14）。

**Q4：Rule 15.5 单出口（Advisory）项目上一般怎么处理？**
答：与其逐条偏差，常见做法是在工具里对整个工程把 15.5 降为信息级，并在 Guideline Compliance Summary 里登记一条项目偏差，台账干净。硬凹单出口的代价是深嵌套金字塔——超过三层 if 嵌套可读性反而更差，优先"提前计算条件变量 + else-if 扁平化"。
