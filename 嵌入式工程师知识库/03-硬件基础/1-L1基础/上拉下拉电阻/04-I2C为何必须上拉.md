# I2C 为何必须上拉

> 一句话定位：I2C 的 SDA/SCL 都是开漏 + 上拉 → 线与总线——START/STOP 时序、多主仲裁、时钟拉伸，以及"上拉丢失后上升沿圆缓"的故障特征，全部由这个电气结构推导出来。
> 等级：L1 ｜ 前置：[原理与作用](01-原理与作用.md)、[OC-OD门与线与](03-OC-OD门与线与.md)

## 原理

### 电气本质：OD + 上拉 = 线与

I2C（Inter-Integrated Circuit）总线的 SDA/SCL 都是开漏（OD）输出 + 一只上拉电阻：

```
  主MCU SDA(OD)──┐   传感器A SDA(OD)──┐   传感器B SDA(OD)──┐
                 ├───┴────────────────┴──────────●────────
                                          │
                                     [Rpu 2.2k~4.7k]
                                          │
                                        +3V3
```

由此得到两个逻辑电平的定义：

- **显性（dominant）= 0**：任一器件把线拉低（强驱动，下降沿陡）；
- **隐性（recessive）= 1**：所有器件都释放（高阻），上拉电阻把线充高（弱驱动，指数上升沿）。

线上值 = 所有输出位的 AND（线与）。**协议把 0 定义成显性**，是 I2C 一切机制的基石（结构细节见 [OC-OD门与线与](03-OC-OD门与线与.md)）。

### START / STOP：协议怎么利用"谁都能拉低"

正常数据位要求：**SCL 低电平期间允许 SDA 变化，SCL 高电平期间 SDA 必须稳定**——违反即成为起止条件：

```wavedrom
{signal: [
  {name: 'SCL', wave: '1.0.ppppppppp.1..'},
  {name: 'SDA', wave: '1.3..4....5.6.x.', data: ['START', '数据位D7..D0', 'ACK(0)', 'STOP']}
], head: {text: 'I2C START/STOP 与数据位：SCL 高时 SDA 下跳=START、上跳=STOP', tick: 0}}
```

- **START（起始条件）**：SCL 为高时，SDA 由高 → 低；
- **STOP（停止条件）**：SCL 为高时，SDA 由低 → 高；
- 软件视角：MCAL/I2c 驱动下发的 START/STOP 命令（如 Lpi2c 命令字的 START/STOP 位）最终就是控制 SDA 在 SCL 高电平窗口内的这两次特殊翻转。

### 多主仲裁（arbitration）：显性 0 赢

两个主机同时起步：A 发地址 `0101000`（0x28），B 发 `0101010`（0x2A）。各自逐位发送并**同时回读**总线：

```wavedrom
{signal: [
  {name: '主机A输出', wave: 'x.0.1.0.1.0.0.0.x.'},
  {name: '主机B输出', wave: 'x.0.1.0.1.0.1.0.x.'},
  {name: '总线SDA',   wave: 'x.0.1.0.1.0.0.0.x.'}
], head: {text: '多主仲裁：0x28 vs 0x2A，第 6 位 B 输出 1 却读回 0 → B 退出', tick: 0}}
```

算例走位：前 5 位 `0 1 0 1 0` 两者相同、总线一致；第 6 位 A 发 0（显性）、B 发 1，总线被 A 拉低 → B 回读到 0 ≠ 自己发的 1 → **B 立刻退出**（转为从机监听，稍后重试），A 继续且**数据零损坏**——它发的每一位都被总线忠实呈现。这就是无损仲裁：硬件上靠线与天然实现，软件零参与。

### 时钟拉伸（clock stretching）

从机忙（如 EEPROM 页写进行中、数据未就绪）时，**主动把 SCL 拉低**不放：

- 主机释放 SCL（输出 1）后必须**回读 SCL 真实电平**，见 0 就等——因为 SCL 也是线与，从机拉低对主机完全可见；
- 软件体现：I2c 驱动里的 SCL 等待/超时参数；某次访问耗时变长不是 bug，是从机在"掐表"；
- 硬件状态机（如 Lpi2c）会自动等待，但驱动的**超时兜底**必须有，否则从机卡死 SCL → 总线整体挂死。

### 上拉缺失 / 过大：波形特征与示波器诊断

| 故障 | 波形特征 | 通信表现 |
|---|---|---|
| 上拉缺失（忘焊/断线） | SDA 或 SCL 常低/随机，无正常高电平 | 无 ACK、总线卡死 |
| 上拉过大或 Cbus 过大 | **上升沿圆缓**（RC 指数型），下降沿陡；高电平到顶缓慢甚至够不到 VIH | 高频失败、偶发 NACK；降频后好转 |
| 上拉电源域掉电 | 总线电平漂移/半高 | 唤醒后首帧失败 |

示波器操作要点：测 SCL 上升沿 10%~90% 时间 t_r，对照 400kHz 规范 300ns（Fast-mode，以规范为准）；量高电平台阶是否稳定 ≥ VIH；检查 SDA 在 SCL 高电平期间是否稳定（判起止条件误触发）。

## 计算与选型（速览）

- Rmax = t_r / (2.2 × Cbus)：400kHz、50pF → ≤2.7kΩ；
- Rmin = (VDD − VOL) / IOL：3.3V、3mA → ≥1kΩ；
- 常用取值 2.2k~4.7k；多板/长线（Cbus 大）取小阻值，电池设备取大阻值省电。完整四步法见 [02-阻值选择计算](02-阻值选择计算.md)。

## ECU 实例

- ECU 内典型 I2C 器件：传感器（加速度/温度）、EEPROM（标定/配置）、PMIC——各约 10pF 输入电容，挂 4~6 个器件 Cbus 约 40~80pF；
- 上拉电阻放主控侧还是"每个从机模块都放"是原理图评审项：整线等价一只，放多个 = 并联变小，必须合并计算；
- CAN 总线的显性/隐性（差分版）与 I2C 的显性 0/隐性 1 是同一思想在不同物理层上的实现——"谁都能拉显性"是共享总线的安全基石。

## 与软件的关联

- **I2c MCAL / Lpi2c 配置**：波特率寄存器的计算隐含了对 t_r 的假设；上升沿太缓时硬件满足不了建立/保持时间 → 仲裁丢失中断/超时——**先查硬件再查软件**；
- **内部上拉能力边界**：MCU 内部上拉 20~50k，对 50pF 总线 τ = 1~2.5µs、t_r ≈ 2~6µs，连 100kHz（t_r ≤ 1000ns）都可能勉强、400kHz 必失败——**Port 配置里开内部上拉救不了 I2C**，必须外部电阻；
- **CDD/应用层调 I2C 设备前的上拉检查项**：
  1. 原理图确认 Rpu 位置、阻值与上拉电源域；
  2. 挂载器件数 → 估算 Cbus → 复核 Rmax；
  3. 睡眠时上拉电源是否断电（断电则该域器件不可访问）；
  4. 总线上是否有未上电器件（掉电器件可能经内部 ESD 二极管把 SDA 拖低）；
  5. 有条件时示波器确认 t_r 与高电平幅度；
- **超时与总线恢复**：驱动对"SCL 被拉死"要有超时 + 恢复序列（典型做法：补发 9 个 SCL 脉冲直到从机释放 SDA），这是 Lpi2c 驱动/CDD 的常见兜底逻辑。

## 易错点与陷阱

- **"软件开内部上拉就行"**：20~50k 太弱，400kHz 直接失败，别把 Port 上拉当 I2C 上拉；
- **每个从机板都放上拉**：并联后等效阻值减半甚至更小，功耗与灌电流双双超预算；
- **上拉挂在可切换电源域**：域断电时总线"半死"，唤醒首帧丢失还难复现；
- **上升沿缓只降波特率**：治标不治本，根因是 Rpu×Cbus 超标，应减阻值或减电容；
- **单主系统报"仲裁丢失"**：没有第二个主机，往往意味着电平异常（干扰/上拉问题）而非真的多主。

## 面试高频题

1. **问：I2C 为什么用开漏 + 上拉？**
   答：多器件共享两线，开漏 + 上拉构成线与：任一器件可拉低（显性 0）互不冲突，从而支持多主无损仲裁与从机时钟拉伸；推挽会短路冲突。

2. **问：描述 START 和 STOP 条件。**
   答：SCL 高电平期间 SDA 下跳为 START、上跳为 STOP；正常数据位只在 SCL 低电平期间变化。

3. **问：两个主机同时发 0x28 和 0x2A，仲裁结果？**
   答：前 5 位一致；第 6 位发 0 的主机（0x28）为显性，发 1 的主机（0x2A）回读不一致退出；胜者数据零损坏继续，败者稍后重试。

4. **问：I2C 通信失败，示波器看到上升沿缓、下降沿陡，什么问题？**
   答：上升沿由 Rpu×Cbus 充电决定，过缓说明上拉过大或总线电容过大，t_r 超规范导致采样错误；减小上拉阻值或降低总线电容/波特率。

5. **问：什么是时钟拉伸？软件要做什么？**
   答：从机拉低 SCL 通知主机等待；主机须回读 SCL 真实电平（线与特性），驱动层要配置等待上限与超时恢复逻辑。
