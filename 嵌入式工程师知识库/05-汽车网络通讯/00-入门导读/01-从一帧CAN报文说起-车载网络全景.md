# 01-从一帧CAN报文说起-车载网络全景

> 一句话定位：跟着一帧报文从信号打包到对端解包走完全程，顺手把 CAN/LIN/FlexRay/车载以太网四张网的位置摆到一张地图上——之后在本区任何子目录迷路，都能靠这张地图找到回程。
> 等级：L1 ｜ 前置：无

## 一帧报文的一生

你在应用里写了一个变量：`车速 = 88`。半毫秒后，另一颗 ECU 的应用读到了它。中间发生了什么？

```plantuml
@startuml
 autonumber on
 box "发送 ECU" #F8F8F8
 participant "应用 SWC\n(车速信号)" as APP1
 participant "Com" as COM1
 participant "PduR" as PDUR1
 participant "CanIf" as CANIF1
 participant "CanDrv\n(MCAL)" as DRV1
 end box
 participant "CAN 总线\n(双绞线)" as BUS
 box "接收 ECU" #F8F8F8
 participant "CanDrv\n(MCAL)" as DRV2
 participant "CanIf" as CANIF2
 participant "PduR" as PDUR2
 participant "Com" as COM2
 participant "应用 SWC\n(读车速)" as APP2
 end box

 APP1 -> COM1 : 写信号 VehSpd = 88
 note right of COM1 : Com 按通讯矩阵把信号\n装配进 PDU 的数据位
 COM1 -> PDUR1 : 发送 PDU
 note right of PDUR1 : PduR 是"路由表"：\n这个 PDU 走哪条总线、哪个 ID
 PDUR1 -> CANIF1 : 转交 CanIf
 note right of CANIF1 : CanIf 做通用包装：\n选硬件对象(Hth)、管理发送队列
 CANIF1 -> DRV1 : Can_Write()
 note right of DRV1 : MCAL 驱动真正碰\nCAN 控制器寄存器
 DRV1 -> BUS : 帧上总线（含 ID、DLC、数据、CRC）
 BUS -> DRV2 : 收发器拾取电平 → 控制器收帧
 DRV2 -> CANIF2 : 接收中断 + CanIf 归一化
 CANIF2 -> PDUR2 : 按接收 PDU ID 上交
 PDUR2 -> COM2 : 路由到 Com 的接收 PDU
 COM2 -> APP2 : 信号通知（或应用轮询读取）
@enduml
```

五个直觉要点：

1. **Com 管打包/解包，PduR 管选路，CanIf 管包装，CanDrv 管寄存器**——四层职责一句话各归其位；
2. **发送是推（应用触发），接收是中断拉**——帧什么时候到不归你管，所以接收路径靠中断唤醒整条链；
3. **通讯矩阵（DBC/ARXML）是全车的"时刻表"**：哪个信号坐哪班车（哪个 ID）、坐哪个座位（起始位/长度），都在数据库里定义——这就是本区"通讯数据库"子目录存在的原因；
4. **本区只覆盖下两层的原理与排障**：CanDrv 的接口契约在 04 区，Com/PduR/CanIf 的栈内细节在 07 区，诊断（更上层用 CanTp 传大数据）在 06 区；
5. 上面每一条箭头出问题都是一种现场故障：信号没打包、路由配错、Hth 选错、总线 busoff——排障就是沿这条链逐段定位。

## 四张网一张对比表

整车不止一种总线，各有各的定位：

| 总线 | 典型速率 | 成本 | 拓扑 | 典型用途 |
|---|---|---|---|---|
| CAN | ≤1 Mbps | 低（双绞线+两端 120Ω） | 总线型 | 车身控制、动力主流网 |
| CAN-FD | 数据段 ≤5~8 Mbps | 低（同 CAN，收发器需支持 FD） | 总线型 | 数据量增长后的 CAN 升级 |
| LIN | ≤19.2 kbps | 极低（单线） | 主从单线 | 车窗、雨刮、座椅等低速执行器 |
| FlexRay | 2×10 Mbps | 高（双通道） | 总线/星型 | 底盘高实时冗余（X-by-wire） |
| 车载以太网 | 100M/1000M | 中高 | 点对点+交换机 | 智驾大数据、诊断刷写（DoIP） |

选择直觉：**要便宜可靠选 CAN/LIN，要带宽选以太网，要硬实时冗余才上 FlexRay**（新平台多用以太网+TSN 替代 FlexRay，后者以了解级对待）。

再给一个整车视角的想象：一辆车里这些网不是孤岛——动力/底盘域跑 CAN（FD）甚至 FlexRay，车身域 CAN+LIN 混布，智驾与座舱之间用以太网骨干，**网关（Gateway）负责跨网转发**；所以排查"信号没到"时还要多问一句：这帧过了几个网关。

## 本区地图

| 带 | 子目录 | 一句话 |
|---|---|---|
| 1-L1基础 | CAN/ | 协议原理与收发器是地基；总线错误与恢复篇级标【L2】 |
| 1-L1基础 | LIN/ | 协议原理起坡；LDF 与配置、排障篇级标【L2】 |
| 1-L1基础 | 通讯数据库/ | DBC、LDF、通讯矩阵 ARXML——全车时刻表 |
| 2-L2进阶 | 网络管理/ | AUTOSAR NM 状态机、睡眠与假醒 |
| 2-L2进阶 | 传输层/ | CanTp 分段（15765-2）、LinTp |
| 3-L3高级 | FlexRay/ | 仅 1 篇概览，点到即止 |
| 3-L3高级 | 车载以太网/ | 100BASE-T1、SOME/IP、DoIP |

CAN 与 LIN 整目录归入 L1 带是"归带从主"：它们的协议原理是主业地基必须早读；个别深水篇（如总线错误与恢复、LDF 配置）在篇级标【L2】，读到再爬坡。

## 三级成长对照：会配置 → 懂原理 → 能排障

| 阶段 | 你能做到 | 对应本区内容 |
|---|---|---|
| 会配置 | 拿着 DBC 在工具里配出 Com/CanIf/CanDrv，报文能收发 | 通讯数据库、CAN/协议原理、LIN/协议原理 |
| 懂原理 | 说得清仲裁为什么 ID 小优先、位时序采样点怎么算、NM 为什么会假醒 | CAN/FD/总线错误、网络管理、传输层 |
| 能排障 | busoff/帧超时/假醒电流，现场沿调用链快速定位 | 各子目录的排障实录篇 |

主业方向（CAN/LIN/诊断）的目标就是站到第三级；本区 L1→L2 的坡道正是照着这三级铺的。

自查口径：读完本篇你应站在"会配置"的门口——知道链上有哪些层、数据库长什么样，缺的只是动手配置的次数。

## 现场故障速查：沿链定位

报文丢了/错了，别瞎猜——故障几乎总落在"链上的某一层"，按层定位：

| 症状 | 先怀疑的层 | 典型根因 |
|---|---|---|
| 对端完全收不到 | 物理层 | 终端电阻/接线/收发器未上电或处于待机 |
| 偶发错误帧、误码 | 物理层/位时序 | 采样点错、波特率偏差、干扰 |
| 时有时无的 busoff | 总线错误与恢复 | 错误计数器涨满（根源多为某节点发送异常） |
| 应用信号不更新 | Com/数据库 | 信号打包位置错、DBC 版本不一致 |
| 大报文（诊断）传不完 | 传输层 | CanTp 流控超时（STmin/BS 配置不匹配） |
| 整车不睡/睡眠电流大 | 网络管理 | 假醒、NM 报文未停、部分网络配置错 |

一条铁律：**先确定"链上哪一段断了"，再进对应子目录**——工具（CANoe/candump）先看总线层有没有这帧，再上查软件栈。这也是本区每个子目录都留"排障实录"篇位的原因。
