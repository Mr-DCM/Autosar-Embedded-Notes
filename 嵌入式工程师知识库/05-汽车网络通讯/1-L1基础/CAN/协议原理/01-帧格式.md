# 01-帧格式

> 一句话定位：把一帧报文拆到"位"——SOF 到 EOF 每个域的位宽、四种帧类型速查、DLC 码表与 CRC/ACK 直觉；配 DBC/ARXML 时那些字段名（IDE、DLC、RTR）全部在这一篇对上物理含义。
> 等级：L1 ｜ 前置：[从一帧CAN报文说起](../../../00-入门导读/01-从一帧CAN报文说起-车载网络全景.md)

## 原理

CAN 是**面向报文（广播）**的串行总线：任何节点发出的帧，总线上所有节点都能收到，靠 ID 表达"内容+优先级"，接收方自行决定取舍。一帧在 TXD 引脚上就是一串显性（0）/隐性（1）位：

```wavedrom
{signal: [
  {name: 'TXD（发送方视角）', wave: '10.3.4.5.6.7.8.92.', data: ['仲裁域 ID11+RTR+IDE+r0','DLC4','DATA 0~64bit','CRC15','CRC界定符(1)','ACK槽(发1,接收方拉0)','ACK界定符(1)','EOF(7个1)']}
], head: {text: '标准数据帧域顺序（前导1=总线空闲，0=SOF）', tick: 0}}
```

三个贯穿全区的直觉：

1. **显性 0 压过隐性 1**（线与）：这是仲裁与 ACK 的物理基础，详见 [03-仲裁与填充](03-仲裁与填充.md)；
2. **帧结构是为"逐位仲裁+全总线校验"设计的**：ID 放最前是让优先级在冲突时立刻分出胜负；CRC/ACK 让接收方当场反馈，发方立刻知道失败并重发；
3. **帧没有"目的地址"**：ID 标识的是报文内容，不是某个节点——这是 CAN 与 UART/SPI 最大的思维差异。

## 详解：帧域逐位表与帧类型速查

### 标准数据帧（CAN 2.0，11 位 ID）

| 域 | 位宽 | 取值/说明 |
|---|---|---|
| SOF | 1 | 显性 0，同时是硬同步边沿 |
| 仲裁域 | 11+1 | ID（高位先发）+ RTR（数据帧=显性 0，远程帧=隐性 1） |
| 控制域 | 1+1+4 | IDE（标准帧=0）+ r0（保留，发 0）+ DLC |
| 数据域 | 0~64 | 0~8 字节，高位字节先发（字节内 MSB 先发） |
| CRC 域 | 15+1 | CRC 序列（生成多项式 x¹⁵+x¹⁴+x¹⁰+x⁸+x⁷+x⁴+x³+1）+ CRC 界定符（隐性 1） |
| ACK 域 | 1+1 | ACK 槽（发方发 1，收到且 CRC 正确的节点拉 0）+ ACK 界定符（1） |
| EOF | 7 | 7 个隐性 1 |
| 帧间隔 | 3 | 3 个隐性 1（IFS/intermission），随后才允许下一帧 |

位宽账：标准帧（不含填充）= 44 + 8n 位，n=8 时 108 位；加上 3 位帧间隔约 111 位——CANoe 里算总线负载时用的就是这个数。

### 扩展数据帧（29 位 ID）

| 域 | 位宽 | 说明 |
|---|---|---|
| SOF + 基本 ID | 1+11 | 与标准帧相同的前 11 位 |
| SRR | 1 | 隐性 1，占在标准帧 RTR 的位置上 |
| IDE | 1 | 隐性 1（扩展帧标志） |
| 扩展 ID | 18 | 低 18 位 ID |
| RTR + r1 + r0 + DLC | 1+1+1+4 | 之后与标准帧相同 |

扩展帧（不含填充）= 64 + 8n 位，n=8 时 128 位。**SRR/IDE 在同 ID 竞争时是隐性**，所以相同数值下标准帧优先于扩展帧。

### 四种帧类型速查

| 帧类型 | 用途 | 结构要点 | 使用现状 |
|---|---|---|---|
| 数据帧 | 携带数据 | 如上表 | 主角 |
| 远程帧 | 请求某 ID 的数据 | RTR=1，无数据域但 DLC=期望长度 | 大多数 OEM 已禁用（节点自发即可，且曾引发总线风暴） |
| 错误帧 | 出错节点广播 | 6 位错误标志 + 错误界定符，详见 [04-错误帧](04-错误帧.md) | 协议自动行为，不由应用发起 |
| 过载帧 | 接收方未准备好 | 结构与错误帧同形（6+8），在帧间隔处插入 | 现代控制器极少主动发 |

### DLC 码表（经典 CAN）

| DLC | 0~8 | 9~15 |
|---|---|---|
| 数据长度 | 0~8 字节，一一对应 | **一律按 8 字节处理**（保留码） |

### CRC 与 ACK 的机制直觉

- **CRC-15 保护的是 SOF 到数据域末尾的位流（含填充位）**，由发方算好放入帧中；接收方重算比对——它只能"检错"，错了就发错误帧，让发方重发，**没有重传计数之外的纠错能力**；
- **ACK 是全总线心跳**：只要有一个节点收到且 CRC 对，ACK 槽就被拉成显性。单节点上电调试时没人应答→发方记 ACK 错误→错误计数飞涨到 busoff，这是台架最常见的"假故障"。

## 配置层/工程关联

| 帧域 | AUTOSAR/工具中的落点 |
|---|---|
| ID / IDE | CanIf 的 CanIfTxPduCanId + CanIfTxPduCanIdType（STANDARD/EXTENDED/MIXED）；DBC 里 Message 的 ID 与 `ID`/`Extended` 属性 |
| DLC | Can PDU 的 length；Com 按 DBC 信号起始位/长度打包后取整字节 |
| RTR | 经典 CAN 一般不配；CanIf 有远程帧支持但多数项目禁用 |
| 数据域 | 信号打包（Intel/Motorola 字节序）在 DBC/Com 中定义，与帧格式无关 |

排障关联：CANoe Trace 里看到的 `DLC=8` 是链路层真值；如果应用层"丢字节"，先看 DBC 信号起始位/长度，再看传输层分段（>8 字节走 CanTp），**不要怀疑帧格式本身**——控制器硬件拼装帧域不会出错，出错的是配置。

## 易错点与陷阱

1. **把 ID 当地址**：现象是"给节点 X 发 0x123 它没回"。原因：0x123 是报文标识，所有节点都收到了，只是 X 的接收过滤/Com 配置没放行。对策：查 CanIf/Com 的接收配置与 DBC 归属。
2. **DLC 写 9~15 想表达 9~15 字节**：经典 CAN 里硬件按 8 字节截断，多出的字节静默丢失。对策：>8 字节上 CanTp（ISO 15765-2）或转 CAN-FD。
3. **扩展 ID 塞进标准帧配置**：29 位 ID 被 11 位掩码截断，总线上出现完全不相干的 ID。对策：CanIfIdType 与 DBC Extended 标志必须一致。
4. **以为 ACK 槽是发方发的**：发方发隐性、接收方拉显性。单节点/对端未上电时必出 ACK 错误，属正常现象而非"帧格式错"。
5. **EOF/帧间隔期间插入新帧**：3 位 intermission 是必需的接收方恢复时间；间隔内出现显性位会触发过载帧。
6. **用 RTR 做"读请求"**：远程帧与数据帧的 ID 空间相同，混用易造成应答与请求互压；多数 OEM 规范直接禁止。

## 面试高频题

**Q1：标准帧和扩展帧的最长位长各是多少？**
答：不含填充：标准 44+8n，n=8 为 108 位；扩展 64+8n，为 128 位；加帧间隔 3 位。含填充最坏再多约两成。

**Q2：CAN 的 ID 是地址吗？**
答：不是。CAN 是广播总线，ID 标识"报文内容+优先级"，所有节点物理上都收到帧，过滤由接收方硬件/软件完成；点对点语义是上层（如诊断寻址）自己实现的。

**Q3：ACK 机制怎么工作？谁拉 ACK？**
答：发送方在 ACK 槽发隐性位；任何收到该帧且 CRC 校验正确的节点把槽拉成显性。发方据此知道"至少有一个节点正确收到"。

**Q4：DLC=15 在经典 CAN 里是什么意思？**
答：保留码，按 8 字节数据长度处理（并非 15 字节）。CAN-FD 中 9~15 才被重新定义为 12~64 字节。
