# S32K 工程模板：把散件组织成可交付的工程

> 一句话定位：给出一个 S32K1xx/S32K3xx 项目的标准目录骨架与配套纪律——S32DS+RTD+EB tresos 的工具分工、生成代码与手写代码的混合编译、Git 分支与 A/B 样件交付节奏，拿到新项目照此搭台第一周就能就位。
> 等级：L2 ｜ 前置：[一个ECU项目的一生-实战全景](../../00-入门导读/01-一个ECU项目的一生-实战全景.md)

## 1. 核心概念：模板的本质是"隔离变化"

练手项目里你已见过：生成区（配置工具吐出）与手写区（你的代码）必须分开。工程模板把这个思想推广到整个仓库：**按"谁生成、谁手写、谁第三方"三分天下**，再叠加"交付节奏"的分支纪律。一个新项目 80% 的结构与上个项目相同——模板就是把这 80% 固化，让你只填那 20% 的业务。

```plantuml
@startuml
skinparam backgroundColor #FEFEFE
skinparam defaultFontSize 13
rectangle "s32k_ecu_proj（Git 仓库根）" as Root
package "01_mcal_cfg（EB tresos 工程）" #E8F0FE {
  [Tresos 工程 .xdm/\n生成输出 output/]
}
package "02_bsw（BSW 静态代码+补丁）" #F5F5F5 {
  [供应商 BSW 源码\n按版本锁定]
}
package "03_app（手写应用）" #E6F4EA {
  [SWC/CDD/任务\n随业务增长]
}
package "04_config（数据资产）" #FFF8E1 {
  [通讯矩阵 ARXML\n诊断 CDD/ODX\n标定 A2L]
}
package "05_tools（脚本）" #F3E5F5 {
  [出包/回归/检查\nPython 脚本]
}
Root --- 01_mcal_cfg
Root --- 02_bsw
Root --- 03_app
Root --- 04_config
Root --- 05_tools
note bottom of Root
  三分天下：生成区(蓝)/第三方(灰)/手写区(绿)，
  各自的"改动手续"不同——生成区改配置不改代码，
  第三方只升级不改行，手写区自由
end note
enduml
```

## 2. 详解：四大件

**第一件：工具链分工。** S32DS 做 IDE 与编译调试（工程操作见 [S32DS](../../../10-工具链与工程化/1-L1基础/IDE/02-S32DS.md)）；芯片侧 RTD 提供基础驱动与启动文件（RTD/SDK 生态对比见 [SDK 与 RTD 生态对比](../../../02-芯片与体系结构/1-L1基础/S32K平台/S32K1与S32K3对比/02-SDK与RTD生态对比.md)）；MCAL/BSW 配置在 EB tresos（流程见 [EB tresos](../../../10-工具链与工程化/2-L2进阶/AUTOSAR配置工具/02-EB-tresos.md)）。铁律：tresos 工程的 `.xdm` 进版本库，`output/` 生成物不入库（可重建）——ARXML/xdm 的版本管理细则见 [ARXML 的版本管理](../../../10-工具链与工程化/1-L1基础/Git与版本管理/03-ARXML的版本管理.md)。

**第二件：混合编译的边界。** 手写代码只 include MCAL/BSW 标准头文件，绝不 include 生成物内部头；跨层引用走 [MemMap](../../../01-编程语言/2-L2进阶/内存管理/05-AUTOSAR-MemMap机制.md) 约定的内存段（core0/core1、calib/nv 各归其段）；开发期开 Det 报开发错误（发布前按需裁剪）。命名规范提前定：`App_`、`Cdd_`、`Cfg_` 前缀分清归属。

**第三件：Git 分支与样件交付节奏。** 分支模型（详见 [分支策略](../../../10-工具链与工程化/1-L1基础/Git与版本管理/02-分支策略.md)）：`develop` 日常集成→交付前两周拉 `release/A1` 只进 bugfix→出包打 tag `A1.0.3`。每次样件交付物清单固定五样：hex/s19、对应 commit+tag、配置基线快照（tresos 导出的配置差异）、Release Note（新功能+已修单号+已知问题）、烧录说明。**"哪个软件包修了哪张单"必须可追溯**——评审时第一个被问的就是这个。

**第四件：出包自动化。** 05_tools 里至少放三个脚本：一键出包（拉 tag→tresos 命令行生成→编译→拷贝产物+清单）、配置 diff（比对两个基线的配置差异，方法见 [配置 diff-review](../../../10-工具链与工程化/2-L2进阶/AUTOSAR配置工具/03-配置diff-review.md)）、编译检查（编译警告数趋势，超阈值报错）。脚本沉淀方法论见 [10 区脚本索引](../../../10-工具链与工程化/2-L2进阶/辅助脚本沉淀/01-脚本索引.md)。

拿到新项目第一周，按模板照做的 checklist（做完打勾，第一周就站稳）：

| # | 动作 | 产出 |
|---|---|---|
| 1 | 从模板复制目录骨架并改项目名 | 仓库 v0.0.1 |
| 2 | 迁入上一项目的 tresos 配置基线并 diff-review | 配置差异清单 |
| 3 | 确认芯片型号/封装，更新链接脚本与内存分区 | 可编译空工程 |
| 4 | 把出包三脚本接上本项目工程名 | 一键出包跑通 |
| 5 | 建 develop/release 分支与 tag 规范 | 首个 tag v0.0.1 |
| 6 | README 写清分核/资源归属/工具版本 | 团队公约 |
| 7 | 第一个"点灯级"冒烟版本烧板验证 | 可运行基线 |

## 3. 易错点与陷阱

- **现象：同事拉同一 tag 编译出的 hex 与你的不一致。原因：** tresos 生成物或编译器版本没锁定，"我机器上能编"式漂移。**对策：** 生成物不入库但生成工具版本写进 README；编译器版本与编译选项随仓库提交（或至少随 Release Note 记录）。
- **现象：A 样件出了一个诡异 bug，回溯发现"当时改了什么"说不清。原因：** 交付前直接在 release 分支之外改代码出包，绕过了 tag。**对策：** 铁律"无 tag 不出包"；任何交付包必须能对应到一个 commit。
- **现象：BSW 升级后工程编译不过/行为变化。原因：** 供应商包整体覆盖，把此前打在旧版上的补丁冲掉了。**对策：** 02_bsw 只按版本目录升级（`bsw_v4.2/`、`bsw_v5.0/` 并存切换），补丁用 patch 文件管理而不是手改源文件。
- **现象：手写代码一加多核，链接报段冲突。原因：** 核间内存分区没按 MemMap 约定，变量都落进了默认段。**对策：** 起步就按 MemMap 分段放代码；多核资源划分参考 [多核 OS](../../../07-AUTOSAR架构/2-L2进阶/系统服务栈/Os/05-多核OS.md)。
- **现象：交付后客户报"配置和我们评审的不一致"。原因：** 出包时 tresos 工程里残留未提交的本地修改，生成物与库内 xdm 不一致。**对策：** 出包脚本第一步强制 `git status --porcelain` 非空即终止；出包后自动导出配置快照附在交付物里。
- **现象：Release Note 越写越薄，交付后没人知道包里有什么。原因：** 没有模板与强约束，靠自觉必然衰减。**对策：** 05_tools 里放 Release Note 模板，出包脚本自动带出 commit log 与问题单清单供人工补充。

## 4. 面试高频题

**Q：为什么生成代码不入版本库？什么时候例外？**

答：生成物可由 xdm/配置完整重建，入库只会制造合并冲突与仓库膨胀；版本管理的对象应是"配置源头"。例外：交付审计场景（如安全项目要求交付物完整快照）会把生成物打进交付包归档，但仍不是日常分支管理对象。

**Q：release 分支与 develop 分支的本质区别？**

答：不是目录不同，是**准入规则不同**：develop 收功能与重构，release 只收 bugfix 且每笔须关联问题单。这保证 release 的变更面最小化——出问题时 diff 范围可控，回归测试量可控。

**Q：一个 A 样软件包，你认为必备的交付物是什么？**

答：固件镜像（hex/s19）、版本可追溯信息（tag/commit/编译时间戳内嵌版本号）、配置基线、Release Note（新增/修复/已知问题/关联单号）、烧录与验证说明。少了追溯信息，后续所有问题定位都会退化为考古。

**Q：S32K 项目里 RTD、MCAL、手写驱动三者怎么共处？**

答：按"层"共处：MCAL（tresos 生成）承担 AUTOSAR 标准外设抽象；RTD 提供启动、时钟、底层工具函数等"非标准外设"支撑；手写 CDD 只写两者都不覆盖的专有硬件。边界判断方法论见 [CDD 定位与边界](../../../04-MCAL与外设驱动/2-L2进阶/CDD设计方法论/01-CDD定位与边界.md)。
