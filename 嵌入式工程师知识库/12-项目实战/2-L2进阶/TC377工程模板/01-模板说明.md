# TC377 工程模板：换平台，哪些变、哪些不变

> 一句话定位：与 S32K 模板同款骨架的 TC377 差异版——AURIX Dev Studio+HighTec+iLLD+EB tresos 的工具组合、TriCore 三核与 BMI 引导头、锁步/CSA/trap 这些平台特有件，以及"工程纪律不随平台变"的可移植清单。
> 等级：L2 ｜ 前置：[一个ECU项目的一生-实战全景](../../00-入门导读/01-一个ECU项目的一生-实战全景.md)

## 1. 核心概念：平台变了，骨架不变，特有件要认

先说不变的：[S32K 模板](../S32K工程模板/01-模板说明.md)那套"三分天下"目录（生成区/第三方/手写区）、Git 分支与样件交付五件套、出包自动化纪律，**原样平移**——工程化纪律是平台无关的资产，这正是模板存在的意义。变的是平台特有件：TriCore 的三核启动、BMI 引导头、CSA 上下文、锁步核、GTM 定时器、trap 体系。TC377 模板的核心工作就是把特有件"安置"进骨架的哪个格子。

判断"一件东西该不该进 04_platform"就用一条标准：**它的配置错误是否会导致"板子不跑/变砖/安全机制失效"级别的后果**——是，就进特有件目录，单独评审；否，归入通用区。

## 2. 详解：TC377 特有件怎么安置

**第一件：工具组合。** AURIX Dev Studio（或 AURIX Studio）做 IDE/调试（见 [AURIX Dev Studio](../../../10-工具链与工程化/1-L1基础/IDE/01-AURIX-Dev-Studio.md)）；HighTec/GCC TriCore 交叉编译器；芯片侧支撑库是 iLLD（分层设计见 [iLLD 分层设计](../../../02-芯片与体系结构/2-L2进阶/TC377平台/资源与iLLD/01-iLLD分层设计.md)，与 MCAL 的关系见 [iLLD 与 MCAL 的关系](../../../02-芯片与体系结构/2-L2进阶/TC377平台/资源与iLLD/02-iLLD与MCAL的关系.md)）；BSW/MCAL 配置仍在 EB tresos——生成纪律与 S32K 完全一致。

**第二件：启动与引导头。** TC377 上电先读 Flash 头部的 BMHD（BMI 引导模式字）决定启动入口，工程模板里 BMHD 生成脚本、链接脚本（.lsl）单独放 04_platform，配置错了是"板子变砖"级事故（原理见 [TC377-BMI 与引导头](../../../02-芯片与体系结构/2-L2进阶/启动流程/01-TC377-BMI与引导头.md)；启动代码逐行导读见 [TC377 启动代码分析](../../../01-编程语言/2-L2进阶/汇编基础/启动代码阅读/01-TC377启动代码分析.md)）。

**第三件：三核分工写进模板 README。** 典型分工：Core0 应用+诊断、Core1 通讯栈、Core2（或锁步核）安全监控。模板预先分好 MemMap 段（core0_/core1_ 前缀目录）、ISR 路由到核（见 [IR 路由与多核分配](../../../02-芯片与体系结构/2-L2进阶/TC377平台/中断系统/02-IR路由与多核分配.md)）、主从核启动顺序（见 [主从核启动](../../../02-芯片与体系结构/3-L3高级/多核架构/01-主从核启动.md) 与 [07 区多核集成](../../../07-AUTOSAR架构/3-L3高级/多核集成/01-主从核启动.md)）。新成员拿到模板先读分工表再动代码。

**第四件：trap 与调试预留。** TC377 的 trap 体系（MPU 违例、栈溢出、调用错误各自有 trap 号）要在模板里预埋 trap 处理钩子：记录 trap 号+返回地址到 NoInit RAM，复位后上报——现场定位的救命稻草（完整方法见 [Trap 定位方法](../../../02-芯片与体系结构/3-L3高级/异常与Trap/02-Trap定位方法.md)）。

双平台差异速查（迁移评估先看这张表）：

| 维度 | S32K | TC377 |
|---|---|---|
| 内核 | Cortex-M 单核/双核 | TriCore 三核+锁步 |
| 启动 | 向量表+复位流程 | BMHD 引导头+启动三步 |
| 上下文 | 软件栈（PSP/MSP） | CSA 链表 |
| 底层库 | RTD | iLLD |
| 异常 | HardFault | trap 分级+TIN |
| 定时器 | eMIOS/FTM | GTM（TOM/ATOM） |
| 配置工具 | EB tresos（同） | EB tresos（同） |
| 交付纪律 | 分支+tag+五件套（同） | 分支+tag+五件套（同） |

## 3. 易错点与陷阱

- **现象：改完代码烧录，板子彻底无反应。原因：** BMHD/链接脚本配置错误，启动入口指向无效地址，程序根本没跑起来。**对策：** 04_platform 目录改动走单独评审；保留已知可启动的 BMHD 备份；先恢复引导头再查应用。
- **现象：单核调试一切正常，三核一起跑就偶发数据错乱。原因：** 跨核共享变量无保护，两核同时读写；或核间中断路由没配，同步机制失效。**对策：** 共享数据走 IOC/自旋锁并按核分 MemMap 段；参考 [核间通讯与共享资源](../../../02-芯片与体系结构/3-L3高级/多核架构/03-核间通讯与共享资源.md)。
- **现象：任务在 S32K 上好好的，TC377 上偶发"跑飞"。原因：** 栈溢出破坏了 CSA 链表——TriCore 函数上下文走 CSA 不是纯软件栈，溢出症状更隐蔽。**对策：** 调大 CSA 区/核对 OS 栈水位；原理见 [CSA 上下文机制](../../../02-芯片与体系结构/3-L3高级/TriCore架构/02-CSA上下文机制.md)。
- **现象：iLLD 与 MCAL 配的同一外设互相干扰。原因：** 两套代码都初始化了同一硬件（比如 GTM 通道），后配置覆盖先配置。**对策：** 资源清单进模板 README：每个外设"归 iLLD 还是归 MCAL"一一登记，禁止双边管。
- **现象：编译过了，一上锁步配置就报错复位。原因：** 锁步核要求两核执行严格一致，使用了非确定性行为（读未初始化内存、依赖时序的代码）。**对策：** 全局变量显式初始化；RAM 初始化由 Mcu 统一完成（见 [RAM 初始化](../../../04-MCAL与外设驱动/2-L2进阶/Mcu模块/02-RAM初始化.md)）。
- **现象：A/B 样交付后客户反馈"某些配置项和台账对不上"。原因：** 与 S32K 同病：tresos 本地未提交修改混进了出包。**对策：** 同款解法——出包脚本强制工作区干净+导出配置快照，纪律平台无关。

## 4. 面试高频题

**Q：从 S32K 迁到 TC377，工程上哪些东西可以直接搬，哪些必须重做？**

答：直接搬：目录骨架、Git/交付纪律、出包脚本、应用层代码（走标准 MCAL/BSW 接口的部分）；必须重做：MCAL 配置（外设模型完全不同）、链接脚本与启动（lsl vs gcc ld、BMHD）、中断路由（三核 SRC 分配）、以及依赖 iLLD/RTD 的底层工具代码。一句话：**越靠标准接口越可移植，越靠硬件越要重做**。

**Q：TC377 三个核你们怎么分工？依据是什么？**

答：典型按"功能域+负载"分：应用与诊断一核、通讯栈一核（收发中断密集）、安全监控/标定一核；依据是负载实测（CPU 占用率）、中断响应时延要求与安全独立性要求（ASIL 相关逻辑与 QM 逻辑分核隔离）。分核本质是资源与风险的隔离设计。

**Q：什么是 BMHD？为什么它配错会"变砖"？**

答：BMI/BMHD 是 TC377 Flash 头部的引导模式描述（入口地址、校验），上电硬件按它跳转。它本身坏了，CPU 第一条指令就取错地址，连 Bootloader 都进不去——所以模板把它当高危配置，改动单独评审+保留可启动备份（仍可通过调试器救援，但产线场景等于事故）。

**Q：TC377 项目的 trap 处理你们怎么做？**

答：预埋全局 trap 钩子：捕获 trap 号/TIN 与上下文（PCXA、返回地址），写入 NoInit RAM 标记区，主动复位；重启后检测标记并上报 DLT/Dem。这把"偶发跑飞"变成"可定位事件"——是模板级基建，不是事后补丁。
