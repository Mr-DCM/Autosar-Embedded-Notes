# SID31-例程控制

> 一句话定位：DID 管"数据"、RID 管"动作"——31 让诊断仪远程触发 ECU 内一段带输入参数、带执行结果的动作（自检/擦 NVM/校验），是产线 EOL 与刷写流程的螺丝刀。
> 等级：L2 ｜ 前置：[SID10-会话控制](SID10-会话控制.md)

## 原理

### RID vs DID：动作与数据的分界

| 维度 | DID（22/2E） | RID（31） |
|---|---|---|
| 本质 | 一块数据（读/写） | 一段可执行动作（启动/查结果） |
| 交互 | 请求-响应即完成 | 启动（01）→ 执行（异步）→ 查询（03）拿结果 |
| 典型 | 版本号、VIN、配置字 | 自检、擦除、校验、风扇控制 |
| 副作用 | 2E 写数据 | 31 可能改变 ECU 运行状态/存储器 |

一句话分界：**"要一个值"用 DID，"要 ECU 干一件事并要结果"用 RID**。边界处也有灰色地带（如标定值写入用 DID、触发重算用 RID），以 OEM 诊断规范为准。

### 三步模型：start / stop / requestResult

```plantuml
@startuml
autonumber on
participant "诊断仪" as TESTER
participant "Dcm" as DCM
participant "例程实现\n(SWC/Bootloader)" as APP

TESTER -> DCM : 31 01 02 03（start：RID 0203 + 输入参数）
DCM -> APP : 启动例程，带参数
APP --> DCM : 已受理
DCM --> TESTER : 71 01 02 03 <routineStatus+初始结果>
note over APP : 异步执行中（长例程）...
TESTER -> DCM : 31 03 02 03（requestResult：查结果）
DCM -> APP : 取执行结果
APP --> DCM : 结果数据（如自检码/校验值）
DCM --> TESTER : 71 03 02 03 <结果>
note right of TESTER : 长例程执行期间\n可轮询 31 03，或按 OEM 用 0x78 等待
TESTER -> DCM : 31 02 02 03（stop：可选中止）
DCM --> TESTER : 71 02 02 03
@enduml
```

三个子功能共用同一报文骨架，`01 start / 02 stop / 03 requestResult`。短例程（毫秒级）start 响应里直接带结果；长例程靠 03 轮询或 0x78 挂起。

### RID 编号惯例：0x02xx 段

车规惯例把 RID 空间与 DID 空间分区编号，`0x0200~0x02FF` 是最常见的例程序号段（OEM 定义），另有 `0xFF00` 段约定俗成给"闪写校验/完整性检查"这类通用例程（`31 01 FF 00` 校验签名/CRC 就是刷写流程的固定角色，见 [SID34-37](SID34-37-刷写下载.md)）。

### 典型例程三件套

| 例程 | 干什么 | 结果怎么用 |
|---|---|---|
| 自检 self-test | EOL 下线检测：跑一遍硬件/回路自检 | 返回逐项 pass/fail 位图 |
| 擦 NVM erase | 刷写前擦除程序 Flash/NVM 块 | 返回擦除状态，失败→0x72 |
| 校验 check | 对刚刷写的镜像算 CRC/验签名 | 返回校验值，Bootloader 比对后放行启动 |

## 详解

### 报文格式逐字节

**请求：** `31 01 02 03 + 输入参数`

| 字节 | 值 | 含义 |
|---|---|---|
| 1 | 0x31 | SID：RoutineControl |
| 2 | 0x01/0x02/0x03 | 子功能：start/stop/requestResult |
| 3~4 | 0x0203 | RID（2 字节） |
| 5~n | 输入参数 | 该 RID 定义（可为空） |

**正响应：** `71 01 02 03 + 例程状态/结果`

| 字节 | 值 | 含义 |
|---|---|---|
| 1 | 0x71 | SID+0x40 |
| 2 | 0x01 | 回显子功能 |
| 3~4 | 0x0203 | 回显 RID |
| 5~n | routineStatusRecord | 该 RID 定义：常含 1 字节结果码 + 结果数据 |

**负响应 `7F 31 NRC`：**

| NRC | 场景 |
|---|---|
| 0x12/0x13 | 子功能不支持/长度错 |
| 0x22 | 例程前置条件不满足（车速≠0、会话/时序不对） |
| 0x24 | 时序错：没 start 就 requestResult |
| 0x31 | RID 不存在、输入参数超范围 |
| 0x33 | 该例程要求先解锁 |
| 0x72 | 执行失败（擦除失败、自检不过） |
| 0x7E/0x7F | 会话不支持（不少例程只在扩展/编程会话开放） |

### 结果码要看正响应里的 routineStatusRecord

NRC 只表达"请求被拒"；**例程执行了但没成功，走的是正响应 + 结果码**（如 `71 01 FF 00 00` 的最后字节表示校验失败）。"收到 71 不等于例程成功"——脚本必须解析结果字段，这是 31 排障与 22/2E 最大的习惯差异。

## 配置层

- Dcm 中每个 RID 一行 **DcmDspRoutine**：会话/安全、start/stop/result 三个回调（`DspRoutineStart` 等）、输入输出长度——接线见 [Dcm配置](../../2-L2进阶/Dcm配置/README.md)；
- 例程本体的实现（自检项表、擦除流程、校验算法）在应用/Bootloader 侧，Dcm 只透传参数与结果——RID 的输入输出结构与 CDD 同步，见 [DID与RID设计](../../2-L2进阶/DID与RID设计/README.md)；
- 刷写相关例程（擦除、校验、一致性检查）与 34-37 的协作时序在 [Bootloader](../../3-L3高级/Bootloader/README.md) 展开。

## 易错点与陷阱

1. **现象：收到 71 却当成功，例程其实失败。原因：结果藏在 routineStatusRecord 的结果码里。对策：脚本按 CDD 解析结果字段，禁止只判首字节 71**；
2. **现象：31 03 报 0x24。原因：例程未 start 或已结束就查结果。对策：严格 01→（等待/轮询）→03 的时序，start 被拒就别发 03**；
3. **现象：长例程 start 后 0x78 一路刷屏。原因：例程同步执行超出 P2。对策：实现改异步（start 立即受理，03 取结果），或诊断仪按 P2\* 容忍 0x78**；
4. **现象：刷写时 31 01 FF 00 校验报 0x72。原因：镜像 CRC 与 ECU 计算不一致（工具算法/初值/范围不同）。对策：两端对齐算法参数（CRC32 初值、覆盖区间含不含向量表）**；
5. **现象：EOL 自检例程在扩展会话报 0x7E。原因：例程只在特定会话（如默认会话或专用 EOL 会话）开放。对策：查 CDD 的例程会话矩阵，EOL 流程按序切会话**；
6. **现象：同一 RID 在两家 ECU 输入格式不同。原因：RID 是 OEM/供应商自定义空间，无强制统一。对策：永远按各 ECU 的 CDD 写脚本，不复用参数模板**。

## 面试高频题

**Q1：RID 和 DID 的本质区别？**
答：DID 标识一块数据（22/2E 读写）；RID 标识一段动作（31 启动/停止/取结果），有执行过程和结果语义。

**Q2：31 的三个子功能？**
答：01 start（带输入参数启动）、02 stop（中止）、03 requestResult（取执行结果）；短例程 start 直接回结果。

**Q3：`31 01 FF 00` 是干什么的？**
答：按惯例是刷写后的校验例程：ECU 对新固件算 CRC/验签，Bootloader 据此决定是否放行启动——刷写闭环的关键一步。

**Q4：例程执行失败会回负响应吗？**
答：不一定：请求被拒回 NRC（0x22/0x31/0x72 等）；例程执行了但结果失败，走正响应 71 + 结果码——判成败要看结果字段。
