# SID22-读DID

> 一句话定位：诊断流量之王——按 DID 号向 ECU 要一块数据（版本号、VIN、传感器值），一条请求可带多个 DID 由 ECU 拼装返回，配错会话/安全就在 0x7E/0x33 上翻车。
> 等级：L1→L2 ｜ 前置：[01-服务总览](01-服务总览.md)

## 原理

### DID 是什么：数据的门牌号

DID（Data Identifier）是 2 字节编号，指向 ECU 内一块定长/变长数据。车规惯例把号码段当"地址分区"用：F1xx 服务/版本信息（F187 件号、F189 SW 版本、F190 VIN）、F2xx ECU 配置，OEM 各自划分供应商区。**DID 表是项目诊断需求的核心资产**——号码怎么分、字节序怎么定，见 [DID与RID设计](../../2-L2进阶/DID与RID设计/README.md)。

### 多 DID 一次读：请求串联、响应拼装

一条 22 请求可携带多个 DID，ECU 按序把每个"DID+数据"拼进同一条正响应：

```plantuml
@startuml
autonumber on
participant "诊断仪" as TESTER
participant "Dcm (ECU)" as ECU
participant "数据提供者\n(SWC/DEM/RTE)" as APP

TESTER -> ECU : 22 F2 10 F1 87（一次要两个 DID）
ECU -> APP : 查 DID 路由表，分别取数
APP --> ECU : F210 数据（示例自定义配置码 2B）
APP --> ECU : F187 数据（件号 15B）
note right of ECU : 拼装：62 + F210+数据 + F187+数据
ECU --> TESTER : 62 F2 10 <2B> F1 87 <15B>
note right of ECU : 拼装后超过 Dcm 缓冲\n则整条拒绝 7F 22 14
@enduml
```

两条铁律：**多 DID 中任何一个不可读（不存在/会话不符/条件不符），整条请求失败**——没有"部分成功"；**拼装后总长超过 ECU 缓冲（含 CanTp 上限），回 NRC 0x14 responseTooLong**——所以"一次读几个"不只是效率问题，是能不能读成的问题。

### 谁在提供数据

Dcm 只接线不产数：静态信息（版本号）配置期直连常量；动态值（传感器、状态）经 RTE/DID 回调从 SWC 取；少数 DID（如 DTC 相关计数）由 Dem 提供。**"22 拿到的值不对"十有八九不是 22 的问题，而是提供者侧的问题**——排障先确认提供者回调的取数路径。

## 详解

### 报文格式逐字节

**请求：** `22 + DID(2B) [+ DID(2B)]...`，例 `22 F1 90`。

| 字节 | 值 | 含义 |
|---|---|---|
| 1 | 0x22 | SID：ReadDataByIdentifier |
| 2~3 | 0xF190 | 第 1 个 DID |
| 4~5 | 0xF187 | 第 2 个 DID（可再串联） |

**正响应：** `62 + DID + 数据 [+ DID + 数据]...`

| 字节 | 值 | 含义 |
|---|---|---|
| 1 | 0x62 | SID+0x40 |
| 2~3 | 0xF190 | 回显 DID |
| 4~n | "V1.2.3" | 该 DID 的数据（长度按 CDD 定义） |
| n+1~ | 0xF187 + 数据 | 第二组"回显+数据"依序拼接 |

**负响应 `7F 22 NRC` 高频表：**

| NRC | 场景 | 排障方向 |
|---|---|---|
| 0x14 | 响应超长 | 减少 DID 个数、拆多次读；核对 Dcm 缓冲配置 |
| 0x22 | 条件不满足 | 该 DID 标注了读取条件（车速/会话），当前不满足 |
| 0x31 | 请求超出范围 | DID 不存在——CDD 有而 Dcm 没配，或号码打错 |
| 0x33 | 安全拒绝 | 该 DID 要求解锁，先走 27 |
| 0x7E/0x7F | 会话不支持 | 换会话（多数受限 DID 在扩展会话开放） |

### 读数据的时序：等还是不等

正常 22 在 P2（典型 50ms~）内返回；提供者慢（如要跨总线取数）时 ECU 回 **0x78 挂起**续命到 P2\*（典型 5s）再出结果——诊断仪把 0x78 当"处理中"而不是错误，抓包看到一串 7F 22 78 末尾跟 62 是正常节奏。

## 配置层

- Dcm 中每个 DID 一行 **DcmDspData/DID 行**：长度、字节序、会话支持、安全等级、读回调（`DspDataRead`）都挂在这——接线细节见 [Dcm配置](../../2-L2进阶/Dcm配置/README.md)；
- CDD/ODX 里同一张 DID 表的另一份拷贝，两侧不同步的典型症状：工具发一个 CDD 里有、Dcm 里没有的 DID → 0x31。数据库侧见 [诊断数据库](../../2-L2进阶/诊断数据库/README.md)；
- 与 2A（ReadDataByPeriodicId，周期上报）、2F（IO 控制）共享 DID 空间的项目，注意三者对同一 DID 的行为差异。

## 易错点与陷阱

1. **现象：多 DID 请求稳定报 0x14。原因：几个大 DID 拼装超了缓冲。对策：拆单读或按 CDD 预估长度分批**；
2. **现象：单个 DID 能读，组合读就 0x31。原因：组合里混进了一个未配置/权限不符的 DID，整条失败。对策：二分法定位害群之马，逐个核对 CDD**；
3. **现象：默认会话读 F190 成功，读 F15E 报 0x7E。原因：不同 DID 的会话支持不同。对策：查该 DID 的 Session 矩阵，先进扩展会话**；
4. **现象：读出的多字节数值和预期差 100 倍量级/字节颠倒。原因：字节序与缩放因子（scaling）在工具侧配错。对策：按 CDD 的字节序（大端为主）与物理单位重配 DBC/CDD 解析**；
5. **现象：偶发 22 超时。原因：提供者回调阻塞或 ECU 负载高。对策：看是否伴随 0x78；提供者侧必须在 P2\* 内返回，超时上限别顶着配**。

## 面试高频题

**Q1：22 支持一次读多个 DID 吗？规则是什么？**
答：支持，请求里串联多个 2 字节 DID；任何一个不可读整条失败，无部分成功；拼装超缓冲回 0x14。

**Q2：正响应的格式？**
答：`62 + DID + 数据`按请求顺序串联，每个 DID 先回显号码再跟数据。

**Q3：0x31 和 0x33 分别在什么场景出现？**
答：0x31：DID 不存在（路由未配/号码错）；0x33：DID 存在但需先通过 27 解锁。

**Q4：Dcm 在 22 里扮演什么角色？**
答：路由与拼装：查 DID 表 → 调提供者回调取数 → 按序拼响应 → 发送；数据本身来自 SWC/Dem/常量。
