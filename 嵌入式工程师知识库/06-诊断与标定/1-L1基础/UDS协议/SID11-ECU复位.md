# SID11-ECU复位

> 一句话定位：让 ECU 按指定方式"重启一次"——硬/点火/软三档复位深度递减，复位完成后一律回到默认会话，是写配置生效与刷写收尾的"最后一脚油门"。
> 等级：L1→L2 ｜ 前置：[SID10-会话控制](SID10-会话控制.md)

## 原理

### 复位深度：三种方式一张图

```plantuml
@startuml
autonumber on
participant "诊断仪" as TESTER
participant "Dcm" as DCM
participant "EcuM/BswM" as ECUM
participant "硬件 (MCU)" as HW

TESTER -> DCM : 11 01（硬复位）
DCM --> TESTER : 51 01（先回正响应，再动手）
DCM -> ECUM : 触发复位请求
ECUM -> HW : 断外设电/看门狗复位
note right of HW : 掉电级重启：\nRAM 可能丢失，\n所有状态从零初始化
HW --> ECUM : 重启，走完整启动序列
ECUM --> DCM : Dcm 重新初始化
note over DCM : 会话=默认，安全=锁定，\n一切回到上电原点
@enduml
```

| 子功能 | 名称 | 复位深度 | 典型场景 |
|---|---|---|---|
| 0x01 | hardReset 硬复位 | 最深：等效断电重启，RAM 状态丢失 | 刷写固件后的生效复位 |
| 0x02 | keyOffOnReset 点火复位 | 模拟 KL15 off/on 一个循环（软模拟，非真断电） | 复现"下电再上电"才能暴露的问题 |
| 0x03 | softReset 软复位 | 最浅：软件重启（跳复位向量/重初始化栈），RAM 可保留 | 写完配置字让任务快速重新加载 |

OEM 还常自定义 0x04+（如"复位进 Bootloader"），具体以 CDD 为准——**子功能表永远以目标 ECU 的诊断数据库为准，不是背标准**。

### 复位后一定回默认会话

无论复位前在扩展/编程会话、解锁到几级，复位 = Dcm 重新初始化 = **默认会话 + 安全锁定 + S3 停止计时**。所以诊断脚本在 11 之后必须重新走 `10 03 → 27 → ...` 全流程，直接复用旧会话状态必吃 0x7F/0x33。

### 报文时序的细节：先应答还是先复位？

协议要求 ECU **先发正响应 51，再执行复位**——否则诊断仪永远等不到那条 51。这意味着抓包看到 `51 01` 之后 ECU 会"消失"几秒（重启中），这期间的诊断请求全部超时，属正常现象。

## 详解

### 报文格式逐字节

**请求：**

| 字节 | 值 | 含义 |
|---|---|---|
| 1 | 0x11 | SID：ECUReset |
| 2 | 0x01/0x02/0x03 | 子功能：复位类型（bit7=0x80 可抑制） |

**正响应：**

| 字节 | 值 | 含义 |
|---|---|---|
| 1 | 0x51 | SID+0x40 |
| 2 | 0x01/0x02/0x03 | 回显子功能 |
| 3（可选） | powerDownTime | 仅 0x04 powerDown 时携带，下电前延迟（秒） |

**负响应：** `7F 11 NRC`

| NRC | 场景 |
|---|---|
| 0x11/0x12 | 11 服务或该子功能不支持（不少量产件只实现 0x01） |
| 0x13 | 长度错误 |
| 0x22 | 条件不满足：车速不为 0、发动机运行中不允许复位 |
| 0x33 | 复位要求先解锁（部分 OEM 把 11 列为受保护服务） |
| 0x7E/0x7F | 会话不支持 |

### 与 EcuM 下电路径的一句关联

AUTOSAR 里 11 的执行链是 **Dcm → Dcm_EcuReset 回调 → EcuM（经 BswM 请求 EcuM_StateReset 或直接 MCU 复位）**：硬复位通常直接喂看门狗/调 `Mcu_PerformReset`；软复位走 RUN→下电序列再快速回 RUN。理解这句就够了，EcuM 细节在 02 区电源管理带展开。

## 配置层

- Dcm 中 11 服务的子功能支持表与"是否需要安全解锁"直接配置在 **DcmDsdServiceRow**；
- 复位动作挂接点：实现 `Dcm_EcuReset()` 回调，内部按子功能分发到 EcuM/BswM/Mcu——接线细节见 [Dcm配置](../../2-L2进阶/Dcm配置/README.md)；
- 刷写流程把 `11 01` 作为收尾步骤之一，与 34-37 的衔接见 [SID34-37-刷写下载](SID34-37-刷写下载.md) 与 L3 带的 [Bootloader](../../3-L3高级/Bootloader/README.md)。

## 易错点与陷阱

1. **现象：发 11 01 后立即读 DID，全部超时。原因：复位执行中 Dcm 不可用。对策：脚本在 11 之后加 2~5s 延时（按 ECU 启动时间实测），再重连**；
2. **现象：写完 2E 配置字后不重启，行为没变。原因：该 DID 配置为"复位后生效"，当前运行值还是旧的。对策：CDD 里确认 DID 生效策略，写完跟一条 11 01（写后生效时机详见 [SID2E](SID2E-写DID.md)）**；
3. **现象：11 02 点火复位报 0x12。原因：该 ECU 只实现硬复位。对策：查 CDD 子功能表，用 11 01 或真实点火循环替代**；
4. **现象：11 01 报 0x22。原因：车速/使能条件不满足，OEM 把复位列为行驶中禁止。对策：确认车速为 0 且 KL15 状态符合要求**；
5. **现象：诊断仪在 11 之后用旧会话发 22，报 0x7F。原因：复位已跌回默认会话且 S3 停止。对策：复位后重走 10 03 → 27 完整握手**；
6. **现象：期望 RAM 保留的数据在 03 软复位后也丢了。原因：实现上软复位仍走了完整下电/初始化，RAM 未按"保留区"处理。对策：与软件负责人确认 no-init/retained RAM 划分，别按标准字面推断**。

## 面试高频题

**Q1：11 的三个标准子功能差在哪？**
答：硬复位=断电级（RAM 丢）；点火复位=模拟 KL15 循环；软复位=软件重启（RAM 可保留）。深度递减、用途各异。

**Q2：复位后 ECU 处于什么会话？**
答：默认会话，安全锁定状态。任何高权限操作都要重新 10→27。

**Q3：ECU 是先复位还是先回正响应？**
答：先回 51 正响应再执行复位，否则诊断仪收不到确认。复位期间的请求超时是正常的。

**Q4：AUTOSAR 中 11 的执行链？**
答：Dcm 收到请求 → 回 51 → 调用 `Dcm_EcuReset` 回调 → EcuM/BswM 执行状态切换或 MCU 复位。
