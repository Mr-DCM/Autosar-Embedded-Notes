# SID27-安全访问

> 一句话定位：诊断世界的"取钥匙"——ECU 发随机种子、诊断仪回密钥证明身份，解锁后写 DID/刷写才放行；配错算法、连错次数、没等延时是产线三大经典卡点。
> 等级：L2 ｜ 前置：[SID10-会话控制](SID10-会话控制.md)

## 原理

### seed-key 完整时序

```plantuml
@startuml
autonumber on
participant "诊断仪" as TESTER
participant "Dcm (ECU)" as ECU

TESTER -> ECU : 10 03（先切对会话）
ECU --> TESTER : 50 03
TESTER -> ECU : 27 01（奇数子功能：请求种子）
note right of ECU : 生成随机 seed，\n同时保存"等待密钥"状态
ECU --> TESTER : 67 01 45 A3 7C 92（seed 4 字节）
TESTER -> TESTER : key = F(seed)（本地算钥匙）
TESTER -> ECU : 27 02 + key（偶数子功能：交钥匙）
alt 密钥正确
  ECU --> TESTER : 67 02（解锁成功，安全等级=1）
else 密钥错误
  ECU --> TESTER : 7F 27 35（invalidKey，失败计数+1）
else 已解锁还再发 27 01
  ECU --> TESTER : 67 01 00 00 00 00（seed 全 0 = 已解锁）
end
note over ECU : 切会话(10)/复位(11)/S3 超时\n都会把解锁状态清零
@enduml
```

### 奇偶子功能成对出现

安全等级按"奇-偶对"编号：**01 请求种子 / 02 发送密钥**是一级；**03/04 二级**；**05/06……** 依此类推。规则三条：

1. 偶数请求必须紧跟同等级的奇数响应之后（否则 NRC 0x24 请求序列错误）；
2. **已解锁状态下再发奇数请求，seed 返回全 0**——诊断仪用它判断"要不要重走解锁"，不必盲目再算 key；
3. 高等级通常需要先解锁低等级（OEM 自定义，看 CDD）。

### 尝试计数与延时惩罚：防暴力破解

| NRC | 触发 | 机制直觉 |
|---|---|---|
| 0x36 exceedNumberOfAttempts | 错误 key 次数达上限（典型 3 次） | 计数器满，锁死；常需断电或正确解锁流程才能清零 |
| 0x37 requiredTimeDelayNotExpired | 惩罚延时未到（典型 10s） | 每次失败（含成功后）启动延时计时，期间再发 27 直接拒绝 |

两个计数常一起用：前几次错是 0x35（invalidKey），达到上限后一律 0x36；延时期间连种子都不给。**产线脚本最怕 0x37**——机械重试只会不断重置惩罚计时，越试越久。

### 密钥算法设计原则（不涉及真实算法）

- **单向性**：由 seed 推 key 容易、由 key 反推 seed 不可行——杜绝抓一次包就伪造；
- **算法与密钥不出库**：算法源码、口令常量只在 ECU 侧与诊断仪工具链（加密容器）里，CDD 中只登记"4 字节 seed / 4 字节 key"的接口形状；
- **加时间因子**：纯 seed→key 映射可被重放（同一 seed 再发同一 key），高性能要求的等级应引入时间戳/计数器因子；
- **随机源要真随机**：seed 用固定值或弱伪随机，等于把锁换成纸糊的——这也是 2020 版引入证书认证（[SID29](SID29-认证.md)）的动机之一。

## 详解

### 报文格式逐字节

**请求种子（奇数）：** `27 01`

| 字节 | 值 | 含义 |
|---|---|---|
| 1 | 0x27 | SID |
| 2 | 0x01/0x03/0x05 | 等级-种子（奇数） |

**正响应（种子）：** `67 01 + seed`

| 字节 | 值 | 含义 |
|---|---|---|
| 1 | 0x67 | SID+0x40 |
| 2 | 0x01 | 回显 |
| 3~n | seed | 长度 OEM 定义（常见 2/4/8 字节），已解锁时全 0 |

**发送密钥（偶数）：** `27 02 + key`；正响应只有 `67 02` 两字节。

**负响应 `7F 27 NRC` 一览：**

| NRC | 场景 |
|---|---|
| 0x12 | 子功能不存在（该等级未配置） |
| 0x24 | 没要种子直接发 key、或奇偶不配对 |
| 0x35 | key 校验失败 |
| 0x36 | 错误次数超限 |
| 0x37 | 延时惩罚未到期 |
| 0x7E/0x7F | 当前会话不支持（编程等级常只在编程会话开放） |

## 配置层

- Dcm 中每个安全等级是一组 **DcmSecurityRow**（seed 长度、key 长度、尝试上限、延时时间、所属会话），算法实现在 `Dcm_GetSeed`/`Dcm_CompareKey`（或 OEM 命名）两个回调里挂接——配置侧见 [Dcm配置](../../2-L2进阶/Dcm配置/README.md)；
- **哪些 DID/RID/服务需要哪级解锁**，登记在各自数据行的 Security 引用上；CDD 与 Dcm 两边必须一致，不一致在产线表现为"工具显示可写、ECU 报 0x33"；
- 解锁状态的生命周期与会话/复位/S3 联动（见 [SID10](SID10-会话控制.md)、[SID11](SID11-ECU复位.md)）。

## 易错点与陷阱

1. **现象：27 01 回 0x7E。原因：目标安全等级只在编程会话开放，当前在扩展会话。对策：按 CDD 核对该等级的 Session 限定，先 10 02 再 27**；
2. **现象：key 明明算对了还报 0x35。原因：seed/key 长度或字节序（大小端）与 ECU 实现不一致。对策：用同一 seed 让 ECU 侧与工具侧各自 dump 中间值比对**；
3. **现象：连错三次后一直 0x36，断电也没用。原因：尝试计数器落在 NvM/EEPROM。对策：按 OEM 规范走解锁恢复流程（有的要求正确完成一次 27 才清零）**；
4. **现象：脚本重试 27 越试越快被拒，全变 0x37。原因：失败重试会刷新惩罚计时器。对策：遇 0x37 老老实实 sleep 满延时（常 10s）再试，别循环轰炸**；
5. **现象：已解锁后再 27 01 拿到全 0 seed，算法算出 key 又报 0x24。原因：seed 全 0 表示"已解锁"，不是新种子，不该再发 27 02。对策：脚本先判 seed 非 0 才走交钥匙步骤**；
6. **现象：抓包回放历史报文竟能解锁。原因：算法无时间因子，纯 seed-key 映射可重放。对策：安全评审时列为必改项，或迁移到 29 认证**。

## 面试高频题

**Q1：27 的完整流程？**
答：切会话（10）→ 27 奇数请求种子 → ECU 回随机 seed → 诊断仪本地算 key → 27 偶数发 key → 67 偶数正响应即解锁；失败分别 0x35/0x36/0x37。

**Q2：奇偶子功能怎么配对？**
答：同一安全等级成对：01/02 一级、03/04 二级……偶数必须紧跟该等级奇数的响应之后，否则 0x24。

**Q3：seed 全 0 意味着什么？**
答：ECU 已处于该等级解锁状态，诊断仪可跳过解锁直接干活（或转去解更高级别）。

**Q4：解锁状态什么时候会被清掉？**
答：切换会话（10）、ECU 复位（11）、S3 超时跌回默认会话——三条路径全部回到锁定。
