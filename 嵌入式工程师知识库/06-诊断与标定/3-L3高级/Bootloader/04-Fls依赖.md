# 04-Fls依赖

> 一句话定位：刷写的最后一公里全落在 Flash 上——BL 要 Fls 交付擦/写/读三种能力、一张钉死的地址布局图、一套口径一致的 CRC 规则，以及"驱动在 RAM 里跑"的重定位手段。
> 等级：L2 ｜ 前置：[刷写流程总览](01-刷写流程总览.md) + [Fls驱动](../../../04-MCAL与外设驱动/2-L2进阶/Fls与Fee/01-Fls驱动.md)

## 原理

34/36/37 看似在传数据，真正的三个 Flash 动作是：31 例程触发**擦除**、36 块触发**写入**、31 例程触发**读出算 CRC**。这三件事全靠 Flash 驱动（AUTOSAR 的 Fls 或芯片原厂库）完成，而 BL 对它的要求比应用侧苛刻得多——**擦写时序不能被打断、驱动代码不能住在被擦的区域、布局必须和镜像一一对应**。

一张布局图把所有依赖摆到桌面上（TC377 风格示例，具体地址由项目分区表定）：

```text
0xA008_0000 ┌────────────────────────────┐
            │  BL 区（含诊断栈+Flash 驱动）│  ← 34 地址表禁写；驱动可在此或 RAM
0xA00F_FFFF └────────────────────────────┘
0xA010_0000 ┌────────────────────────────┐
            │  应用 Bank A（镜像头+程序） │  ← 镜像头：版本/大小/CRC32/入口
0xA02F_FFFF └────────────────────────────┘
0xA030_0000 ┌────────────────────────────┐
            │  应用 Bank B（备用镜像）    │  ← 双分区回滚的备区（03 篇）
0xA04F_FFFF └────────────────────────────┘
0xA050_0000 ┌────────────────────────────┐
            │  标定区（Flash page）       │  ← XCP 固化目标，独立升级
0xA057_FFFF └────────────────────────────┘
0xA058_0000 ┌────────────────────────────┐
            │  NVM 数据区（Fee 逻辑扇区） │  ← 激活标志/失败计数存独立小扇区
0xA05B_FFFF └────────────────────────────┘
            ┌────────────────────────────┐
            │  DFlash / EEE（S32K：EEE） │  ← 掉电数据（标志、计数）
            └────────────────────────────┘
```

布局原则一句话：**BL 区与数据区钉死不动，应用区对称可换，标定区独立成区**——这样擦应用区永远碰不到 BL 和掉电数据。

## 详解

### BL 对 Fls 驱动的需求表

| 需求 | Fls API / 能力 | BL 用在哪 | 关键点 |
|---|---|---|---|
| 擦除 | `Fls_Erase(addr, length)`（扇区对齐） | 31 擦除例程 | 擦除粒度=扇区（TC377 扇区不等大，见 [DMU与扇区](../../../02-芯片与体系结构/2-L2进阶/TC377平台/存储器映射/03-DMU与扇区.md)；S32K 为 phrase/sector，见 [FTFC机制](../../../02-芯片与体系结构/1-L1基础/S32K平台/存储器与Flash/01-FTFC机制.md)），长度必须按扇区向上取整 |
| 写入 | `Fls_Write(addr, buf, len)` | 36 块落盘 | 页编程约束：一次写入长度/对齐按芯片规格；先擦后写，只许 1→0 |
| 读出 | `Fls_Read` 或直接内存读 | CRC 校验、版本回读 | PFlash 可线性读时直接指针读更快；DFlash 走驱动 |
| 任务结果 | `Fls_GetJobResult()` / 主函数轮询或完成中断 | 全流程状态推进 | 擦写期间 CPU 不能在依赖区取指——与 02 篇 RAM 驱动联动 |
| 扇区管理 | 分区表（地址↔扇区映射） | 34 地址合法性检查 | 表与链接脚本同源生成，手抄必错 |

Fls 本身的接口契约与异步模型在 04 区 [Fls驱动](../../../04-MCAL与外设驱动/2-L2进阶/Fls与Fee/01-Fls驱动.md) 已细讲，这里只补 BL 特有视角。

### CRC 计算时机与范围

- **时机**：37 退出后、31 激活前——**读回 Flash 实际内容**算，而不是对 RAM 缓冲算。理由：写 Flash 可能因坏块/掉电产生位错，"我以为写了"和"真写进去了"必须用读回来验证；
- **范围**：从镜像头第一个字节到镜像声明结束；**未写满的字节按擦除态 0xFF 参与计算**（"无关字节填充"约定）——上位机离线算 CRC 与 BL 在线算 CRC 必须逐字节同口径，否则永远对不上（02 篇陷阱 3 的根源）；
- **存哪**：CRC 值通常放在镜像头内随镜像一起下载；BL 算完与头内值比对，通过才写"有效"标志。启动时再复算一次头 CRC，坏了就走 03 篇回滚。

### Flash 驱动的 RAM 执行

两条路线（02 篇讲过动机，这里讲落地）：

1. **重定位链接**：Flash 驱动源码标 `MemMap` 的 RAM 段（如 `_MEM_$$CORE0$$fls_code`），链接脚本把该段定位到 PSPR/DSPR，启动时 BL 用复制循环把它从加载地址搬到运行地址再调用——段名与复制逻辑见 [AUTOSAR-MemMap机制](../../../01-编程语言/2-L2进阶/内存管理/05-AUTOSAR-MemMap机制.md)，RAM 区特性见 [DSRAM-PSPR-DSPR](../../../02-芯片与体系结构/2-L2进阶/TC377平台/存储器映射/02-DSRAM-PSPR-DSPR.md)；
2. **运行时下载**：把独立编译的 Flash 驱动小镜像按普通数据 34/36 下到 RAM 固定地址，BL 通过函数指针调用（入口/校验由驱动镜像头约定）——驱动随上位机更新，BL 不用重编。

验证手段：擦写期间用调试器看 PC，必须始终落在 RAM 段或 BL 区，一旦进入被擦 bank 即配置错误。

## 配置层/工程关联

- **链接脚本与分区表同源**：BL 的地址合法性表、镜像头地址、Fee 扇区划分应由同一份分区描述生成（脚本产出 C 表 + lsl/ld 两份），杜绝"表和脚本各改一半"；
- **Fee/NvM 边界**：BL 存激活标志/计数用独立小扇区直写（裸 Fls），不走 Fee——BL 里带整套 NvM 链路太重；应用运行期的数据才走 Fee/NvM（[与NvM链路](../../../04-MCAL与外设驱动/2-L2进阶/Fls与Fee/03-与NvM链路.md)、[Fee模拟EEPROM](../../../04-MCAL与外设驱动/2-L2进阶/Fls与Fee/02-Fee模拟EEPROM.md)），两者物理扇区必须分开；
- **擦写互斥**：BL 擦写期间挂起其他 Fls 使用者（应用未运行时可忽略，App+BL 共存架构要显式加锁）。

## 易错点与陷阱

1. **现象：擦除长度不是扇区整数倍，返回错误或擦不干净。原因：Fls_Erase 按扇区粒度生效，34 声明大小直接当长度传入。对策：BL 内部按分区表向上对齐到扇区边界再擦。**
2. **现象：CRC 偶发不匹配但数据看着都对。原因：尾部空隙一侧算 0xFF 一侧跳过；或头部长度字段本身算不算进 CRC 口径不一致。对策：文档锁死"起止+填充"，用小镜像联调对齐。**
3. **现象：写 Flash 中途复位后该区偶发位错。原因：页编程未完成即断电（写入非原子）。对策：CRC 读回校验兜底（这就是必须读回算的原因），必要时关键区双份。**
4. **现象：BL 里也配了 Fee，与应用的 Fee 抢 DFlash。原因：BL/应用各自带 NvM 栈，逻辑扇区重叠。对策：BL 用裸 Fls+独立小扇区，或两边 Fee 配置严格分区并校验。**
5. **现象：RAM 驱动函数调用即跑飞。原因：复制循环没跑（段没搬）就调用了，或函数指针类型/入口错。对策：启动先复制段、再校验段 CRC、后调用；调用前反汇编核对入口。**
6. **现象：升级后标定区丢了。原因：分区表变更后标定区被并入应用区遭擦除。对策：分区表变更走兼容性评审——标定/数据区只许向后扩展不许挪位。**

## 面试高频题

**Q1：BL 对 Flash 驱动有哪些要求？**
A：擦（扇区对齐）、写（页编程约束、先擦后写）、读（CRC 读回验证）、异步任务结果查询、以及一张与链接脚本同源的分区表支撑 34 地址合法性检查。擦写期间驱动还要保证不在被擦区执行。

**Q2：CRC 为什么要在写入后读回来算？**
A：Flash 写入可能因坏块、断电产生位错，对 RAM 缓冲算 CRC 只验证了"发对了"，读回算才验证"存对了"。启动时还要复算镜像头 CRC，坏了走回滚——这是双分区方案的安全闭环。

**Q3：Flash 驱动 RAM 执行怎么实现？**
A：两条路——链接期重定位（MemMap 段放 PSPR/DSPR，启动复制后调用）或运行期下载（驱动作为小镜像 34/36 下到 RAM 固定地址，函数指针调用）。前者随 BL 固定，后者可随上位机升级驱动。

**Q4：BL 的数据（激活标志等）为什么不用 Fee/NvM？**
A：BL 要极简且独立——带整套 NvM 链路体积大、依赖多，且和应用侧 Fee 可能抢物理扇区。惯例是 BL 用裸 Fls 在独立小扇区直写双份标志+CRC。
