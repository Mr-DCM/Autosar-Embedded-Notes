# 01-从一个坏掉的ECU说起-调试全景

> 一句话定位：跟着一个"报文丢了"的 bug 从接到问题到关闭走完全程，顺手把调试器/总线工具/方法论/案例库四件工具的位置摆到一张地图上——之后本区任何子目录迷路，都能靠这张地图找到回程。
> 等级：L1 ｜ 前置：无

## 一个真实的下午

周一早上，测试同事丢来一句话："你负责的 ECU，车速报文偶尔丢，仪表偶尔闪一下，概率大概千分之一。"

这就是调试的起点：**一句模糊的现象描述 + 一个"偶尔"**。接下来你做什么？凭感觉改代码？祈祷它自己好？都不是。调试是一场有章法的旅行，本篇就用这一个 bug 把整条路走一遍。

```plantuml
@startuml
title 一个"报文丢了"bug 的完整旅程
start
:接到问题：车速报文**偶尔**丢;
:第 1 步 复现\n想办法让它"必现"或"高概率出现"\n（低温箱/高频触发/压力循环）;
if (能稳定复现吗？) then (能)
  :第 2 步 假设\n列出候选原因：\n软件没发？总线没到？对端没收？
else (不能)
  :加"飞行记录仪"\n日志/录波器挂上，等它自己再犯;
  detach
endif
:第 3 步 分治——用工具切开怀疑面;
split
  :总线工具看**线上**\nCANoe trace：这帧到底上没上总线？
split again
  :调试器看**程序内部**\nTRACE32 断点：发送函数被调用了吗？变量对吗？
end split
if (总线上没有这帧？) then (没有)
  :问题在**本机软件**\n继续往里查：变量、状态机、优先级;
  :定位到根因\n（例：某分支把发送条件写反了）;
else (总线上有)
  :问题在**总线或对端**\n查物理层/网关/接收方;
  :定位到根因\n（例：对端滤波器配错 ID）;
endif
:第 4 步 修复 + 验证\n只改这一个变量，回归复现手段确认;
:第 5 步 复盘\n一坑一档：现象→定位→根因→预防;
:bug 关闭，资产 +1;
stop
@enduml
```

五个直觉要点：

1. **复现在一切之前**——不能复现的 bug 等于看不见的敌人，先想办法让它"多犯错"；
2. **假设先于工具**——工具是用来"切开怀疑面"的，不是用来瞎看的；
3. **先分治、后深入**——总线有没有这帧，一查就能把"本机软件问题"和"总线/对端问题"一刀切开；
4. **只改一个变量**——一次改三处，好了也不知道是哪处起效，坏了更说不清；
5. **复盘才算结束**——bug 不入档，下次同一个坑还会踩一遍。

## 工具箱地图：四件工具各管一摊

| 工具                     | 管什么             | 直觉                                                              | 本区位置                                      |
| ------------------------ | ------------------ | ----------------------------------------------------------------- | --------------------------------------------- |
| 调试器（TRACE32/串口）   | **程序内部** | "打开引擎盖"：断点、单步、看变量、读日志                          | [调试器](../1-L1基础/调试器/README.md)         |
| 总线工具（CANoe/CANape） | **线上报文** | "装摄像头"：这帧报文发没发、什么时候发、内容对不对                | [总线工具](../2-L2进阶/总线工具/README.md)     |
| 调试方法论               | **套路**     | "老兵的检查单"：复位溯源、Trap 定位、busoff、假醒，照着走少走弯路 | [调试方法论](../3-L3高级/调试方法论/README.md) |
| 踩坑案例库               | **沉淀**     | "病历本"：一坑一档，让每个 bug 只发生一次                         | [踩坑案例库](../2-L2进阶/踩坑案例库/README.md) |

一句话记忆：**看不见的用调试器，看得到的用总线工具，怎么查用方法论，查完记进案例库。**

另外还有一件"防患工具"：单元测试（[单元测试与自动化](../2-L2进阶/单元测试与自动化/README.md)）——它在 bug 出生之前就把一部分掐死在代码里，属于"不调试的调试"。

## 三种典型故障域：先猜对域，再选工具

拿到问题，先问一句："这更像哪一类错？"

| 故障域                  | 典型症状                               | 直觉                                 | 首选工具                               |
| ----------------------- | -------------------------------------- | ------------------------------------ | -------------------------------------- |
| **软件逻辑错**    | 算出来的值不对、分支走错、偶发跑飞     | 程序"想错了"——**看变量**     | 调试器：断点 + 变量观察                |
| **通讯错**        | 报文丢了/错了/迟了、busoff、对端收不到 | 话没说到或没说清——**看总线** | 总线工具：trace + 错误统计             |
| **状态机/时序错** | 偶发不复现、上电概率性失败、睡眠假醒   | 顺序错了——**看时序**         | 日志时间戳 + 逻辑分析仪/CANoe 图形窗口 |

直觉展开：

- **软件逻辑错**：变量在某个瞬间变成了不该有的值。办法是"守株待兔"——在可疑变量上设断点/观察点，等它再变；
- **通讯错**：先别怀疑软件。打开 CANoe 看 trace，这帧到底有没有上总线？没有→查发送端软件；有但内容错→查打包（Com/DBC）；有且对→查接收端。**先看总线，再查软件**，能省一半时间；
- **时序错**：单看任何一个变量都对，但顺序错了（例：应用来读时初始化还没完成）。这类问题的钥匙是"时间轴"——把日志和总线报文放到同一条时间线上看。

三个 30 秒小场景，练一下"猜域"的手感：

| 场景                                   | 先猜哪个域                    | 第一动作                              |
| -------------------------------------- | ----------------------------- | ------------------------------------- |
| "车速信号偶尔显示 0，其他信号正常"     | 通讯错（单信号丢/错）         | CANoe 过滤该 ID，看线上数据与刷新周期 |
| "扭矩计算结果偶尔偏大，输入都对"       | 软件逻辑错（内部变量）        | TRACE32 观察中间变量，找出错的那一环  |
| "冷车启动偶发仪表黑屏一次，热车不复现" | 时序错（初始化顺序/低频时钟） | 上电日志时间戳 + 复现手段低温箱       |

## 复现难题：三招让"偶尔"变成"经常"

千分之一的 bug 最折磨人——等它犯错可能要一天。三个土办法：

1. **加压循环**：把触发条件做成脚本高频循环（如每 10ms 发一次触发报文），一晚上等于别人一个月的里程；
2. **改变环境**：低温箱、高温箱、电压跌落（KL30 拉低再恢复）——很多"偶发"其实是临界时序对温度/电压敏感；
3. **飞行记录仪**：复现不了就先布网——串口/RTT 日志环形缓冲 + CANoe 录制一直挂着，等它再犯时现场就在手里。

复现不了一定要"留下现场"，否则每次都从零开始猜——这是偶发问题最大的时间黑洞。

## 调试第一原则

三条，背下来：

1. **先复现，再动手**——不能复现就先加日志/录波，别凭想象改代码；
2. **再分治**——每一步都设计"能一刀切开怀疑面"的实验（总线有没有帧、函数有没有被调、变量是不是这个值），让每一步实验都排除一半可能；
3. **只改一个变量**——改完立刻验证；一次改多处 = 丢失因果链。

反面对照：新手最常见的三连击——"重启一下看看""把怀疑的代码都注释掉""多加几个延时"——本质上都是不复现、不分治、乱改三原则的反面教材。

自查口径：读完本篇你应能不查资料说出——四件工具各管什么、三种故障域各先看什么、调试三原则是什么。
