# 02-容器与参数

> 一句话定位：把 ECUC 值侧的两种节点——容器（Container）与参数（Parameter/Reference）——的 ARXML 语法逐行解剖，讲透 def-ref 配对机制、多重容器层级与路径寻址，读完能"看着标签说出这行配置在干什么"。
> 等级：L2 ｜ 前置：[ECU配置结构](01-ECU配置结构.md)

[上篇](01-ECU配置结构.md) 说了配置树 = 定义 × 值。本篇钻进值侧的 XML 细节：容器怎么开、参数怎么写、引用怎么指。目标不是背语法，是建立"标签级语感"——从此打开任何 ARXML 不再是黑压压一片尖括号。

## 原理

### 语法解剖：一个容器 + 三个参数

```
<ECUC-CONTAINER-VALUE>                          ← 容器节点（一个"抽屉"实例）
  <SHORT-NAME>CanIfTxPduCfg_EngSpd</SHORT-NAME> ← 容器名（树内唯一路径名，人读用）
  <DEFINITION-REF DEST="ECUC-PARAM-CONF-CONTAINER-DEF">/AUTOSAR/EcucDefs/CanIf/CanIfInitCfg/CanIfTxPduCfg
  </DEFINITION-REF>                             ← 锚定定义：我是哪种抽屉
  <PARAMETER-VALUES>
    <ECUC-NUMERICAL-PARAM-VALUE>                ← 参数 1：数值型
      <SHORT-NAME>CanIfTxPduCanId</SHORT-NAME>
      <DEFINITION-REF DEST="ECUC-INTEGER-PARAM-DEF">/AUTOSAR/EcucDefs/CanIf/.../CanIfTxPduCanId</DEFINITION-REF>
      <VALUE>291</VALUE>                        ← 真正的取值：0x123
    </ECUC-NUMERICAL-PARAM-VALUE>
    <ECUC-TEXTUAL-PARAM-VALUE>                  ← 参数 2：文本/枚举型
      <SHORT-NAME>CanIfTxPduCanIdType</SHORT-NAME>
      <DEFINITION-REF DEST="ECUC-ENUMERATION-PARAM-DEF">/AUTOSAR/EcucDefs/CanIf/.../CanIfTxPduCanIdType</DEFINITION-REF>
      <VALUE>EXTENDED_CAN</VALUE>
    </ECUC-TEXTUAL-PARAM-VALUE>
  </PARAMETER-VALUES>
  <REFERENCE-VALUES>                            ← 参数 3：引用型（指到别的节点）
    <ECUC-REFERENCE-VALUE>
      <SHORT-NAME>CanIfTxPduRefCanTxPdu</SHORT-NAME>  ← 引用节点自己的名字
      <DEFINITION-REF DEST="ECUC-REFERENCE-DEF">/AUTOSAR/EcucDefs/CanIf/.../CanIfTxPduRefCanTxPdu</DEFINITION-REF>
      <VALUE-REF DEST="ECUC-CONTAINER-VALUE">/Can/Can/CanGeneral/CanTxPduCfg_EngSpd</VALUE-REF>
    </ECUC-REFERENCE-VALUE>                             ← 引用的目标写在 VALUE-REF
  </REFERENCE-VALUES>
</ECUC-CONTAINER-VALUE>
```

三类值节点一张表：

| 节点类型 | XML 标签 | VALUE 写法 | 典型例子 |
|---|---|---|---|
| 数值参数 | `ECUC-NUMERICAL-PARAM-VALUE` | `<VALUE>291</VALUE>`（十进制） | CanId、超时时间 |
| 文本参数 | `ECUC-TEXTUAL-PARAM-VALUE` | `<VALUE>EXTENDED_CAN</VALUE>` | 枚举、true/false、字符串 |
| 引用 | `ECUC-REFERENCE-VALUE`（或 INSTANCE-REFERENCE） | `<VALUE-REF>/目标路径</VALUE-REF>` | TxPdu 指向 Can 驱动、Com 的 Ipdu 引用 |

### def-ref 配对机制

每个值节点都有且只有一个 `DEFINITION-REF`，指向定义侧（BSWMD）里的 ParamDef/ContainerDef 路径。校验时的三连问：

1. **锚点存在吗**——def 路径在所配模块的定义树里找得到吗？（找不到=版本错配/模块没装）
2. **锚点合法吗**——这个参数确实允许出现在当前父容器下吗？（摆错抽屉）
3. **值越界吗**——VALUE 落在 ParamDef 声明的范围/枚举集合内吗？（范围校验）

一句话：**DEFINITION-REF 是"户口"，VALUE 是"信息"，工具先验户口再看信息**。这也是 diff review 时为什么盯 def-ref 尾段——参数的"身份"变了，值再对也白搭。

### 多重容器层级：CanIf 走查

模块配置典型三层抽屉，以 CanIf 发送配置为例：

```
CanIf（模块根）
└─ CanIfInitCfg（初始化配置容器，常 1 个）
   └─ CanIfTxPduCfg × N（发送 PDU，多重容器——每条发送报文一个实例）
      ├─ CanIfTxPduCanId = 291
      ├─ CanIfTxPduCanIdType = EXTENDED_CAN
      └─ CanIfTxPduRefCanTxPdu → /Can/.../CanTxPduCfg_EngSpd（引用 Can 驱动对象）
```

读法：**模块根 → 功能分组容器 → 多重实例容器 → 叶子参数/引用**。"多重"意味着定义允许 N 个实例，实例之间靠各自的 SHORT-NAME 区分（如 `CanIfTxPduCfg_EngSpd`、`CanIfTxPduCfg_VehSpd`）——这就是为什么工具里配置界面长得像"加行/删行"的表格：每行 = 一个容器实例。

## 详解

### 路径寻址：`/Autosar/Os/...` 怎么读

ARXML 里所有引用与 SHORT-NAME 都在"树路径"坐标系里。两种根，别混：

| 路径开头 | 含义 | 例 |
|---|---|---|
| `/AUTOSAR/EcucDefs/...` | **定义树**：BSWMD 的定义路径，全 AUTOSAR 统一口径 | `/AUTOSAR/EcucDefs/CanIf/CanIfInitCfg/CanIfTxPduCfg` |
| `/模块名/...` | **值树**：本工程配置文件里的实例路径 | `/Can/Can/CanGeneral/CanTxPduCfg_EngSpd`、`/Os/OS/TaskEt_10ms` |

读路径三步：去掉头两个固定段 → 中间段是抽屉嵌套链 → 最后一段是实例名或参数名。例：`/Os/OS/TaskEt_10ms` = Os 模块值树 → OS 总容器 → 名叫 `TaskEt_10ms` 的 Task 实例。

- 跨模块引用（VALUE-REF）一定指向**值树**路径——所以引用断链时，要么目标实例被删了，要么 SHORT-NAME 被改名了；
- SHORT-NAME 是路径的一段，**改名即引用搬家**：改 SHORT-NAME 前先搜谁引用了它（见 [03-ARXML手读](03-ARXML手读.md) 的定位三招）。

### INSTANCE-REFERENCE 与 CHOICE-CONTAINER

进阶两眼，见到不慌：`ECUC-INSTANCE-REFERENCE-VALUE` 用来引用"某个容器定义的实例集合"（如 Os Task 集合）；CHOICE 容器定义表示"此处二选一"（如 Can 驱动里不同控制器类型的配置互斥分支）。它们都是同一套 def-ref 配对思想的变体。

## 配置层/工程关联

- tresos 的 xdm 与标准 ECUC arxml 一一对应（导入导出可互转），GUI 里每个输入框 = 一个 ParamDef 的值，每个列表行 = 一个多重容器实例；
- 排障套路：工具报错"引用失效/悬空"→ 打开 arxml 搜该 VALUE-REF 路径 → 沿路径逐段找断点（通常是中间某层容器被删/改名）；
- 联调对账：CanIf 的 TxPduCfg 与 Can 驱动的 CanTxPduCfg 必须一一对应（靠那个 VALUE-REF 串起来）——报文发不出去时，第一件事就是核对这条引用链是否完整；
- 手改 arxml 属高风险动作：改完必须让工具重新加载校验，并以 diff 报告留痕（见 [04-diff-review技巧](04-diff-review技巧.md)）。

## 易错点与陷阱

1. **把 SHORT-NAME 当注释随手改**：它是路径坐标，改名会让所有指向它的 VALUE-REF 断链——改名前全局搜索引用。
2. **只看 VALUE 不看 DEFINITION-REF**：两个同名的 `CanIfTxPduCanId` 可能挂在不同的 def 下（不同父容器），语义完全不同；比对参数先比对 def 尾段。
3. **十进制/十六进制误读**：ARXML 的 `<VALUE>291</VALUE>` 是十进制，别按 0x123 习惯读成别的数；工具界面显示 hex，文件里是十进制，来回核对要小心。
4. **引用与参数分不清**：PARAMETER-VALUES 里的值是"字面量"，REFERENCE-VALUES 里的 VALUE-REF 是"指针"——排障方向完全不同（值错 vs 链断）。
5. **多重容器少配/多配实例**：定义的 multiplicity 有上下限（0..1、1..n），删掉一个 TxPduCfg 容器可能顺带删掉别人对它的引用目标，校验器会一次报一串错——按第一处错修。
6. **手写 arxml 不带命名空间/schema**：xsi:schemaLocation 与 DEST 属性写错，文件能被文本编辑器保存却进不了工具——手改前先复制既有节点改值，别从零手写。

## 面试高频题

1. ECUC 容器与参数在 ARXML 里如何表示？SHORT-NAME 与 DEFINITION-REF 各起什么作用？
   答：容器是 `ECUC-CONTAINER-VALUE` 节点，参数挂在 PARAMETER-VALUES/REFERENCE-VALUES 下。SHORT-NAME 是树内唯一路径名（人读+被引用的坐标，改名即引用搬家）；DEFINITION-REF 是"户口"，把值节点锚定到定义侧的 ContainerDef/ParamDef——定义管合法性与范围，值管取什么。
2. PARAMETER-VALUES 与 REFERENCE-VALUES 的区别？各举一例。
   答：PARAMETER-VALUES 写字面量（数值 ECUC-NUMERICAL-PARAM-VALUE 如 CanIfTxPduCanId=291；文本 ECUC-TEXTUAL-PARAM-VALUE 如 CanIdType=EXTENDED_CAN）；REFERENCE-VALUES 写"指针"（VALUE-REF 指向值树路径，如 CanIfTxPduRefCanTxPdu → /Can/.../CanTxPduCfg_EngSpd）。排障方向不同：值错 vs 链断。
3. 什么叫 def-ref 配对？配置校验器按什么顺序检查？
   答：每个值节点用 DEFINITION-REF 与定义树配对。校验三连问：①锚点存在吗（def 路径在定义树里找得到，找不到=版本错配/模块没装）→②锚点合法吗（参数允许出现在当前父容器下吗）→③值越界吗（VALUE 落在 ParamDef 范围/枚举内吗）。
4. 一个 CanIf 发送 PDU 的配置从容器到参数到引用长什么样？（能白板画出三层抽屉）
   答：CanIf 模块根 → CanIfInitCfg（功能分组容器）→ CanIfTxPduCfg ×N（多重实例容器，每条发送报文一个，SHORT-NAME 如 _EngSpd）→ 叶子：参数 CanIfTxPduCanId=291（数值）、CanIdType=EXTENDED_CAN（文本）、引用 CanIfTxPduRefCanTxPdu 指向 Can 驱动的 CanTxPduCfg 实例——发送链就是靠这条 VALUE-REF 串起来的。
