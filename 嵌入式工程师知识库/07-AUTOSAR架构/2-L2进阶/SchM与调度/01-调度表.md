# 01-调度表

> 一句话定位：讲透 AUTOSAR OS 的 ScheduleTable——一张在时间轴上摆好 expiry point 的"节目单"：duration 与周期、expiry point 如何联动 Task/Event、隐式/显式同步一句话级，最后回答"毫秒级周期任务到底用 ST 还是 Alarm"。
> 等级：L2 ｜ 前置：[分层架构](../../1-L1基础/架构总览/01-分层架构.md)

服务层的 Os 里，让任务"每 10ms 跑一次"有两条路：Alarm（到点发一枪）和 ScheduleTable（整张节目单按表走）。国内项目（尤其 EB tresos + Infineon/NXP Os）近年几乎清一色用 ScheduleTable，因为它天生解决"多个周期任务的相位关系"问题——本篇讲清它为什么香、怎么配、哪里坑。

## 原理

### ScheduleTable 的机制：时间轴上的节目单

一个 ScheduleTable = 一条有限长度的时间轴（duration，tick 为单位）+ 轴上若干 **expiry point（到期点）**。表跑起来后从 0 走到 duration，每到 expiry point 就"放一次事先配好的动作"（激活任务/置事件），到头按配置重复（REPEATING）或停（ONESHOT）：

```
SchTbl_10ms（duration = 10ms，REPEATING，driver counter = 主频计数器）
周期→  |<────────────────────── 10ms ──────────────────────>|
tick:  0        1ms        5ms        10ms
       ├─────────┼──────────┼──────────┤
       │         │          │          │
   StartPoint  ExpPt_A    ExpPt_B   (绕回=下一个周期的 0)
   激活        SetEvent    SetEvent
   TaskEt_5ms  Ev_10ms    Ev_5ms
              (TaskEt_10ms)(TaskEt_5ms, 第二次)

读法：一张表可同时承载不同周期的动作——5ms 任务在 5ms 点出现两次，
10ms 任务在 10ms 点出现一次；相位（谁先谁后）由 expiry point 位置写死。
```

要点四条：

1. **duration 建议配成周期的整数倍/最小公倍数**：一张表管理多个周期任务，表长=各周期的最小公倍数（10ms+5ms→10ms 即可；10ms+20ms→20ms）；
2. **动作两类**：expiry point 里配 `ActivateTask` 或 `SetEvent`（也可配回调/增加计数器，工程上以前两者为主）；
3. **start 点**：表启动（`StartScheduleTableAbs/Rel`，常由 EcuM/BswM 或启动任务调）后按绝对/相对对齐计数器；
4. **表由 counter 驱动**：counter 是 Os 的"表针"（绑定硬件定时器，如 STM/GPT），表的 tick 换算由 counter 的 ticks per base 与表的前置分频决定。

### ScheduleTable vs Alarm：选型对照

| 维度 | ScheduleTable（调度表） | Alarm（闹钟） |
|---|---|---|
| 心智模型 | 一张节目单，多个动作有固定相位 | 独立闹钟，各自到点各自响 |
| 多周期管理 | 一张表统一管（10ms/20ms/100ms 共表） | 每个周期配一个 Alarm，互不知相位 |
| 相位/抖动 | 显式控制：expiry point 精确摆位，周期任务相位稳定 | 各 Alarm 独立计数，启动顺序/重装误差会漂 |
| 配置量 | 集中一张表，动作在点上挂 | Alarm 数=任务数，散 |
| 灵活动态性 | 运行中较少动态调整 | 可随时 SetRelAlarm/CancelAlarm，动态增删方便 |
| 典型用途 | BSW 周期 MainFunction 派发、 runnable 的周期调度 | 看门狗喂狗、超时计时、一次性延时 |
| 工程直觉 | 周期性"正事"用 ST | 计时器类"杂事"用 Alarm |

一句话：**ST 管"节奏"，Alarm 管"计时"**。别用一堆 Alarm 拼出 5/10/20ms 周期体系——相位漂移和配置爆炸都会来找你。

### expiry point 与 Task/Event 的联动

expiry point 放动作，动作把 Os 对象唤醒，被唤醒的 Task 里再跑 SchM 派发出来的各模块 MainFunction：

```
expiry point（10ms 点）
  → SetEvent(TaskEt_10ms, Ev_10ms)
      → TaskEt_10ms 被置位等待→转为就绪→（优先级足够时）抢占运行
          → OsTaskExecution 体内依次调用：
             SchM_Com_MainFunctionRx/Tx()、CanSM_MainFunction()、...（按 SchM 生成的顺序）
```

两种动作的选择：任务平时阻塞在 `WaitEvent` 上时用 **SetEvent**（省 CPU，周期任务的教科书姿势）；任务本身就是"到点全跑一遍"且无其他等待点，可用 **ActivateTask**（简单但注意 activation 排队上限）。BswM/EcuM 这类非严格周期的，则常直接由各自 MainFunction 链处理。

### 同步：隐式/显式、GLOBAL/LOCAL（一句话级）

ScheduleTable 可以与一个"同步源计数器"对齐，用于跨表/跨核/与网络时间对拍：

- **隐式同步（EXPLICIT=否）**：表不主动追同步源，只保证在同步源的窗口内推进——开销小，适合"大致同拍即可"；
- **显式同步（EXPLICIT=是）**：Os 主动拉伸/压缩表的推进速度去追同步源，分 **GLOBAL**（表在同步源的整个周期内对齐）与 **LOCAL**（只在每个匹配点附近局部调整）两种精度策略；
- 工程直觉：单 ECU 内部周期调度一般**不同步**（不同步=不折腾）；需要同步的场景典型是 FlexRay 通信（表与 FR 通信周期对拍）和跨核/跨 ECU 时间敏感的分布式功能。

## 详解

### 配置一瞥（tresos/Os 容器直觉）

```
Os
├─ OsCounter（表针：绑硬件定时器，定 ticks-per-base）
├─ OsScheduleTable
│  ├─ OsScheduleTableDuration / OsScheduleTableRepeating(ONESHOT|REPEATING)
│  ├─ OsScheduleTableCounterRef → OsCounter
│  └─ OsScheduleTableExpPoint × N
│     ├─ OsScheduleTblExpPointOffset（在表上的 tick 位置）
│     └─ OsScheduleTblExpPointAction（ActivateTask / SetEvent ...）
└─ OsTask（TaskEt_10ms： prio、stack、activation、等待的事件）
```

读配置先看三处：表挂哪个 counter、duration 与各 expiry point 偏移（算出各任务周期与相位）、动作指向哪个 Task/Event（对照 [容器与参数](../方法论与ARXML/02-容器与参数.md) 的 def-ref 知识即可裸读）。

### 常见排布模板（拿走即用）

- 单表小系统：`SchTbl_10ms`，点上挂 SetEvent(10ms) 与 ActivateTask(5ms 的点两个)——够跑 Com/CanSM/NvM 全家；
- 多周期分层：5ms 表 + 20ms 表 + 100ms 表各自独立（counter 共用），语义比一张 100ms 大表直白，团队评审友好——两种都合法，项目内统一即可；
- 启动时机：表由 `StartScheduleTableAbs`（对齐绝对 tick）启动，调用点常在 EcuM 启动任务或 BswM 规则里——评审时确认"谁在什么模式启动了表"。

## 配置层/工程关联

- tresos 的 Os 插件里配 counter/task/schedule table；SchM 的 `SchM_<Mod>_MainFunction` 挂载其实由各模块 SchM 配置（见 [Runnable到Task映射](02-Runnable到Task映射.md)）与 Os 任务体共同决定；
- 抖动排查抓手：counter 的 tick 粒度决定理论抖动下限；任务优先级与同 Task 内 MainFunction 顺序决定实际抖动——测量用 OS trace（如 tresos 的 OS trace / Infineon MCDS）而不是 printf；
- 多核（TC377 三核）注意：ScheduleTable 属于核内 Os 实例，跨核各有各的表；跨核同拍要么靠主核广播同步（SpinLock/IOC 传节拍），要么上全局时间（StbM/GPT）；
- 与 EcuM/BswM 的关系：睡眠流程前通常 `StopScheduleTable`，唤醒后重新启动——忘了停表是"睡不下去"的经典原因（表在跑，Os 不允许休眠）。

## 易错点与陷阱

1. **duration 不是任务周期**：duration 是表长（绕回周期），任务周期由 expiry point 的偏移差决定——把 duration 配成 5ms 却想要 10ms 任务，表绕两圈才触发一次该点是不行的（点只配在 10ms 处时一周期只出现一次）。
2. **expiry point 偏移超 duration**：点的 offset 必须 < duration，配置校验会拦，但手改 arxml 时容易漏（校验习惯见 [04-diff-review技巧](../方法论与ARXML/04-diff-review技巧.md)）。
3. **SetEvent 给了从不 WaitEvent 的任务**：事件堆着不消费（EXTENDED 任务才可用事件，BASIC 任务只能 ActivateTask），周期一长事件位语义混乱。
4. **一张表塞满所有动作导致某点过载**：一个 expiry point 挂太多动作→该点触发风暴，后面动作被推迟；应把重活按相位摊到不同点上。
5. **忘记 StopScheduleTable 就想休眠**：Os 活动未停，EcuM 的睡眠校验过不去，卡在 PrepareSleep——排查"睡不下去"先看表与报警器是否停干净。
6. **counter 粒度配错**：tick 太粗（如 1ms）想要 200us 周期，表点摆不出来；太细又吃中断——粒度按最小周期的 1/5~1/10 取。

## 面试高频题

1. ScheduleTable 与 Alarm 的区别？什么时候选哪个？
   答：ST 是时间轴上摆好 expiry point 的一张节目单，多周期任务共表、相位显式可控；Alarm 是独立闹钟，各自到点各自响、可动态增删。周期性"正事"（BSW MainFunction 派发、runnable 周期调度）用 ST；计时器类"杂事"（喂狗、超时、一次性延时）用 Alarm。
2. 一个 expiry point 能做什么？SetEvent 与 ActivateTask 两种动作怎么选？
   答：到期点可配 ActivateTask、SetEvent（或回调/增计数器）。任务平时阻塞在 WaitEvent 上等周期唤醒的用 SetEvent（省 CPU，周期任务教科书姿势）；任务"到点全跑一遍"且无等待点可用 ActivateTask（注意 activation 排队上限与 BASIC/EXTENDED 任务限制——BASIC 任务只能 ActivateTask）。
3. duration、expiry point offset、counter 三者什么关系？如何用一张表同时调度 5ms 和 20ms 任务？
   答：counter 是驱动表的"表针"（绑硬件定时器，tick 粒度决定抖动下限）；duration 是表长（绕回周期），offset 是点在表上的 tick 位置（必须 < duration），任务周期由点的偏移差决定。5ms+20ms 共表：duration 取最小公倍数 20ms，5ms 任务的点摆 0/5/10/15ms 四处、20ms 任务摆在 20ms（或 0）处，相位即摆位。
4. ScheduleTable 的显式同步是什么？什么场景才需要（FlexRay/跨核同拍）？
   答：显式同步是 Os 主动拉伸/压缩表推进速度去追同步源计数器（分 GLOBAL 全周期对齐与 LOCAL 局部微调两种精度）。单 ECU 内部周期调度一般不同步；需要与 FlexRay 通信周期对拍、跨核/跨 ECU 时间敏感的分布式功能时才开。
