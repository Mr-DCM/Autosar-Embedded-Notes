# 02-规则配置

> 一句话定位：把 BswM 规则拆成"条件列表 + 逻辑表达式 + 动作列表"三段来读，分清 IMMEDIATE 与 DEFERRED 两种执行时机，再走查三个工程实例——从此看别人的规则表不再迷路。
> 等级：L2 ｜ 前置：[01-模式仲裁](01-模式仲裁.md)

## 原理

### 一条规则的解剖

```plantuml
@startuml
title 规则解剖：以"KL15 OFF 且总线静默→睡眠准备"为例
skinparam defaultFontName "Microsoft YaHei"
package "BswMRule_PrepSleep" {
  [Condition C1\nECUM_MODE == POST_RUN] as C1
  [Condition C2\nCANSM_MODE == SILENT] as C2
  [Condition C3\nNVM_PENDING == FALSE] as C3
  [LogicalExpression\nC1 AND C2 AND C3] as LE
  [ActionList_True\n停调度表→NvM_WriteAll→ComM 睡眠请求→EcuM 请求 SLEEP] as AT
  [ActionList_False\n（恢复运行态动作，可选）] as AF
}
C1 --> LE
C2 --> LE
C3 --> LE
LE --> AT : 表达式为真（且与上次记录不同）
LE --> AF : 表达式为假（若配置）
note bottom of AT : 动作顺序即列表顺序\n逐条执行，无回滚
end note
@enduml
```

三段各司其职：
- **条件列表（ModeCondition）**：一条 = "某模式源 == 某期望值"，是原子传感器；
- **逻辑表达式（LogicalExpression）**：条件的 AND/OR/NOT 组合，注意 AUTOSAR 表达式一般两级（条件层+表达式层），不写嵌套长链；
- **动作列表（ActionList）**：真/假各一列（假列可选），按序执行的动作集。

### IMMEDIATE vs DEFERRED：执行时机

| 属性 | IMMEDIATE 规则 | DEFERRED（默认）规则 |
|---|---|---|
| 触发 | 模式源**一变**立即在事件上下文评估执行 | 等下一轮 BswM_MainFunction 周期评估 |
| 延迟 | 微秒级 | 最多一个 MainFunction 周期（10~20ms） |
| 上下文 | 调用者上下文（可能在 ISR/模块函数里） | BswM 任务上下文，安全 |
| 适用 | 需即时反应：BusOff 应急、关键降级 | 绝大多数模式切换 |
| 风险 | 动作跑在别人上下文里，必须极短且可重入 | 慢半拍 |

工程直觉：**默认全 DEFERRED，只给"慢半拍会出事"的规则开 IMMEDIATE**，且 IMMEDIATE 动作只做轻量切换（置模式量/开关调度表），重活留给周期规则接力。

## 详解：三条典型规则走查

**例一：CanSM BusOff → 切通讯降级模式**

- 条件：`CANSM_BUSOFF == BUSOFF`（指示源，CanSM 上报事实）；
- 表达式：单条件直通；
- 动作（真）：停发送调度表 / 置内部模式 `COMM_DEGRADED` / 通知应用 SWC 降级（RTE 模式切换）；
- 动作（假）：`CANSM_BUSOFF == NORMAL` 恢复发送调度表、清降级模式；
- 要点：BusOff 恢复由 CanSM 自身重试，BswM 只做**策略层的降级与恢复联动**，不去碰底层恢复。

**例二：NvM Job 完成 → 发事件放行功能**

- 条件：`NVM_JOBRESULT == ALL_DONE`（指示）AND `内部模式 INIT_DONE == FALSE`；
- 动作（真）：置 `INIT_DONE=TRUE` / 起应用调度表 / RTE 通知 SWC"数据就绪"；
- 要点：典型"规则链"——本条动作置的内部模式量，被后续"开业务功能"规则引用；保证 NvM 没落盘前业务不开门。

**例三：KL15 OFF → 请求睡眠准备**

- 条件：`KL15 == OFF`（引脚指示）AND `DIAG_ACTIVE == FALSE` AND `COMM_REQ == NONE`；
- 动作（真）：ComM 释放网络请求→等总线静默（另一条规则接力）→NvM_WriteAll→EcuM 请求 SLEEP；
- 要点：**一整条睡眠策略拆成 2~3 条规则接力**（KL15 裁决→静默确认→执行睡眠），而不是一条巨型规则；每条规则单一职责，评审和排障都容易。

## 配置层：规则配置表模板（评审用三列法）

| 规则名 | 条件（表达式） | 动作（真 / 假） |
|---|---|---|
| Rule_CommDegraded | CANSM_BUSOFF==BUSOFF | 真：停 Tx 调度表、置 DEGRADED、RTE 通知；假：恢复 Tx 调度表 |
| Rule_InitDone | NVM_RESULT==ALL_DONE AND INIT_DONE==FALSE | 真：置 INIT_DONE、起 App 调度表；假：— |
| Rule_KL15Off | KL15==OFF AND DIAG==FALSE AND COMM_REQ==NONE | 真：ComM 释放、置 SLEEP_PENDING；假：撤销 SLEEP_PENDING |
| Rule_GoSLeep | SLEEP_PENDING==TRUE AND CANSM==SILENT AND NVM_DONE==TRUE | 真：EcuM 请求 SLEEP；假：— |

| 配置项 | 含义 | 典型值 | 易错点 |
|---|---|---|---|
| BswMRule*ModeInstance/触发 | 规则绑定表达式+动作列表 | 每规则一表达式 | 真假动作列表配反 |
| BswMRule*ImpliedMode | 规则隐含模式（置内部量） | INIT_DONE 等 | 隐含量被两条规则互斥写，打架 |
| BswMActionList（顺序） | 动作执行序 | 先发令后通知 | 先通知 SWC 后开总线：SWC 立刻发帧踩空 |
| BswMAction*RteSwitch/RteSend | RTE 模式切换/数据发送 | 通知类动作放列表尾部 | RTE 动作放在排他区请求前，被阻塞 |
| BswMRequestPort 初始值 | 各模式源初始值 | 与上电实际态一致 | 全默认 0：首轮规则全不触发 |
| 排他区（ExclusiveArea）请求动作 | 切换时保护共享配置 | CanSM 切换场景用 | 忘申请排他区：切换中数据竞争 |

## 易错点与陷阱

1. **假分支不配**：规则进入时动作齐全、退出时没人恢复（调度表停了不再起、降级模式清不掉）；评审表强制"真/假两列都过一遍"。
2. **IMMEDIATE 动作干重活**：在 CanSM 调用上下文里跑 NvM 写类长动作，拖垮上层实时性甚至死锁；IMMEDIATE 只置标志，重活交周期规则。
3. **一条规则塞一整个流程**：条件七八个、动作十几条，任何一环不满足全盘不动，排障无从下手；按"裁决→确认→执行"拆链。
4. **动作顺序错**：先 RTE 通知 SWC 再开底层（SWC 立刻发帧而总线未开）；动作列表排序原则：先机制后通知。
5. **规则之间写同一隐含模式量**：两条规则对同一内部模式置不同值且触发次序不定，出现偶发跳变；一个内部量只允许一个写者。
6. **忘配初始值**：首轮评估所有条件取默认，正常流程"看起来配置都对就是不动"；把"上电第一轮应该触发哪些规则"写进集成测试用例。

## 面试高频题

- **Q：一条 BswM 规则由哪几部分构成？**
  A：条件列表（模式源==期望值的原子条件）→ 逻辑表达式（AND/OR 组合）→ 真/假两个动作列表（按序执行的动作集）；BswM 在表达结果变化时执行对应列表。
- **Q：IMMEDIATE 和 DEFERRED 规则的区别与选择？**
  A：IMMEDIATE 在模式源变化的事件上下文立即评估执行（微秒级、上下文受限），DEFERRED 等下一轮 MainFunction（周期级、任务上下文）；默认 DEFERRED，只给需要即时反应的关键切换开 IMMEDIATE 且动作要轻。
- **Q：举一个 BusOff 相关的规则设计。**
  A：条件=CANSM 指示 BUSOFF；真动作：停发送调度表+置降级内部模式+RTE 通知应用；假动作：恢复正常；底层 BusOff 恢复由 CanSM 自己做，BswM 只管策略联动。
- **Q：怎么用 BswM 实现"NvM 全部写完才允许睡眠"？**
  A：两条规则接力：睡眠裁决规则（KL15/诊断/通讯条件）置 SLEEP_PENDING；执行规则在 SLEEP_PENDING 且 CANSM==SILENT 且 NVM==ALL_DONE 时才调 EcuM 请求 SLEEP——把"意图"和"条件齐备"拆开。
