# 03-唤醒源

> 一句话定位：睡眠不是关机——ECU 靠一张"唤醒源清单+限时校验"的机制决定要不要真醒：总线上真叫我就起，风吹草动（假醒）就接着睡。
> 等级：L2 ｜ 前置：[02-上下电时序](02-上下电时序.md)

## 原理

### 唤醒源类型

| 唤醒源 | 硬件信号 | 触发条件 | 典型用途 |
|---|---|---|---|
| CAN 总线唤醒 | CAN 收发器 RXD/WAKE | 总线出现显性位（报文沿） | 网络管理唤醒、诊断唤醒 |
| LIN 总线唤醒 | LIN 收发器 | 检测到 break（持续显性） | 主节点唤醒从节点 |
| 局部唤醒引脚 | GPIO 输入沿 | 开关/点火信号电平变化 | KL15、按键、充电枪插入 |
| RTC 定时唤醒 | RTC 中断 | 定时到期 | 周期自检、均衡电池、防盗扫描 |
| （扩展）以太网唤醒 | PHY WoL/魔法帧 | 特定帧匹配 | DoIP 诊断唤醒 |

共性：**睡眠前必须把唤醒源的中断/检测使能打开**，进低功耗后靠它把 MCU 拽起来——这是 SLEEP 能"醒"的唯一保证。

### 唤醒事件处理流与假醒

```plantuml
@startuml
title 唤醒校验：真醒与假醒的分岔
skinparam defaultFontName "Microsoft YaHei"
participant "硬件" as HW
participant "EcuM" as EM
participant "CanIf/CanTrcv" as TRCV
HW -> EM : 唤醒事件（CAN 显性沿/引脚沿）
EM -> EM : EcuM_SetWakeupEvent(source)\n离开 Halt，恢复时钟
EM -> TRCV : 检查唤醒源，启动验证定时器
alt 验证窗口内收到有效 NM 报文
  TRCV -> EM : 校验通过（EcuM_ValidateWakeupEvent）
  EM -> EM : 按"有效唤醒"走启动序列\n（NM 起网→BswM 裁决→RUN）
else 窗口超时仍无有效报文
  EM -> EM : 判定假醒（WakeUpValidationTimeout）
  EM -> EM : 复位唤醒标志、清理现场
  EM -> EM : EcuM_GoSleep（回 Halt 继续睡）
end
note over EM : 为什么必须有校验：\nCAN 总线上的毛刺/非 NM 报文\n也会产生显性位——\n不校验就会"整网被一帧噪声叫醒"
end note
@enduml
```

**假醒（spurious wakeup）的定义**：唤醒事件触发了，但验证不通过（窗口内没有合法理由继续运行）。处理原则就一条：**清理干净，回去睡**——耗电指标就看这段代码写得干不干净。

### 超时验证的定时从哪来

验证窗口 = "唤醒后到合法证据到达"的最坏时间，工程上按两条算：
- CAN 唤醒：本节点 NM 报文周期 + 网络起网时间，一般 **500ms~2s**；
- 引脚唤醒（KL15/开关）：信号本身即证据，窗口可极短甚至直接通过；
- RTC：定时器就是合法理由，无需窗口。
窗口配太短：真唤醒被判假醒，整车"叫不醒"；配太长：每次假醒都白耗几百毫秒的电。

## 详解

**一次 CAN 唤醒的完整链路（睡眠视角）**：Halt 中收发器进待机仍盯着总线 → 显性位 → 收发器拉 RXD/INT 唤醒 MCU → EcuM 离开 Halt、恢复时钟 → 查唤醒源是 CAN → 起总线（CanTrcv_SetOpMode NORMAL、CanIf 起控制器）→ 验证窗口等 NM 报文 → 收到 → EcuM_ValidateWakeupEvent → 走启动（等效上电但跳过部分初始化）→ BswM 仲裁进 RUN。

**和 NM 的配合**（谁叫醒谁）：网络管理中"本网段该不该醒"由 NM 状态机说了算（收到 NM 报文/自身有网络请求）；EcuM 的校验本质上是在等 NM 给证据。两个机制的衔接详见 [05 区-睡眠与假醒](../../../../05-汽车网络通讯/2-L2进阶/网络管理/03-睡眠与假醒.md)，收发器级的唤醒电路见 [05 区-唤醒与休眠](../../../../05-汽车网络通讯/1-L1基础/CAN/收发器与物理层/02-唤醒与休眠.md)。

**排障定位**："睡不醒"查三件事：唤醒源睡眠前有没有使能（漏使能=真睡死）、Halt 后时钟/引脚配置是否丢了、验证窗口是否太短；"假醒耗电"查：回睡路径是否清理了中断标志与总线状态、窗口内有没有做多余初始化。

## 配置层

| 配置项 | 含义 | 典型值 | 易错点 |
|---|---|---|---|
| EcuMWakeupSource*WakeupSourceId | 唤醒源编号 | 按位编号（CAN=0x10 类平台值） | 编号与 CanIf/Pmc 侧不对齐，事件对不上号 |
| EcuMWakeupSource*WakeupSourceValidationTimeout | 验证超时 | CAN 500ms~2s | 太短真醒误判、太长假醒耗电 |
| EcuMWakeupSource*WakeupSourceConfiguration | 绑定硬件通道（引脚/收发器） | CAN 收发器唤醒引脚 | 引脚没配边沿检测，事件进不来 |
| SleepMode 使能的唤醒源集 | Halt 前打开哪些源 | CAN+KL15+RTC | 漏开=对应场景睡死 |
| （Flexible）用户校验代码 | 自定义验证逻辑 | 按 NM 周期定窗口 | Flexible 下配了超时没人执行，形同虚设 |
| EcuM_SetWakeupEvent 通知 | 事件上报路径 | EcuM→BswM 模式仲裁 | 校验结果没通知 BswM，策略层不知情 |

## 易错点与陷阱

1. **睡眠前没使能唤醒源**：Halt 后没有任何中断能拽醒 MCU——真"睡死"，只能断电；SLEEP 序列的使能清单要 code review 逐源核对。
2. **验证窗口拍脑袋配**：不按 NM 周期+起网时间算，配 100ms——网络还没来得及发 NM 报文就被判假醒回睡，整车"叫不醒"；窗口=最坏合法证据时间+裕量。
3. **假醒回睡不清现场**：回睡前不清唤醒标志/不关刚起的一半外设——中断风暴或耗电超标；回睡路径要"完整撤销唤醒路径上做过的每一步"。
4. **唤醒源与 NvM/ComM 状态打架**：唤醒校验期间 NvM 还在懒加载、ComM 未就绪就收到报文要求应答——协议超时；启动序列里明确"校验通过后才放行上层"。
5. **引脚唤醒没有消抖**：开关抖动造成连续假醒-回睡循环，电流毛刺+计数器狂涨；引脚类唤醒在验证里加消抖窗口或电平确认。
6. **RTC 唤醒当总线唤醒处理**：RTC 到期是合法理由，还去等 NM 报文——白白等满窗口才起或误判假醒；分类处理，别共用一条校验路径。

## 面试高频题

- **Q：什么是假醒？EcuM 怎么处理？**
  A：唤醒事件发生但验证窗口内无合法证据（如 CAN 上只是毛刺/非 NM 报文）；EcuM 判定验证超时，清理唤醒标志与总线状态后调回睡序列（GoSleep→Halt），保证睡眠电流不超标。
- **Q：CAN 唤醒的验证超时怎么定？**
  A：按"唤醒后到合法 NM 证据的最坏时间"：本网段 NM 报文周期+起网时间+裕量，常见 500ms~2s；引脚/RTC 类证据即时的可直通。
- **Q：唤醒源在什么时机使能？**
  A：进入 SLEEP/Halt 之前——Halt 后 MCU 全靠预使能的唤醒中断拽醒；使能清单在睡眠序列里完成，漏使能等于睡死。
- **Q：唤醒后为什么不能直接 RUN，要走启动序列？**
  A：Halt 前总线、外设、调度都已下电/停止，唤醒后必须恢复时钟、起总线、校验有效性，再交给 BswM 仲裁决定进什么模式——直接 RUN 会跳过校验与协调，造成整网状态不一致。
