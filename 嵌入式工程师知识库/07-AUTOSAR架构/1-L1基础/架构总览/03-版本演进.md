# 03-版本演进

> 一句话定位：一张时间线看清 AUTOSAR 从 R4.0 奠基到 R19-11 新命名再到 R24-11 的关键变化，回答"我手上这个项目到底用哪一版、去哪儿查、版本差异影响我什么"。
> 等级：L1→L2 ｜ 前置：[01-分层架构](01-分层架构.md)

读分层架构时你接触的是"空间轴"（五层）；本篇补"时间轴"——同一张五层图，R4.2 和 R24-11 画出来内容并不相同。版本感是工程师的暗语：一听"我们锁 R4.2.2"就知道配置风格、模块包结构、SWS 行文长什么样。

## 原理

### 版本时间线一览

| 版本 | 年份 | 关键变化一句话 | 工程界地位 |
|---|---|---|---|
| R3.x | 2005-2008 | 前四代体系，旧式分层与 OSEK 集成 | 已退役，仅老平台可见 |
| R4.0 | 2009 | **奠基版**：确立现行分层/RTE/BSW 概念，引入多核、EcuM 重构、FlexRay 增强 | 现代架构起点 |
| R4.1 | 2013-2014 | 车辆以太网初入（SOME/IP）、Dlt/加密栈扩充 | 过渡 |
| R4.2 | 2015 | **主流工程基线**：以太网/SOME/IP 成熟、SecOC、内存栈完善 | 大量量产平台选此 |
| R4.2.2 | 2016-2017 | R4.2 的修订版，bug 修复+澄清 | **OEM 最常见的锁定版**（"4.2.2 工程"遍地） |
| R4.3 | 2016-2017 | 全局时间同步（GPTP/StbM）增强、CAN FD 全面支持、多核扩展 | 新平台起点 |
| R4.4 | 2018 | 模块细化修订、诊断增强（DCM/DEM 扩容）、以太网强化 | 部分量产 |
| R17-10 | 2017-2018 | 旧命名的最后一代（Adaptive 起步于 17-03/17-10） | 命名分水岭前夜 |
| R19-11 | 2019-11 | **新命名规则起点**（年-月制）；模块按 Classic/Adaptive/Methodology 重新打包分组 | 现行文档体系开端 |
| R20-11 | 2020-11 | SDV 议题入场、RTE/E2E 持续演进、持续集成方法论 | |
| R21-11 | 2021-11 | 功能安全/信息安全联动增强、以太网新品类 | |
| R22-11 | 2022-11 | SOVD（面向服务诊断）起步、AP 成熟化 | |
| R23-11 | 2023-11 | 持续完善：AP 功能簇扩充、工具链互操作改进 | |
| R24-11 | 2024-11 | SDV/平台化持续演进 | 最新年度版 |

三条主线帮你记：**R4.0 定骨架 → R4.2 定主流工程实践（以太网+SecOC）→ R19-11 换命名并重打包文档**。2017 年起 Adaptive 平台并行发展（17-03 首版起步），此后每版都同时发布 CP+AP。

### 命名规则的变化

- 旧制：`R主版本.次版本`（R4.2），修订以 `R4.2.2` 表示；
- 新制：`R年年-月月`（R19-11、R20-11），一年一版（11 月发布），不再有"次版本"，修订体现在文档自身的 Revision History。

注意：R4.2.2 的".2"是**修订（revision）不是新版本**——它是 R4.2 的勘误与澄清集，但因被大量 OEM 指定为交付基线，工程口语里像独立版本一样被提及。

## 详解

### 如何知道自己项目用哪一版

四条路径，由近及远：

1. **看 tresos/工具**：EB tresos 安装目录下的 base 插件各自带版本（如 `Os` 插件的 4.2.2、`Com` 的 4.2.2）；工具 About 页也标明支持的规范版；
2. **看 SWS 文档头**：每份 SWS 首页标注所实现的 AUTOSAR 版本与修订——这是"以文档为准"的权威口径；
3. **看供应商交付物**：MCAL 包 Release Note、BSW 交付的 arxml 里 `AUTOSAR xsd version` 与模块版本号（如 `CanIf 4.2.2`）；
4. **看 ARXML/XSD 版本声明**：文件头 `xmlns="http://autosar.org/schema/r4.0"` 的 schema 版本（r4.0 schema 贯穿 R4.x 时代）与各模块 `DEFINITION-REF` 指向的定义版本。

### 版本差异对配置的直觉影响

| 差异类别 | 直觉 |
|---|---|
| 参数增删 | 同一容器在新版多出/少了参数——旧 ARXML 导入新工具会报"未知参数"或默默丢项 |
| def-ref 路径变化 | R19-11 重打包后部分定义路径调整，跨版本迁移配置要核对 DEFINITION-REF |
| 模块边界调整 | 个别功能在版本间换了模块归属（如收发器管理相关），配置位置随之搬家 |
| XSD schema | R4.x 共用 r4.0 schema；工具按 schema+模块版本双保险校验 |
| 文档组织 | R19-11 起文档库按 Classic/Adaptive/Methodology 分组下载，旧习惯找 PDF 的路径变了 |

一句话：**版本决定"配置语言里的方言"**——跨版本搬配置不是复制粘贴，是带着 diff 审查的迁移（怎么做见 [04-diff-review技巧](../../2-L2进阶/方法论与ARXML/04-diff-review技巧.md)）。

### 两类工程速认：R4.2.2 味 vs R19-11+ 味

拿到陌生工程，五分钟"闻"出版本段位的观察点：

| 观察点 | 典型 R4.2.2 工程 | 典型 R19-11+ 工程 |
|---|---|---|
| SWS 文档头 | 标 R4.2 REV 2，文档名不带平台前缀 | 按 Classic/Adaptive 分组发布，页面结构不同 |
| BSW 模块版本号 | 插件版本常见 4.2.2 字样 | 模块版本带新版本段，工具界面风格也换代 |
| ARXML schema | `schema/r4.0` 命名空间 | 新版本 schema 声明，部分 def 路径重组 |
| 以太网/多核特性 | CAN FD 可用、SOME/IP 基础可用 | 特性面更全（GPTP/SOVD/AP 互操作） |
| 工具链 | tresos/DaVinci 较旧版本组合 | 新版 tresos、ARTOP 生态、CI 工具链更常见 |

速认的意义不是炫耀眼力，是**降低误判成本**：把 R4.2.2 工程按 R19-11 的经验去改，参数名对不上还只是小事，静默丢配置才是大坑。

### 版本三问自测

| 问题 | 一句话答案 |
|---|---|
| OEM 说"锁 R4.2.2"，锁的到底是什么？ | 锁的是规范修订基线：SWS 条目口径 + BSWMD 定义 + 交付物按 R4.2 REV 2 验收 |
| 项目中途想升到 R19-11，第一件事做什么？ | 盘点模块清单与三方件（MCAL/OS/工具）兼容矩阵，再做配置迁移 PoC + 全量 diff |
| AP 的版本和 CP 的版本是一回事吗？ | 并行两套：同一发布日（如 R19-11）同时出 CP 与 AP 包，但内容各自独立演进 |

## 配置层/工程关联

- 新项目选版直觉：OEM 指定什么就锁什么；自研平台无强约束时，"R4.2.2（成熟稳定）"与"R19-11+（新文档体系、以太网/多核特性全）"是两个典型落点；
- 三方件版本对齐：MCAL（Infineon/NXP）、OS（如 EB tresos 的 OS）、工具版本三者要构成"经过验证的组合"（vendor 的 compatibility matrix），别自行混搭；
- 版本信息落盘位置：工程根的 `*.arxml` 头部 schema 声明、每个模块配置的 `DEFINITION-REF` 后缀版本、以及 Admin Data 里的工具版本——这些是配置 diff 时最先看的三处。

## 易错点与陷阱

1. **把 R4.2.2 说成"R4.2 版本之后的 R4.3 之前那个版本"**：它是 R4.2 的**修订**，不是独立大版本；面试与文档评审里要叫准"修订版"。
2. **以为 R19-11 是 R4.5**：新命名不是数值延续，是从"主次版本制"切到"年月制"，两者没有 R4.x→R5 的关系。
3. **只看 schema 版本判断工程版本**：R4.0~R4.4 的 ARXML 都标 `schema r4.0`，真正的版本信号在模块 DEFINITION-REF 与交付物清单里。
4. **跨版本直接导 ARXML**：参数名/容器路径在版本间有微调，导入"成功"≠语义等价，必须做 diff review 与校验报告核对。
5. **新版本一定更好**：新版特性多但三方件（尤其 MCAL/OS）生态跟进有延迟，量产项目常"锁旧版"，跟新要算工具链成本。

## 面试高频题

1. 你们项目基于哪个 AUTOSAR 版本？R4.2 与 R4.2.2 的关系是什么？
   答：R4.2 是 2015 年的主流工程基线（以太网/SOME/IP 成熟、SecOC），R4.2.2 是它的**修订版**（勘误+澄清），不是独立新版本——因被大量 OEM 指定为交付基线而像独立版本一样被口语化提及。回答时先报项目锁定版（如 R4.2.2），再点明修订关系。
2. R19-11 相比 R4.x 在文档与命名上有什么变化？为什么换命名？
   答：从"主次版本制"（R4.2）切换为"年月制"（R19-11，一年一版 11 月发布），文档库按 Classic/Adaptive/Methodology 重新分组打包，部分模块定义路径也重组。换命名是为了并行的 CP/AP 双平台统一发布节奏、让版本与时间线直观对应，不是 R4.x 的数值延续。
3. 怎么确认一个交付的 BSW 包实现了哪个版本的规范？
   答：四处证据由权威到辅助：SWS/交付文档头标注的规范版本与修订、模块配置里 DEFINITION-REF 指向的定义版本（如 CanIf 4.2.2）、MCAL/OS Release Note、ARXML 头部 schema 声明（注意 r4.0 schema 贯穿 R4.x，不能只看它）。
4. 把 R4.2 的配置迁到 R19-11 工具上，可能遇到什么问题？怎么做安全迁移？
   答：参数增删、def-ref 路径变化、模块边界调整都会导致"未知参数"报错或静默丢项，导入成功≠语义等价。安全迁移：先盘点模块与三方件兼容矩阵，做迁移 PoC，再全量配置 diff review + 校验报告逐项核对。
