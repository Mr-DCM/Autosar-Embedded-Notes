# DSPR/PSPR 与寻址

> 一句话定位：TC377 每个核都有独占的紧耦合本地内存 DSPR/PSPR——数据放对位置零等待、放错位置绕远路，这是多核性能与确定性优化的第一课。
> 等级：L3 ｜ 前置：[02-CSA上下文机制](02-CSA上下文机制.md)

## 太长不看

- **人话直觉**：DSPR 私人仓库，PSPR 私人快道，LMU 公共区。
- **本篇解决**：变量和函数放哪个内存才不"绕远路"？跨核共享放哪？
- **赶时间记住 3 条**：
  1. DSPR/核私有放栈与局部变量；
  2. PSPR 放关键代码零等待；
  3. 跨核共享走 LMU。

## 原理

### 本地内存架构：每核的"私人高速口袋"

TriCore 三十二位统一编址，但物理内存与核的"亲疏关系"差异巨大。每个核贴身一套（容量查 DS）：

| 资源 | 性质 | 典型放什么 |
|---|---|---|
| DSPR（Data Scratchpad RAM，数据暂存 RAM） | 紧耦合、零等待、**核独占** | 本核栈、本核 CSA 池、热点变量、通信缓冲 |
| PSPR（Program Scratchpad RAM，程序暂存 RAM） | 紧耦合、零等待、可执行、核独占 | 热点函数、对时序敏感的 ISR |
| D CACHE | 缓存远端数据（透明） | — |
| PCACHE | 缓存 PFlash 取指（透明） | — |

DSPR/PSPR 背后的存储器实例在手册里常称 DSRAM/PSRAM（命名以 DS 为准）。要点是**"scratchpad 不是 cache"**：没有硬件动态搬入搬出，放什么完全由软件（链接脚本 + MemMap）显式决定，换来的是**访问延迟恒定**——车规确定性场景要的就是"每次都一样快"。

### 访问代价金字塔：放对位置省的是真金白银

```text
        快/确定                                    慢/受扰
┌──────────────────┐
│ 本核 DSPR/PSPR   │  零等待，独占带宽 —— 热点数据/代码的家
├──────────────────┤
│ 本核 D CACHE 命中 │  近零等待，但首访/替换有填充延迟
├──────────────────┤
│ 共享 LMU/DLMU     │  经系统互联（SRI），延迟高一档，带宽三核共享
├──────────────────┤
│ PFlash（经PCACHE）│  取指有等待状态，靠 PCACHE 摊平
├──────────────────┤
│ 远端核的 DSPR     │  跨核访问：绕 SRI 到别的核门口，延迟最高，
│                  │  还可能与对方本地流量争用 —— 能不去就不去
└──────────────────┘
```

**跨核远端访问的三个代价**：①延迟——绕系统互联，比本核 DSPR 慢数倍量级（具体倍数随实现，测为准）；②带宽——互联是三核共享的高速公路，远端流量互相挤占；③确定性——延迟受当时互联负载影响，抖动不可控。最阴险的是：**C 代码里远端指针与本核指针写法完全一样，编译器不报错，只有性能默默变差**——多核优化的第一排查项。

### 为什么热点数据要放各自 DSPR（与 MemMap 联动）

多核工程（如 AUTOSAR：OS 与分区按核划分）把每个核频繁读写的数据放进它自己的 DSPR，是教科书级操作。AUTOSAR 里的落地链路：

```text
C 源码 #include MemMap.h
  → #define START_SEC_XXX（选择内存段）
  → 编译器把变量放进指定 section
  → 链接脚本把 section 映射到 某核 DSPR 地址区
  → 该编译单元的数据从此零等待访问
```

典型受益者：本核中断计数器、滤波器状态、通信 RX 缓冲、OS 本核就绪队列。机制细节（`#define START_SEC_NO_INIT` 等宏如何变成 section）在 [AUTOSAR MemMap 机制](../../../01-编程语言/2-L2进阶/内存管理/05-AUTOSAR-MemMap机制.md)展开；跨核共享数据才放 LMU/DLMU，并配核间同步手段（见 [多核架构](../多核架构/README.md)）。

### 代码放 PSPR：收益与预算的权衡

把热点函数放 PSPR 执行：

- **收益**：取指零等待、不受 PFlash 等待状态与互联仲裁影响——中断延迟抖动显著收窄；高频小函数（CRC、滤波、协议栈热路径）收益最大。
- **代价**：①PSPR 是稀缺 RAM 预算（KB 量级，查 DS），放代码就挤占别的；②需要搬运——与 .data 同机制：链接器把 LMA（Flash 镜像）记入拷贝表，startup 启动时搬到 PSPR（VMA），机制见 [读 startup 汇编](../../../01-编程语言/2-L2进阶/汇编基础/TriCore汇编/03-读startup汇编.md)；③调试时符号/断点要认 VMA，工具链都支持但要知道这层。
- **取舍手感**：先放 PFlash 靠 PCACHE，实测抖动/负载不达标，再把最热的几个函数搬 PSPR——一上来就全搬是 RAM 预算灾难。

### 地址空间分段：统一编址、分区而治

TriCore 32 位地址空间按用途分段（**具体区间一律查 DS 的 Memory Map 章节，以下只记概念**）：

| 分区（概念） | 放什么 | 访问特点 |
|---|---|---|
| PFlash 代码区（cached/uncached 双视图） | 程序/常量 | cached 视图走 PCACHE，uncached 视图直读（地址前缀区分，查 DS） |
| 各核 DSPR/PSPR 区 | 每核私有数据/代码 | 三核各自一段独立基址，零等待 |
| 共享 RAM 区（LMU/DLMU） | 跨核共享数据 | 三核可达，走互联 |
| DFlash 区 | 标定/非易失数据 | 经 Flash 编程接口写 |
| 外设/SFR 区（地址空间高端 0xF 段概念区） | 外设寄存器、CSFR | 查 DS；访问受 IO 特权级约束（见 [03-Trap与中断机制](03-Trap与中断机制.md)） |

## 寄存器与位表

本主题没有"数据表寄存器"，关键是**地址映射事实**，全部以 DS 为唯一权威：每核 DSPR/PSPR 基址与容量、PFlash 双视图前缀、LMU/DLMU 分布、SFR 区范围。工程里先读链接脚本（工具链已把这些区写成符号），再回 DS 对表，不要凭记忆写裸地址。

## 双平台对照

| 维度 | TriCore TC377 | Cortex-M4 | Cortex-M7 |
|---|---|---|---|
| 紧耦合内存 | 每核 DSPR+PSPR（标配，软件显式管理） | 无 TCM（普通 SRAM 经总线矩阵） | 可选 ITCM/DTCM（0 等待） |
| 管理方式 | scratchpad：链接脚本/MemMap 显式放置 | —（M7：链接脚本放 TCM） | 同 M4 |
| 指令缓存 | PCACHE（对软件透明） | 无 cache（Flash 预取/加速器） | 可选 I-Cache |
| 数据缓存 | D CACHE | 无 | 可选 D-Cache |
| 多核内存归属 | 三核各有 DSPR/PSPR + 共享 LMU | 单核，无此问题 | 单核 |
| 确定性卖点 | scratchpad 零等待 + 无一致性问题 | SRAM 快但共享总线 | TCM 同卖点 |
| 经典坑 | 远端 DSPR 访问"语法无感、性能有感" | 总线抢占（SRAM/DMA 竞争） | Cache 一致性（DMA 场景） |

一句话：**TC377 把 M7 的 TCM 思路做成三核标配**，并额外送了一个必须想清楚的问题——"这个数据归哪个核"。

## 代码/实操

### 1. 把变量放进指定核的 DSPR（AUTOSAR 工程，概念骨架）

```c
/* 编译单元属于 CPU2 的代码时，MemMap 指到自定义段： */
#define CPU2_DSPR_VAR_START
#include "MemMap.h"   /* 概念：自定义 section，如映射到 CPU2 的 DSPR 区 */

volatile uint32_t CanRxCounter;      /* 本核高频读写：零等待 */

#define CPU2_DSPR_VAR_STOP
#include "MemMap.h"
/* 真实工程的段名/宏名随工具链与 Os 配置不同；
   核心动作是：MemMap 选段 → 链接脚本定地址 → map 文件验证 */
```

验证三步：map 文件里看变量落点地址是否在目标 DSPR 区间 → 调试器观察访问延迟/断点命中 → 压力工况对比搬移前后抖动。

### 2. 把函数放进 PSPR（链接脚本概念）

```text
链接脚本（概念写法，语法随工具链）：
  .cpu2_pspr_text : VMA = PSPR2 区地址
  { *(.text.cpu2_hot*) } > PSPR2 AT> PFlash   /* 运行在 PSPR2，镜像存 Flash */

startup：拷贝表自动覆盖该段（与 .data 同机制，无需手写代码）
C 侧：函数加 section 属性进 .text.cpu2_hot
```

### 3. 多核数据布局的自查清单

1. 这变量谁读写最频繁？→ 放那个核的 DSPR。
2. 有跨核共享吗？→ 放 LMU/DLMU，加同步（原子/信号量），并评估是否可用消息传递替代共享。
3. ISR 热路径的栈在哪个核的 DSPR？（栈默认就在本核 DSPR，别被链接脚本改去共享区）
4. CSA 池在本核 DSPR 吗？（见 [02-CSA上下文机制](02-CSA上下文机制.md)）

## 易错点与陷阱

1. **跨核访问 DSPR 的"语法无感"**：`cpu2_ptr->field` 与本核指针写法一样、编译运行全对，只有性能和抖动变差——多核性能问题先查数据落点，别先怀疑算法。
2. **scratchpad 当 cache 用**：DSPR 不会自动"缓存热点"，不放进去就没有零等待待遇；以为"变量热了硬件会自己搬"是把 PCACHE 的习性错安在 DSPR 头上。
3. **PSPR 搬运被跳过**：自定义段没进拷贝表（链接脚本 AT> 缺失或 startup 未覆盖该段名），PSPR 里是随机数——执行即跑飞，症状像"偶发死机"。
4. **共享变量不做同步**：放 LMU 只解决"看得见"，不解决"读得完整"——跨核共享仍需原子操作/互斥，32 位对齐读写也不是天然原子的保证（以 UM 内存模型为准）。
5. **栈和 CSA 池被挤到共享区**：改链接脚本时误把某核栈/CSA 挪出 DSPR，所有函数调用与中断都变慢且抖动——性能回退却查不出"哪行代码"的问题。
6. **裸地址硬编码**：DSPR/LMU 基址凭记忆写进代码，换型号/改布局即错；永远用链接符号或 DS 对表。

## 面试高频题

1. **DSPR/PSPR 是什么？和 CACHE 什么区别？**
   答：每核独占的紧耦合零等待内存，DSPR 放数据、PSPR 放可执行代码，内容放什么由软件显式决定（scratchpad）；CACHE 缓存远端内存副本、对软件透明。前者赢确定性，后者赢容量便利。

2. **为什么多核工程要把每核热点数据放各自 DSPR？**
   答：本核 DSPR 零等待且独占带宽；放共享区则跨核绕互联访问——延迟高、带宽共享、抖动不可控，而 C 代码语法上无感。AUTOSAR 工程用 MemMap 选段 + 链接脚本定地址实现"数据跟核走"。

3. **代码放 PSPR 有什么收益和代价？**
   答：收益是取指零等待、不受 PFlash 等待状态与互联仲裁影响，中断延迟抖动收窄；代价是 PSPR 容量小（挤占 RAM 预算）且需 startup 从 Flash 搬运（LMA→VMA）。实践上先靠 PCACHE，实测不够再把最热函数搬 PSPR。

4. **CPU0 访问 CPU2 的 DSPR 会发生什么？**
   答：语法上是普通指针访问（统一编址）；物理上请求绕系统互联到 CPU2 的 DSPR，延迟数倍于本地访问，还要与互联上其他流量争带宽——性能与确定性双重代价，热路径应避免。

5. **TriCore 的 scratchpad 和 Cortex-M7 的 TCM 像在哪、不像在哪？**
   答：像：都是零等待紧耦合内存、都由链接脚本显式放置。不像：TC377 三核各配一套 DSPR+PSPR 是标配且引出"数据归哪个核"的多核问题；M7 单核，TCM 是可选项。另外 TriCore 用 PCACHE/DCACHE 摊平 PFlash/远端访问，M4 则无 cache。

6. **怎么验证一个变量真的被放进了指定核的 DSPR？**
   答：map 文件查变量最终地址落在该核 DSPR 区间（对照 DS/链接脚本符号）；调试器读写观察延迟；再在压力工况下对比放置前后的时序抖动。三步走完才算闭环。
