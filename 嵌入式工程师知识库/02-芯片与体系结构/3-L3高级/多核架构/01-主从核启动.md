# 主从核启动（TC377 三核 & AUTOSAR 多核）

> 一句话定位：多核不是"三个 main 一起跑"——核 0 先行初始化共享资源、SSW 释放从核、各核在同步点会合，主从职责划清楚，才不会出现"从核访问了没初始化的时钟"这类时序惨案。
> 等级：L3 ｜ 前置：[01-TC377-BMI与引导头](../../2-L2进阶/启动流程/01-TC377-BMI与引导头.md)

## 太长不看

- **人话直觉**：开店模型：店长（核0）备货开门口，喊伙计（从核）上岗，到齐开张。
- **本篇解决**：从核什么时候被释放？谁负责初始化共享资源、各核在哪会合？
- **赶时间记住 3 条**：
  1. CPU0 先行，启动代码写从核入口+释放；
  2. 共享资源单一归属初始化；
  3. 同步栅栏会合后才进主循环。

TC377 引导入口（BMI/BMHD）见 [../启动流程/01-TC377-BMI与引导头](../../2-L2进阶/启动流程/01-TC377-BMI与引导头.md)；从核代码在链接脚本里的分区见 [../启动流程/03-链接脚本与分散加载](../../2-L2进阶/启动流程/03-链接脚本与分散加载.md)。

## 原理

### TC377 三核启动顺序

- 复位后 **CPU0 先行**：SSW 校验 BMHD 后先放 CPU0 跑用户程序；CPU1/CPU2 处于等待状态，由启动流程按配置释放（起始地址与释放机制以 UM 的 SSW/多核启动章节为准）。
- 各核起始地址：CPU0 来自 BMHD 的 STADABMHD；从核的入口地址由启动配置指定（**具体配置载体查 UM**——工程上通常由启动软件/启动代码写从核起始地址寄存器后置释放位）。
- 从核被释放后从各自入口执行，与 CPU0 并行。

### 从核启动代码差异：只做"自己那份"

| 初始化项 | 主核（CPU0） | 从核（CPU1/2） |
|---|---|---|
| 时钟/PLL | 做（全局唯一） | **不做**，等待主核完成 |
| Flash/DMU 配置 | 做 | 不做 |
| 看门狗全局配置 | 做 | 不做 |
| 各核本地栈/CSA | 各自做 | 各自做 |
| OS 调度器 | StartOS | StartOS（各核自己的） |

从核若重复配 PLL/Flash，等于两核并发写同一外设寄存器——竞态与时序双重灾难（共享资源纪律见 [03-核间通讯与共享资源](03-核间通讯与共享资源.md)）。

### 启动同步点（栅栏等待）

- 目的：从核等主核把**共享资源**（时钟、共享 RAM、核间通讯设施）初始化完，再开始使用。
- 实现概念：共享内存中的"就绪标志" + 原子操作（置 1）+ 自旋等待——本质是个启动栅栏（barrier）；实现细节必须用原子/带屏障的访问，禁止裸 volatile 自旋（正确姿势见 [03-核间通讯与共享资源](03-核间通讯与共享资源.md)）。
- 栅栏的两侧职责：主核"置完所有就绪标志后最后放行"，从核"等齐全部标志才通过"——少等一个标志就是一个偶发 bug。

### AUTOSAR 多核视角：StartOS 与 EcuM 协调

- 每个核都有自己的 OS 实例（同一 OS 镜像的各核调度域），各核入口最终各自调用 `StartOS()`；
- **EcuM 主从协调**：主核 EcuM 负责上下电流程，从核 EcuM 随主核阶段推进（从核通常在主核进入 RUN 前被拉起并完成初始化）；跨核的启动/下电顺序由 EcuM 与 OS 的核间接口保证（概念详见 [07 区系统服务栈](../../../07-AUTOSAR架构/2-L2进阶/系统服务栈/README.md) 与 [07 区多核集成/主从核启动](../../../07-AUTOSAR架构/3-L3高级/多核集成/01-主从核启动.md)）。
- 下电顺序是启动的镜像：从核先停（任务收尾、退出调度），主核收尾共享资源并执行最终下电——顺序反了就是"从核访问已关外设"。

## 代码/实操

**主核释放从核（概念伪代码，寄存器以 UM 为准）**：

```c
/* CPU0：全局初始化完成后 */
Ifx_Cpu_setStartAddress(CPU1, &core1_start);   /* 写从核起始地址 */
Ifx_Cpu_releaseCore(CPU1);                     /* 置释放位（时序按 UM） */

/* CPU1 入口（core1_start）：只做本地初始化 */
void core1_start(void)
{
    /* 不碰时钟/Flash！ */
    init_local_stack_and_csa();
    wait_startup_barrier();      /* 等主核共享资源就绪标志 */
    StartOS();                   /* 本核 OS 调度 */
}
```

- **TRACE32 观察多核启动**：
  ```
  ; attach 后切换核：Peripherals/Cores 窗口选 CPU1
  ; 断点挂 core1_start 验证从核入口
  ; 观察释放前后从核 PC（停止/运行状态）
  ```
- **启动时序验证清单**（评审/联调各过一遍）：

| 验证项 | 通过标准 |
|---|---|
| 从核入口命中 | 断点挂在 core1_start 能停 |
| 全局初始化唯一性 | 全局搜索确认时钟/Flash 初始化只在主核路径 |
| 栅栏双向到达 | 两核都过栅栏且无死等（加超时计数观测） |
| 从核本地栈/CSA | 第一个函数调用前已初始化（看 SP/FCX 初值） |
| 共享资源首访问时间 | 均晚于主核就绪标志置位 |
| 下电顺序 | 从核先停，主核最后关共享外设 |
| 栅栏超时保护 | 栅栏等待带超时计数，死等能被检出 |
| 从核首任务时序 | 首个任务运行晚于主核 StartOS |

## 易错点与陷阱

- **从核重复初始化时钟/Flash**：并发配置共享外设，轻则配置丢失、重则总线挂死——从核启动代码务必只含本地初始化。
- **从核"抢跑"**：主核还没初始化完共享资源，从核已开始用（比如核间中断/共享缓冲），偶发数据错乱——栅栏等待不能省。
- **从核栈/CSA 没配就调函数**：入口处第一件事是设栈和 CSA 指针，顺序错了入口即跑飞。
- **释放时序不查 UM**：写起始地址与置释放位之间可能有硬件要求（延迟/顺序），拍脑袋写会偶发从核不启动。
- **多核镜像链接冲突**：各核代码/数据区在链接脚本中重叠，互相踩踏（见 [../启动流程/03-链接脚本与分散加载](../../2-L2进阶/启动流程/03-链接脚本与分散加载.md)）。
- **下电顺序反着来**：主核先睡、从核还在跑并访问已被关的外设——下电流程同样是"从核先停、主核收尾"。
- **栅栏标志用普通变量**：编译器优化或可见性延迟导致从核"看见了假就绪"——标志必须原子+屏障实现。
- **只测启动不测下电**：下电顺序 bug 藏在"偶发起不来"背后，上下电各一千次的压力测试是验收底线。
- **打印日志本身依赖未初始化设施**：从核入口用串口打印，而串口/时钟还在主核手里——入口期日志用内存标记替代打印。

## 面试高频题

1. **TC377 三核的启动顺序是怎样的？**
   答：复位后 CPU0 先跑用户程序；主核完成全局初始化后写从核起始地址并释放从核；各核各自本地初始化后在同步点会合，再进各自 OS 调度。
2. **从核启动代码为什么不能初始化时钟？**
   答：时钟/PLL 是全局共享资源，归属主核；两核并发配置会竞态写寄存器，且从核看不到"初始化是否完成"。
3. **什么是启动同步点？怎么实现？**
   答：主从核在共享资源就绪前的会合点（栅栏）：共享内存就绪标志 + 原子置位 + 自旋等待。
4. **AUTOSAR 里多核怎么启动？**
   答：各核入口各自调用 StartOS；EcuM 主从协调：主核主导上下电流程，从核随阶段推进，保证跨核顺序。
5. **从核不启动，你怎么排查？**
   答：查释放链：主核是否走到释放代码 → 起始地址寄存器值 → 释放位是否置上 → 从核 PC 是否停在入口 → 从核栈/CSA 是否初始化 → 栅栏是否死等。
6. **多核下电为什么要"从核先停"？**
   答：从核停了主核才能安全关闭共享外设；反过来从核会在主核关时钟/外设后继续访问，产生总线错误。
