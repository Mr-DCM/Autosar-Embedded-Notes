# 中断优先级实践：从 SRPN 到 OS 天花板

> 一句话定位：TC3xx 用 SRPN（0~255，号大优先）做硬件仲裁，但 AUTOSAR OS 的 Cat1/Cat2 分类与内核临界区给这些数字套上了工程约束——优先级表是团队资产，不是个人灵感。
> 等级：L2 ｜ 前置：[01-SRC模块](01-SRC模块.md)、[02-IR路由与多核分配](02-IR路由与多核分配.md)

## 原理

### TriCore 的优先级仲裁模型

- 每个源带 SRPN（Service Request Priority Number，见 [01-SRC模块](01-SRC模块.md)），投递到核后与核的"当前中断优先级"比较：号更大则抢占，否则挂起等待；
- 核内当前优先级保存在架构状态寄存器（ICR 类）中，进 ISR 自动抬升、退出恢复；OS 内核进出临界区时主动抬高它来屏蔽低优中断（思想类似 Cortex-M 的 BASEPRI，实现细节查 UM/内核架构手册）；
- 中断入口按优先级（及服务类型）索引向量表（单核服务与跨核服务在向量布局上有区别，槽位组织查 UM 中断章节）。

### 服务类型：单核服务与跨核服务（概念）

- **单核服务**：请求由本核外设/软件产生、在本核 ISR 执行，绝大多数中断属于此类；
- **跨核服务**：借助核间请求机制，让一个核的触发由另一个核响应（典型：GPSR 通知，见 [02-IR路由与多核分配](02-IR路由与多核分配.md)）。工程意义：把"事件产生"与"处理负载"解耦到不同核。

### 与 AUTOSAR OS 的耦合

| 概念 | 含义 | 工程约束 |
|---|---|---|
| Cat1 ISR | 不经 OS 管理的一类中断 | 快进快出；不调用 OS API；通常给最高实时性需求（如电流环），数量严格受限 |
| Cat2 ISR | OS 管理的中断 | 可调用部分 OS API（如激活任务）；进出有 OS 包装，延迟略高 |
| OS 内核优先级 | OS 内核占用的高优先级窗口 | 内核执行期间屏蔽低优中断；Cat1 的 SRPN 一般要求低于/高于该窗口的策略由 OS 实现约定（以所用 OS 文档为准） |
| 优先级天花板（概念） | 任务的"逻辑优先级"由其上所有 ISR/任务推导 | ISR 抢占任务导致的共享资源竞争，用资源 ceiling 机制保护 |

一句话记忆：**SRPN 决定"硬件谁先跑"，OS 分类决定"软件允许它干什么"**——两个维度都要对，配置才算对。

### 优先级分层模板（概念）

| 层（示意） | 内容 | 约束 |
|---|---|---|
| 最高层 | 极少数 Cat1（电流环/安全相关） | 禁 OS API、时间预算最严、数量审批 |
| 高层 | Cat2 硬实时事件 | 可激活任务，短执行 |
| 中层 | Cat2 常规外设 | 常规预算 |
| 低层 | Cat2 慢速/统计类 | 尽量移交任务处理 |
| OS 内核保留窗口 | OS 内核级 | 应用不得占用（策略以 OS 文档为准） |

分层区间数字由 OS 供应商约定与项目约定共同决定，模板的价值在于"层级语义"固定下来：新人加中断先对号入层，再领具体 SRPN。

### ISR 移交任务的正确姿势

中断上下文是"最贵的上下文"：抢占能力强、限制多。标准模式是"ISR 收数据/置事件 → 激活任务 → 任务里做全部重活"：

- ISR 内只做：读硬件、清源、写队列/标志、激活任务（Cat2 允许的 OS API）；
- 共享队列按"单生产者-单消费者"设计最稳；多生产者就要锁或每源独立队列；
- ISR 执行时间预算（如若干微秒量级，项目自定）写进优先级表并实测回归。

### 优先级配置表的维护方法

把全项目中断收敛进一张表（放版本库，与 Ecuc/Tresos 配置对照评审），字段建议：

| 字段 | 示例 | 说明 |
|---|---|---|
| 中断源 | GTM 某 TOM 组中断 | UM 源命名 |
| SRPN | （示例）37 | 唯一性/分层规划见下 |
| TOS | CPU1 | 与 ISR 注册核一致 |
| ISR 名 | OsCat2Isr_xxx | OS 生成名 |
| 类别 | Cat2 | Cat1 需额外审批 |
| 上限时间 | ≤ 20 us | ISR 执行时间预算 |
| 备注 | 共享缓冲 sBuf，任务 T2 消费 | 天花板评审依据 |

维护纪律：改中断先改表、再改配置工具；表与生成配置做 diff 作为评审附件。

### 过高与过低的后果

- **SRPN 过高**：抢占 OS 内核/关键区，引发调度异常或数据竞争；把别的核的中断节奏也带偏（共享资源竞争升级）；
- **SRPN 过低**：响应延迟变大，事件积压甚至溢出（边沿型丢事件）；上层的任务截止期跟着失守；
- **同级堆叠**：互不抢占造成长尾等待，抖动不可控——同核尽量避免同 SRPN。

## 寄存器与位表

> SRPN/TOS 位号见 01 篇与 UM；本篇补充 CPU 侧关注点。

| 关注点 | 位置 | 权威出处 |
|---|---|---|
| 当前中断优先级（ICR 类字段） | CPU 架构状态寄存器 | UM/内核架构手册 |
| 中断向量表布局（按优先级/服务类型索引） | 向量表组织章节 | UM |
| OS 内核优先级策略 | OS 移植层文档 | 所用 OS 文档 |
| 每核可用的优先级范围 | 中断章节 | UM |

### 从表到配置的核对流程

优先级表要真正"管住"配置，靠的是固定核对流程：

1. 表先行：新增/修改中断先在表上提出变更（含 SRPN/TOS/类别/预算）；
2. 配置落地：按表修改 Tresos/EB 与 OS 配置，生成配置报告；
3. 机械比对：表内容与生成报告做 diff，差异逐条解释（工具脚本或人工皆可，关键是留痕）；
4. 实测回归：ISR 时间预算项用 TRACE32/示波器实测，超标回表调整；
5. 归档：变更记录随版本入库，任何"绕过表格直接改配置"的行为在评审视为缺陷。

这套流程的本质是把"中断配置"从个人手艺变成团队资产——人可以流动，表不能断。

## 双平台对照（TC377 vs S32K/Cortex-M）

| 维度 | TC377（TriCore） | S32K（Cortex-M NVIC） |
|---|---|---|
| 优先级数量 | SRPN 0~255，号大优先 | 实现位宽（常见 16 级），号小优先 |
| 屏蔽机制 | ICR 当前优先级抬升（OS 操纵） | BASEPRI/PRIMASK |
| 向量入口 | 按优先级（及服务类型）索引 | 按源编号直接索引 |
| RTOS 集成 | Cat1/Cat2 由 OS 定义 | bare-metal/RTOS ISR 惯例分层 |
| 多核 | TOS 路由 + 每核独立仲裁 | 单核不涉及 |

## 代码/实操

- 配置评审清单（逐条过）：
  1. 每个 ISR 的 SRPN/TOS/类别与优先级表一致；
  2. 同核无重复 SRPN（或经评估确认）；
  3. Cat1 只给确有需要的源，且内部无 OS API 调用；
  4. ISR 执行时间有预算且实测过（TRACE32 性能分析/示波器翻转引脚）；
  5. ISR 与任务共享的资源都登记并有保护手段；
  6. OS 内核优先级窗口与 Cat1 的关系符合 OS 供应商约定。
- TRACE32：断点进 ISR 看当前优先级字段验证抢占关系；统计 ISR 进入次数与耗时分布，对照"上限时间"列做回归。

## 易错点与陷阱

1. **Cat1 里调 OS API**：直接违反 OS 约定，轻则 Protection Hook，重则调度器状态损坏；
2. **优先级方向搞反**：Cortex-M 老习惯带到 TriCore，所有抢占关系颠倒，偶发"低优抢高优"的灵异现象；
3. **只改配置不改表**（或反之）：表与实际漂移，三个月后没人说得清哪个是真的；
4. **ISR 里做长活**：关抢占状态下跑毫秒级循环，其他中断全体迟到；长活移交任务（Cat2 里 ActivateTask 是标准姿势）；
5. **跨核共享资源忽视中断上下文**：核 A 的 ISR 与核 B 的任务竞争同一缓冲，双核都要按"天花板"思想保护；
6. **同 SRPN 同核**：长尾等待不可控，评审时当作坏味道处理。

## 面试高频题

1. **Cat1 与 Cat2 ISR 的区别？**
   答：Cat1 不经 OS 管理，进出无包装、延迟最小，但不能调用 OS API，只留给最高实时需求；Cat2 由 OS 管理并可调用部分 API（如激活任务），代价是进出开销略大。

2. **为什么 OS 内核要"抬高"当前中断优先级？**
   答：内核临界区（调度器/资源管理数据结构）不能被低优 ISR 打断，抬升当前优先级即硬件级屏蔽，离开临界区再恢复——与 Cortex-M 的 BASEPRI 思想相同，实现载体是 TriCore 的 ICR 类状态。

3. **SRPN 相同的两个中断在同一个核上会怎样？**
   答：互不抢占，先被接受者先执行，另一个挂起等待；行为可预期但延迟不可控，工程上避免同核同优先级堆叠。

4. **一个中断的优先级定高了/低了各有什么症状？**
   答：过高：抢占内核关键区、踩碎调度与共享数据，出现随机错乱（难查是因为"看起来无关"）；过低：响应迟、事件积压溢出、上层截止期失守，症状相对"温和但持续"。

5. **怎么系统地管理一个项目的全部中断配置？**
   答：维护唯一的优先级配置表（源/SRPN/TOS/类别/ISR 名/时间预算/备注）入库，配置工具从表出，评审对表做 diff；ISR 执行时间纳入回归测量。

6. **什么时候该把中断里的工作移交任务？**
   答：凡是非"取数/清源"的重活（协议解析、计算、IO 操作）都移交：Cat2 ISR 激活任务即可。判据是 ISR 时间预算——预算内的短处理可留在 ISR，超出预算的一律移出去，否则拖累同核所有更低优先级中断与任务。
