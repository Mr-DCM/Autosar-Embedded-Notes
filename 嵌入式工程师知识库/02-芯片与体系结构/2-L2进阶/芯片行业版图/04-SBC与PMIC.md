# SBC 与 PMIC：ECU 的心脏起搏器

> 一句话定位：SBC 把供电、复位、看门狗、唤醒四件事打进一颗芯片——EcuM 上下电时序、WdgM 喂狗、睡眠电流、复位溯源四类"软件怪病"的根因常在它身上；NXP UJA/FS、Infineon TLE/TLF、TI TPS6538x 三家地图与四个软件交点一篇讲清。
> 等级：L2 ｜ 前置：[01-KL30-KL15供电](../../../03-硬件基础/2-L2进阶/ECU硬件常识/01-KL30-KL15供电.md)

## 原理

### SBC 是什么：四合一

SBC（System Basis Chip，系统基础芯片）= 多路电源（DCDC/LDO 轨）+ 复位发生器 + 看门狗 + 唤醒源管理，一颗芯片管住 ECU 的"活着与睡着"：

与分立方案（独立 LDO + 独立看门狗 + 复位芯片）对比：SBC 集成度高、安全机制联动（喂狗失败→复位→复位计数→进入锁死模式）、待机功耗低；分立方案 BOM 灵活、单一故障隔离好——**功能安全项目倾向 SBC（安全机制成套认证），低成本 ECU 用分立**。

### 三家地图（家族级，能力以 DS 为准）

| 厂商 | 系列 | 定位 | 常与谁配对 |
|---|---|---|---|
| NXP | UJA1132/UJA1169（mini SBC，1169 内置 CAN/LIN 收发器） | 车身 ECU 降本集成 | S32K1 车身节点 |
| NXP | FS26/FS85（安全 SBC） | 高 ASIL 供电+诊断 | S32K3/MPC57xx（FS26 与 S32K3 官方搭配） |
| Infineon | TLE926x/TLE927x（中端 SBC，含 CAN/LIN） | 车身/通用 ECU | AURIX/通用 MCU 车身节点 |
| Infineon | TLF35584/TLF35585（多轨安全 PMIC） | 多轨安全供电 | AURIX TC3xx（官方搭配） |
| TI | TPS65381x（多轨安全 PMIC） | 安全 MCU 供电 | Hercules/TMS570 生态为主 |

**看门狗形态是分档的关键**：低端 SBC 是简单超时窗口；安全 SBC（FS26/TLF）是**窗口看门狗 + 问答式（Question-Answer，按伪随机序列答询）**——后者能防"程序跑飞了还在傻喂狗"，是 ASIL 项目的标配，对应 AUTOSAR 侧 WdgM 的 Alive/Deadline supervision 分层（[11 区/看门狗](../../../11-功能安全与信息安全/2-L2进阶/看门狗与监控/README.md)）。

## 选型对照表

| 关注对象 | 看什么 | 权威出处 |
|---|---|---|
| 轨数与电压 | 各轨电压/电流是否覆盖 MCU 与外设需求 | SBC DS + MCU DS 供电章节 |
| 看门狗类型 | 简单窗口还是问答式；窗口开闭时间 | SBC DS 看门狗章节 |
| 唤醒源 | 本地（引脚）/CAN 总线/LIN；睡态下哪些可用 | SBC DS + 应用笔记 |
| 复位行为 | 复位类型（POR/功能复位）、复位计数与锁死（FOTA 失败保护） | SBC DS |
| 低功耗模式 | Sleep/Stop/Off 各态电流与轨保持情况 | SBC DS 电气特性（整机 KL30 预算表） |

## 多平台对照（双平台扩展版）

SBC 与 MCU 常成"官方搭档"，两家平台的典型供电链路：

| 维度 | TC377 典型 | S32K 典型 |
|---|---|---|
| 搭档 SBC/PMIC | TLF35584（多轨：核/IO/模拟轨） | UJA1169（车身，含收发器）/ FS26（S32K3 搭档） |
| 喂狗接口 | SPI 问答式（TLF 安全问答） | 窗口/问答（FS26） |
| 唤醒管理 | SBC 汇总唤醒→释放 MCU | 同左；UJA1169 连收发器唤醒一并管 |
| 软件落点 | WdgM→Wdg 驱动→SPI 问答；EcuM 下电请求 SBC 进 Sleep | 同左（模块名一致，配置对象不同） |

**软件栈是无差别复用的**：AUTOSAR 的 Wdg/EcuM/CanTrcv 抽象抹平了 SBC 差异——这正是 BSW 工程师跨 SBC 迁移比裸机工程师快的原因。

## 代码/实操

四个软件交点，每个都对应一类高频问题：

1. **EcuM 唤醒源**：SBC 唤醒中断 → MCU 唤醒脚 → EcuM WakeupSource 上报 → 应用跑唤醒原因判断（[EcuM/03-唤醒源](../../../07-AUTOSAR架构/2-L2进阶/系统服务栈/EcuM/03-唤醒源.md)、[02-唤醒电路](../../../03-硬件基础/2-L2进阶/ECU硬件常识/02-唤醒电路.md)）；
2. **喂狗时序**：窗口看门狗必须"窗口内喂、太早太晚都复位"——喂狗任务的周期与窗口参数要联合设计，见 [01-WdgM与Windowed-WDT](../../../11-功能安全与信息安全/2-L2进阶/看门狗与监控/01-WdgM与Windowed-WDT.md)；
3. **复位溯源**：复位后先读 SBC 复位原因寄存器（POR/看门狗/软件请求），写进 NvM 供诊断读取（DID）——[09 区/复位溯源](../../../09-调试与测试/3-L3高级/调试方法论/01-复位溯源.md) 的硬件侧；
4. **睡眠链路**：下电时 EcuM → 请求 SBC 进 Sleep → SBC 切轨只留唤醒域 → 电流降到目标值——任何一步没做完，睡眠电流超标（[04-睡眠电流假醒](../../../09-调试与测试/3-L3高级/调试方法论/04-睡眠电流假醒.md)）。

## 易错点与陷阱

1. **喂狗窗口设错**：窗口开得太窄，任务抖动一下就复位；开得太宽失去保护意义——窗口参数由喂狗任务周期的最坏抖动决定，不是拍脑袋；
2. **上下电时序不核对**：SBC 各轨上电顺序与 MCU 复位释放有先后要求（DS 时序图），顺序错会 brown-out 或反复复位——带 SBC 的板 100% 要过一遍时序评审；
3. **唤醒源没配就睡**：请求 Sleep 前未使能任何唤醒源，ECU 一觉不醒只能断 KL30——睡前 checklist 第一条就是"唤醒源使能确认"；
4. **睡眠电流超标只查软件**：先读 SBC 当前模式寄存器确认它真的睡了（而不是 Standby），再查收发器（[03 篇](03-收发器与物理层.md)），最后才轮到应用代码的 IO/外设漏关；
5. **复位计数/锁死模式当 bug**：安全 SBC 有连续复位计数上限，超限进入锁死（防刷写失败循环）——FOTA 场景要专门设计恢复路径；
6. **把 SBC 当纯电源芯片**：它的看门狗与复位是安全机制链的一环，WdgM 的分层设计（ Alive/Deadline/逻辑监督）要落到 SBC 能力上对齐。

## 面试高频题

**Q：SBC 和"独立 LDO + 独立看门狗"方案比，优缺点是什么？**

答：SBC 优点——集成（供电+复位+看门狗+唤醒）、安全机制成套（问答式看门狗、复位计数锁死、低功耗管理）且有安全认证材料，适合功能安全项目；缺点——单点故障影响面大、选型绑定后灵活性差、需要专门驱动。分立方案反之，低成本非安全 ECU 常用。

**Q：窗口看门狗为什么比简单超时看门狗安全？问答式又强在哪？**

答：窗口式防"喂太早"——程序跑飞后高频空转也能及时喂狗的场景，窗口式要求喂狗时刻落在窗口内；问答式更进一步，SBC 发伪随机问题、软件算答案，防"错误的代码在正确的时间喂狗"（喂狗代码被误执行/跑飞恰好在喂）。对应 WdgM 是 Alive/Deadline supervision + 逻辑监督的分层。

**Q：ECU 睡眠电流超标，你的排查顺序？**

答：①读 SBC 模式寄存器——它睡了吗（Sleep vs Standby 差一个数量级）；②读收发器模式——总线唤醒过滤配了吗；③查 MCU 侧——IO/外设/时钟是否按睡前 checklist 关闭；④量各轨电流定位漏电支路。原则：从"谁管电"往"谁用电"查，先芯片模式后应用代码。
