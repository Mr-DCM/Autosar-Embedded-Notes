# 01-看门狗原理

> 一句话定位：建立普通看门狗与窗口看门狗的两种直觉，搞懂喂狗序列、独立时钟为什么是功能安全的刚需，为双平台 WDT 和 WdgM 联动打底。
> 等级：L1→L2 ｜ 前置：[MCAL第一课-从点灯到分层驱动](../../00-入门导读/01-MCAL第一课-从点灯到分层驱动.md)

## 原理

看门狗 = **一个到期就咬人的倒计时器**：程序必须在超时前"喂狗"（写特定序列复位计数器）。程序跑飞、死循环、中断风暴时喂狗动作停摆，狗到期触发复位——用最小的硬件换回系统最后的自愈手段。

### 两种狗：普通 vs 窗口

| | 普通（独立）WDT | 窗口 WDT |
|---|---|---|
| 直觉 | **喂晚就咬** | **喂晚咬，喂早也咬** |
| 合法喂狗区间 | (0, T_timeout) 任意时刻 | (T_open, T_close) 之间，之前之后都复位 |
| 防什么 | 程序彻底不跑（死机/跑飞） | 额外防"喂狗任务卡死但被别处循环狂喂"的假活 |
| 咬人方式 | 直接复位（或先中断再复位） | 越窗复位；有的平台窗口前有中断预警 |

口诀：**普通狗防"死"，窗口狗防"假活"**——喂狗代码若被错误地塞进一个高频空转循环，普通狗照样被喂得白白胖胖，只有窗口狗能戳穿"喂得太勤"这件事本身。

### 喂狗姿势：先写 Key，再写 Service

喂狗从来不是"写一个寄存器"这么简单，标准套路是**两步序列**：

1. **Key 解锁**：向密码寄存器写魔数（各平台不同），表明"我懂规矩"；
2. **Service 喂狗**：向服务寄存器写入喂狗命令，计数器清零重新倒数。

两步顺序错、间隔错、或中间插了别的写操作——多数实现视为**非法序列，直接复位**。这样设计的原因：程序跑飞后 PC 乱跳，误打误撞写中服务寄存器的概率不低；要求先写对 Key（一个特定值）再紧跟写服务，乱跳代码几乎不可能碰巧走出正确舞步。

### 为什么窗口 WDT 是功能安全刚需

ISO 26262 要求软件能检出"逻辑流错误"。危险场景：喂狗函数被多个任务/中断调用，某个低优先级任务卡死，但另一个高频任务仍把狗喂着——普通 WDT 完全无感。窗口 WDT 把"喂狗必须落在规定区间"变成硬约束，喂狗时机被任务调度节奏决定，**节奏乱了（卡死、抢占异常）就立刻越窗**，等于把调度健康也纳入监视。

### 慢速独立时钟的意义

看门狗时钟必须**独立于主时钟**（常用片内 LPO/IRC 振荡器）：主 PLL 挂了、时钟树配错、Mcu 把外设时钟全关了，狗照样在倒数——如果狗吃的是主时钟的饭，系统时钟一死狗也跟着死，最后一点自愈能力就没了。代价是 LPO 精度差（±数 %），算超时时间要留裕量。

## 双平台硬件单元对照

| 对照项 | TC377（WDT） | S32K（WDOG/WWDT） |
|---|---|---|
| 狗的档位 | CPU WDT（锁步核监督）+ Safety WDT（安全管理） | S32K1 WDOG（窗口可选）/ S32K3 WWDT（窗口+预警中断） |
| 窗口支持 | 有（服务寄存器上/下限 SRVL/SRVH） | S32K1 CS.WIN 位开窗；S32K3 原生 WWDT |
| 独立时钟 | 独立低频振荡源 | LPO 1kHz，独立于 SOSC/PLL |
| 喂狗序列 | 解锁 Key + 写服务值 | 解锁序列（写 CNT 魔数）+ 喂狗 |
| 到期行为 | 复位/中断可配 | S32K1 中断或复位；S32K3 预警中断后再复位 |
| 调试行为 | 调试器挂起可暂停 | CS.DBG 位决定挂起时暂停与否 |

## MCAL 配置要点

| 配置项 | 含义 | 典型值 | 易错点 |
|---|---|---|---|
| WdgTimeoutPeriod | 超时周期 | 500~2000 ms | 按最坏喂狗间隔 ×1.5 裕量，太短误咬 |
| WdgWindowPeriod | 开窗点（超时的 %） | 50%~75% | 开太晚=错过正常喂点，开太早=窗口名存实亡 |
| WdgTriggerMode | 到期动作 | 复位（或先中断） | 选"仅中断"不复位=失去自愈，量产禁用 |
| WdgClockReference | 独立时钟源 | LPO/独立振荡 | 误选主时钟派生源，违背独立性 |
| WdgSettingsFast/Normal/Slow | 分模式超时集 | 各模式独立 | 刷写/下电模式忘了配更长时间，升级被咬 |

## 代码示例

```c
/* 喂狗的正确姿势：Key 解锁 → 紧跟 Service（平台伪码，寄存器名见后续双平台篇） */
void Wdg_Feed(void)
{
    Wdt->KEY = WDT_UNLOCK_KEY;        /* 第一步：写解锁魔数 */
    Wdt->SRV = WDT_SERVICE_VALUE;     /* 第二步：紧跟喂狗值，计数器清零 */
    /* 两步之间不得插入任何对该模块的其他写操作！ */
}

/* MCAL 标准 API 视角：把"还要多久到期"延后（喂狗的标准化身） */
void Task_100ms(void)
{
    static uint8 u8Alive = 0u;
    u8Alive++;
    if (u8Alive >= 5u)                /* 500ms 事务一次，落在窗口内 */
    {
        u8Alive = 0u;
        Wdg_SetTriggerCondition(100u); /* 延后 100 个 tick 再到期（间接喂狗） */
    }
}
```

## 易错点与陷阱

1. **喂狗序列被拆**：中断恰好插在 Key 与 Service 之间并碰了模块寄存器，序列非法→复位；对策：喂狗函数做成不可分割区（关中断或原子宏），且全局只此一处。
2. **多处喂狗**：几个任务都调喂狗，单点卡死被掩盖，狗形同虚设；对策：喂狗收敛到一个受监督的调度点（这正是 WdgM 存在的意义，见 [04-WdgM联动](04-WdgM联动.md)）。
3. **窗口算错**：开窗点配得晚于正常喂狗点，每次都"早喂复位"；对策：开窗 < 最小喂狗周期 < 关窗 < 最大喂狗周期，四点一线验算。
4. **超时裕量不足**：偶发长任务/刷写把喂狗挤晚，量产车偶发复位；对策：按最坏调度延迟 ×1.5 设超时，示波器量喂狗抖动。
5. **调试器一挂狗就咬**：停在断点超时复位，无法调试；对策：配 DBG 位让调试挂起时暂停计数（仅调试版），量产恢复。
6. **下电/刷写模式沿用正常超时**：擦写 Flash 阻塞喂狗，升级到一半被咬；对策：WdgSettings 分模式配更长超时，进刷写前 Wdg_SetMode。

## 面试高频题

- **Q：窗口看门狗比普通看门狗强在哪？**
  A：普通狗只防"不喂"（死机），窗口狗额外防"喂得太早/太勤"（假活）——把喂狗时机约束在窗口内，等于同时监视了任务调度的节奏是否正常。
- **Q：为什么喂狗要"先 Key 后 Service"两步？**
  A：程序跑飞后乱序写操作很容易碰到单个寄存器，但按正确顺序连写两个特定值的概率趋近于零——两步序列是给"合法喂狗"加的防伪签名。
- **Q：看门狗时钟为什么要独立？**
  A：若狗吃主时钟的饭，时钟树一挂狗也停摆，系统失去最后的自愈手段；独立 LPO 保证主频域全死时狗还在倒数并复位系统。
- **Q：超时时间怎么定？**
  A：大于最坏情况下两次喂狗的间隔（含任务抖动、刷写阻塞）再乘裕量；同时尽量短于外部可容忍的无响应时间，两者取交集。
