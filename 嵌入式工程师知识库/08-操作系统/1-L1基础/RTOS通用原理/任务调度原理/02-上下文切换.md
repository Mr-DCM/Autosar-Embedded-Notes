# 02-上下文切换

> 一句话定位：上下文切换 = 把上一个任务的寄存器现场存进它的栈、把下一个任务的现场从它的栈里恢复、换栈指针——RTOS"换人"的全部物理动作，也是一切临界区规则存在的原因。
> 等级：L2 ｜ 前置：[01-调度模型](01-调度模型.md)

## 核心概念

上下文（Context）= 一个任务被换下 CPU 那一刻的全部"现场"，清单如下：

- 通用寄存器（Cortex-M 的 R0~R15、TriCore 的 D*/A*/P* 寄存器）；
- 程序计数器 PC 与程序状态字（xPSR/PSW）——决定"从哪条指令、什么标志位继续"；
- 可选：浮点寄存器（Cortex-M4F 的 S0~S31、TriCore 的上下文对）。

**上下文切换就是"存现场 → 换栈 → 恢复现场"三步**，全部动作围绕每个任务自己的栈展开：

```plantuml
@startuml
title 一次抢占式上下文切换的全过程（异常入口触发）
skinparam defaultFontName "Microsoft YaHei"
participant "低优任务 L\n(在跑)" as L
participant "异常入口\n(PendSV/SysCall/Trap)" as EX
participant "调度器" as SCH
participant "高优任务 H\n(就绪)" as H
L -> L : 正在执行
-> tick 到期 / 服务调用\n激活了 H
EX -> L : 保存 L 的上下文\n压入 L 的栈
EX -> SCH : 调度决策：\n从就绪集合选 H
SCH -> SCH : 更新 TCB：\nL.sp = 当前栈顶；读出 H.sp
SCH -> H : 从 H 的栈恢复上下文\n（最后弹 PC/PSW）
H -> H : 从上次被打断处继续执行
note over SCH : 换的本质是“栈指针”——\nTCB 里存着每个任务的 sp，\n谁的栈谁做主
@enduml
```

先分清两个常被混淆的动作：**中断进出不是切换**——ISR 打断任务再返回，SP 始终指着同一个任务的栈，任务是"同一个人挨了一下"；只有 SP 从 A 的栈换到 B 的栈，才叫上下文切换。

## 详解

### 切换的四条来路

| 来路 | 谁发起 | 典型时刻 |
|---|---|---|
| 主动让出 | 任务自己 | 调用延时/等待类阻塞 API、TerminateTask |
| 被动抢占 | 内核 | API 内部激活了更高优任务（ActivateTask/SetEvent/Give） |
| tick 驱动 | 时钟 ISR | 延时到期唤醒、同优先级时间片轮转 |
| ISR 退出 | 中断尾部 | ISR 里唤醒过高优任务，退出时挂起 PendSV 完成切换 |

### 每个芯片家族的做法

| 平台 | 硬件帮了什么 | 软件还要做什么 |
|---|---|---|
| Cortex-M（S32K） | 异常入口自动压 8 个字：xPSR/PC/LR/R12/R3~R0 | PendSV 里补压 R4~R11（用到 FPU 再压 S16~S31） |
| TriCore（TC377） | CALL/RET 类指令经 CSA 链自动存取上/下文（UCX/LCX），PCXI 指向链头 | 内核初始化 CSA 池、为任务预链接上下文与栈 |
| 老式 ARM7/MIPS | 全靠软件 | 逐个压栈保存全部通用寄存器再切换 |

Cortex-M 的经典设计：**PendSV 设为最低异常优先级**，保证"切换动作"永远在所有 ISR 之后一次性完成、不被打成两半；多个异常连续到达时还能尾链（tail-chaining）省一次出栈入栈。TC377 上则由 trap/syscall 类机制进入 OS 内核完成同样的事。

### 栈：每个任务一条命

- 每个任务独立一条栈；TCB（任务控制块）里最重要的字段之一就是**栈指针 sp**——"当前是哪个任务"最终就体现在 SP 指着谁的栈；
- 栈的真实需求 = **函数调用深度 + 被抢占时压入的上下文 + ISR 嵌套压栈** 三层叠加，只算局部变量必翻车，见[内存管理](../内存管理/README.md)；
- OSEK 的省钱招：**基本任务没有 Waiting 态、跑完即结束**，切换天然 LIFO，允许基本任务共享一条栈；扩展任务会挂起、现场必须留底，必须独立栈——这正是 07 区 [Os/01-任务与调度](../../../../07-AUTOSAR架构/2-L2进阶/系统服务栈/Os/01-任务与调度.md) 里基本/扩展任务差异的内存根源。

### 切换成本与临界区的本质

- 一次切换 ≈ 几十到几百个指令周期（百 MHz 级 MCU 上亚微秒~微秒级），主要花在压/出栈；带 FPU 现场的任务更贵——Cortex-M4F 的 lazy stacking（FPCCR 的 ASPEN/LSPEN）让 FPU 现场只在 ISR 真用到时才压，省掉大半开销；
- 切换频度由优先级结构决定：高优任务越多、周期越密，切换越频繁——设计期就该把"切换开销"算进利用率，见[优先级设计](03-优先级设计.md)；
- **切换只发生在合法点（调度点）**。关中断 / 调度锁 / 持有 OSEK Resource 期间，调度点被封死，切换不会发生——这就是"临界区"的本质：不是不让别人跑，而是**不让"换人"这个动作发生**；
- 由此得出铁律：**临界区里绝不调用可能阻塞的 API**（等锁/延时/收队列）。FreeRTOS 用断言拦截，OSEK 直接错误码进 ErrorHook；更深的后果是"持锁睡眠"型死锁，见[死锁与竞态分析](../死锁与竞态分析/README.md)。

## 易错点与陷阱

1. **临界区里调用阻塞 API**。现象：任务"消失"、内核断言或 ErrorHook 报错。原因：阻塞要求切换，临界区禁止切换，逻辑矛盾。对策：临界区只留纯计算，任何"等"字辈 API 挪出去。
2. **栈只按局部变量最大值估算**。现象：偶发 HardFault/栈溢出，与负载相关。原因：漏算上下文压栈与 ISR 嵌套（中断里再调函数再压栈）。对策：三层预算叠加，再用高水位检测+栈溢出钩子实测校准。
3. **把切换当函数调用理解**。现象：以为存个返回地址就够。原因：函数调用只存 LR；切换必须存全部寄存器 + PC + PSW。对策：读一遍移植层的 PendSV 汇编或 OS 切换函数，十来行就能看懂。
4. **FPU 任务的 lazy stacking 没配好**。现象：ISR 延迟变大或浮点结果偶发错乱。原因：FPU 现场全量压栈或压栈规则与编译器不一致。对策：核对 FPCCR 的 ASPEN/LSPEN 与编译选项（-mfpu）匹配，ISR 尽量不碰浮点。
5. **ISR 里干重活**。现象：全系统任务切换、tick 全部抖动。原因：ISR 执行期间等效"隐性临界区"，一切切换被推迟。对策：顶半只登记，重活回任务，见[中断管理](../中断管理/README.md)。
6. **用毫秒级打点测切换开销**。现象：测出几十微秒，不合常理。原因：把 tick 处理、定时器链表遍历都算进去了。对策：用 DWT/STM 周期计数器围绕切换点精确打点，或引用内核厂商数据。

## 面试高频题

**Q：上下文切换具体做了哪些事？开销大概多少？**
答：①保存当前任务现场（通用寄存器、PC、PSW，按需含浮点）到其私有栈；②把当前 SP 写回其 TCB；③调度器选出下一个任务，从其 TCB 取出新 SP；④恢复新任务现场，最后弹出 PC/PSW 实现"跳转续跑"。Cortex-M 上硬件先压 8 个字，PendSV 只需补 R4~R11。开销约几十~几百周期，百 MHz MCU 上亚微秒到微秒级；带 FPU 更贵，可用 lazy stacking 优化。

**Q：Cortex-M 中 PendSV 为什么必须设成最低异常优先级？**
答：切换动作必须不可分割。若 PendSV 能被其他 ISR 打断，"旧任务现场存一半、新任务现场恢复一半"的中间态可能被破坏。设为最低优先级后所有 ISR 先跑完，PendSV 最后一次性完成切换；连续多个异常还能尾链合并进出栈，又快又安全。FreeRTOS 等主流内核的 Cortex-M 移植都遵循此约定。

**Q：OSEK 基本任务为什么可以共享栈，扩展任务不行？**
答：基本任务没有 Waiting 态：一旦运行就跑到 TerminateTask 结束，切换只发生在"运行→结束"这种 LIFO 边界，栈可弹干净复用，所以多个基本任务能共享一条栈省内存。扩展任务在 WaitEvent 处挂起，挂起期间现场必须留在栈里不能被覆盖，必须人手一条独立栈——这也是扩展任务内存开销大的根源。

**Q：为什么临界区里不能调用阻塞 API？**
答：阻塞的实现是"把自己挂进等待队列并触发上下文切换"；而临界区（关中断/调度锁/持 Resource）的作用恰是封死调度点、禁止切换。二者矛盾：轻则内核断言或返回 E_OS_RESOURCE 类错误码进 ErrorHook，重则先拿锁再睡眠直接制造死锁。工程规则：临界区只包纯计算，"等"字辈 API 一律在临界区外。
